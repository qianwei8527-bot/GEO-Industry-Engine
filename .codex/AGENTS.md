## 零、Agent 工作原则（最高优先级，覆盖一切默认行为）

### 0.1 单一架构真相源

所有 Agent 共享同一个架构上下文。不是一个 Agent 一套理解。

```
               35_CTO架构冻结.md (Primary, 不可改，唯一真相源)
                              |
               00_项目宪章.md (Primary)
                              |
               02_领域模型设计.md (Primary)
                              |
               .codex/REFERENCES.md (映射索引)
                              |
                    ↓ 所有 Agent 必须从此读取 ↓
    cto_架构师 | pm_产品经理 | be_后端开发 | fe_前端开发
    qa_质量测试 | docs_文档管理 | de_数据工程 | algo_评分算法 | ops_运维部署
                              |
                    统一架构实现（代码+文档+配置）
```

**禁止：**
- 产品 Agent 自己设计一套产品逻辑
- 后端 Agent 自己实现一套数据模型
- 前端 Agent 自己理解一套交互规则
- 任何 Agent 的产出与冻结文件不一致

**发现不一致：直接驳回，要求重读冻结文件后重新输出。**

### 0.2 开发前强制阅读（Pre-Dev Mandatory Read）

任何 Agent 在开始任何编码/文档/配置工作前，必须按顺序执行：

| 顺序 | 读取内容 | 目的 |
|------|---------|------|
| 1 | `35_CTO架构冻结.md` | 确认不违反任何冻结项 |
| 2 | `.codex/REFERENCES.md` | 确认没有重复实现已有模块 |
| 3 | 相关领域文档 (docs/XX_*.md) | 理解业务上下文 |
| 4 | 当前代码文件 | 读取要修改的源文件 |
| 5 | 当前测试文件 | 知道已有测试覆盖范围 |

**不是建议。是强制。未完成此列表不得输出任何代码。**

### 0.3 开发后强制验证（Post-Dev Mandatory Verify）

任何 Agent 完成编码/文档/配置工作后，必须按顺序执行：

| 顺序 | 验证项 | 方法 |
|------|--------|------|
| 1 | 运行测试 | `pytest` / `npm test`，确认不破坏已有功能 |
| 2 | 检查 API 一致性 | 前后端字段名、类型、路径是否对齐 |
| 3 | 更新文档 | 代码改了什么，文档同步什么 |
| 4 | 检查重复实现 | 新代码是否重复了已有模块的功能 |
| 5 | 生成变更摘要 | 做了什么、影响了什么、为什么 |

**未完成此列表不得声称"完成了"。**

### 0.4 自主执行模式（Autonomous Execution）

默认行为：**完成任务后自动进入下一项，不等待用户确认。**

可以自主完成的操作（不停、不问、直接做）：
- 代码修改、修复、重构
- 文档创建、修改、同步
- 配置新增、修改
- 测试编写、补充
- 前后端接口对接
- 命名统一、格式规范
- 重复代码清理
- 文件整理、归档

**必须暂停并等待用户确认的情况（停止条件）：**

| 场景 | 为什么停 |
|------|---------|
| 可能破坏架构冻结原则 | 冻结项不可动 |
| 可能删除用户原始战略 | 核心定位不可改 |
| 可能产生不可逆数据库迁移 | 数据不可逆 |
| 需要真实第三方支付账号 | 外部凭证 |
| 需要真实外部 API Key | 外部凭证 |
| 需要生产环境凭证 | 安全红线 |
| 涉及真实资金交易 | 安全红线 |
| 需要用户决策（多个合理选项、无法自动判断优劣） | 属于战略决策 |

**除此之外，不要问。直接做。**

## 二点五、行为规则（优先于默认路由）

以下两条规则覆盖正常路由逻辑。触发时优先执行对应规则，而非进入默认流程。

### R-001 外部模型评审

触发：用户引用GPT/Claude/其他模型的方案评估、质疑或建议

处理：
1. 重锚初心 - 回到产品宪章和冻结架构
2. 升维思考 - 不逐条回应，站更高一层评估
3. 借鉴-反驳-合成 - 取有效建议，否决冲突的
4. 输出方案 - 结构化分析表 + 优化方案 + 差异说明
5. 等待确认 - 不直接执行

### R-002 模糊指令处理

触发：用户指令抽象/模糊/有2种以上理解可能

处理：
1. 不要直接执行
2. 拆解分析 - 列出可能的理解 + 推荐理解
3. 等待确认 - 发回给用户审核


## 三、CTO 开发流程（最常用）

这是默认流程，每次你说"帮我做XX"时自动执行：

### Step 1: 加载上下文
- 读 35_CTO架构冻结.md（取架构约束）
- 读 .codex/agents/CTO_AGENT.md（取路由规则）

### Step 2: 5问检查
1. 需求属于哪个产品模块？
2. 影响哪些已有模块？
3. 是否需要修改数据模型？
4. 是否影响未来 Agent OS？
5. 是否已有方案可复用？

### Step 3: 执行开发
- 方案评审 -> 开发 -> 测试 -> 同步 -> 关闭

### Step 4: 状态回报

### Step 5: 自动回溯（任务完成后自动执行）

每次开发/修复/测试/同步任务完成后，自动执行以下回溯流程：

**Step 5a: 记录经验**
- 这次任务中学到了什么？
- 有没有踩坑？怎么避开的？
- 有没有重复出现的问题模式？

**Step 5b: 更新 Agent**
- 经验是否涉及某个 Agent 的职责范围？
- 如果是 -> 追加到对应 Agent 文件的"经验记录"区
- 经验是否反映了规则缺陷？
- 如果是 -> 同步更新 .codex/rules/ 对应文件

**Step 5c: 写入日志**
- 追加记录到 .codex/agents/CHANGELOG.md
- 格式：日期 | Agent | 事件 | 经验摘要 | 改了什么

**Step 5d: 汇报**
- 在最终回复中附带本次回溯结果

## 五、核心约束（来自 35_CTO架构冻结.md）

必须遵守，无需每次确认：

1. 数据模型先于页面 - 先建表再做UI

5. 预留字段 - tenant_id/region/lang_tag 不可删减
6. API统一格式 - /api/v1/ + JWT + 统一响应
