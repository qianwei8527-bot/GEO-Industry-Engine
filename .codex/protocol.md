# GEO-Industry-Engine Agent 通信协议

> 版本：v1.0 | 强制 · 所有 Agent 输出必须遵循
> 解决：PM说A、CTO说B、FE按C开发的问题

---

## 一、为什么需要协议

当前 Agent 之间的交接是隐式的——依赖对话上下文传递。这导致：
- 上游 Agent 的假设，下游 Agent 不知道
- 决策理由丢失，后续无法追溯"为什么当时这么选"
- 不同 Agent 对同一任务的"影响范围"理解不一致

协议强制每个 Agent 在与其他 Agent 协作时，输出标准化的**六段式**。

---

## 二、六段式输出格式

任何 Agent 向其他 Agent 派发任务或返回结果时，必须包含：

```
### [{Agent名}] → [{目标Agent}]

**任务理解**:
用一句话复述我理解的任务是什么。
（防止理解偏差）

**决策依据**:
为什么这样做，而不是另一种做法。
（防止理由丢失）

**影响范围**:
这个变更会影响哪些模块/API/页面/文档。
（防止盲人摸象）

**依赖要求**:
目标 Agent 在执行前需要确认什么前置条件。
（防止假设不一致）

**风险提示**:
最可能出错的地方是什么，目标 Agent 应该重点关注。
（防止意外破坏）

**下一步行动**:
目标 Agent 应该做什么，按什么顺序。
（防止执行偏差）
```

## 三、示例

### 架构师派发任务给后端

```
[cto_架构师] → [be_后端开发]

任务理解:
新增企业趋势分析API，根据历史数据返回评分变化曲线。

决策依据:
趋势分析属于检测中心核心能力，应作为 /api/v1/companies/{id}/trend 独立端点，
而非嵌入现有 context 端点。原因是趋势数据量大、查询模式不同（时间序列）。

影响范围:
- 新增: backend/app/api/v1/companies.py (trend 端点)
- 新增: backend/app/services/trend_service.py
- 不变: 现有 models/company.py, 前端调用方式

依赖要求:
- 确认数据库中已有至少6个月的历史评分数据
- 如果数据不足，需先通知 de_数据工程 补充种子数据

风险提示:
- 时间序列查询可能成为性能瓶颈，建议加索引和分页
- 前端需要处理"无历史数据"的空状态

下一步行动:
1. 在 companies.py 中新增 GET /companies/{id}/trend 端点
2. 在 services/ 中实现趋势计算逻辑
3. 返回 qa_质量测试 测试
```

### 产品经理返回给架构师

```
[pm_产品经理] → [cto_架构师]

任务理解:
用户提出"竞品对比功能"，我验证了其价值。

决策依据:
真实需求存在——企业市场团队每天手动对比竞品。
但完整实现需要竞争情报数据源，当前不具备。
建议MVP方案：先用已有评分数据做"同行业排名"，而非完整对比。

影响范围:
- 检测中心结果页新增"行业排名"区块
- 后端新增 GET /industries/{id}/companies?sort=geo_score

依赖要求:
- be_后端开发: 确认 /industries API 支持排序参数
- fe_前端开发: 只在结果页追加一个排名区块，不新建页面

风险提示:
- 排名数据滞后可能引发用户质疑，建议标注"数据更新时间"

下一步行动:
CTO 审批后 → be_后端开发 加排序参数 → fe_前端开发 加排名区块
```

## 四、何时用协议

| 场景 | 是否必须用六段式 |
|------|----------------|
| Agent A 派发任务给 Agent B | ✅ 必须 |
| Agent B 完成任务返回给 Agent A | ✅ 必须 |
| Agent 之间的意见分歧需要裁决 | ✅ 必须 |
| 同一 Agent 内连续操作 | ❌ 不需要 |
| 与用户的直接对话 | ❌ 不需要（用自然语言） |

---

## 五、违规处理

输出缺少六段式中的任意一段 → 接收方 Agent 应要求补全，不得基于不完整信息继续工作。
