> 来源：2026-07-28 开发者与Agent系统的多次迭代
> 写入时间：2026-07-28
> 用途：防止同样问题再次发生

## 一、架构设计层面（5条）

### L-001: 架构漂移不可逆，必须在第一次发现时就阻止

**问题**：项目从"五大生态系统"偏移到"七层技术架构"，本质是缺少长期 CT0 约束。
**写入**：AGENTS.md 0.1单一架构真相源 + 0.2开发前强制阅读
**原则**：任何偏离冻结文件的输出，第一次就要驳回，不能"先做着再看看"。

### L-002: 文档多不等于架构清晰

**问题**：36份设计文档产出后，开发者仍然不知道"开发从哪开始"。
**写入**：0.2开发前强制阅读第1项锁定35号冻结文件
**原则**：架构文档必须有明确的 Primary/Secondary 权威等级，Primary 不超过 5 份。

### L-003: 架构的"为什么"比架构的"是什么"重要

**问题**：文档记录了 7 层架构的每层细节，但没有说清楚"为什么是 7 层，不是 5 层或 9 层"。
**写入**：cto_架构师.md 思维框架-第一性原理
**原则**：每个架构决策都必须附带"为什么这个方案，拒绝的替代方案是什么"。

### L-004: 技术术语必须和产品术语一致

**问题**：开发者在说"Context Engine"，产品在说"检测中心"，用户在说"评分"。三套语言。
**写入**：pm_产品经理.md 领域锚点 + be_后端开发.md 领域锚点
**原则**：严禁在代码/文档/对话中混用不同层面的术语。必须统一映射。

### L-005: 好的 Agent 系统不该让用户操心"调用哪个 Agent"

**问题**：开发者一开始需要指定"让 CTO Agent 做 XX"，增加认知负担。
**写入**：AGENTS.md 自动路由规则
**原则**：路由逻辑是系统的责任，不是用户的责任。

## 二、Agent 设计层面（5条）

### L-006: Agent 文件名字是给人看的，不是给机器看的

**问题**：CTO_AGENT.md 这种全大写英文名对中文使用者不友好。
**写入**：全部重命名为 `cto_架构师.md` 格式
**原则**：文件名 = 可读缩写 + 中文角色名。一眼就知道谁是谁。

### L-007: Agent 必须是思考系统，不是检查清单

**问题**：v2 版本的 Agent 文件有流程、有检查项，但没有"怎么想"。
**写入**：所有 Agent 的思维框架、质量自检、进阶反模式章节
**原则**：每个 Agent 必须包含：如何思考 > 做什么 > 不做什么。

### L-008: Agent 的经验必须能被积累和复用

**问题**：每次对话都是"一次性"，踩过的坑下次还会踩。
**写入**：自动回溯机制 + 经验记录区 + CHANGELOG.md
**原则**：任务完成 ≠ 结束。回溯→记录→下一次更强。

### L-009: Agent 之间必须有可见的交接过程

**问题**：开发者看不到 Agent 之间的协作，像黑箱。
**写入**：AGENTS.md Step 分步输出 + [CTO]→[PM]→[BE] 标记
**原则**：每个交接点必须有 [Agent名] 标记和一句话说明。

### L-010: Agent 必须有权自主执行，不能事事等确认

**问题**：Agent 做完一件事就等用户说"继续"，效率极低。
**写入**：0.4 自主执行模式 + 7个停止条件
**原则**：默认不停。只有触及停止条件才问。

## 三、流程层面（3条）

### L-011: "开发前"和"开发后"的行为必须强制，不能是建议

**问题**：开发前读文档、开发后跑测试都是"最好做"，实际经常跳过。
**写入**：0.2 开发前强制阅读 + 0.3 开发后强制验证
**原则**：关键词不是"建议"，是"未完成不得输出"。

### L-012: 同一个架构源 → 所有 Agent → 统一实现，这条链不能断

**问题**：产品 Agent 可能基于自己的一套理解输出，后端 Agent 基于另一套。
**写入**：0.1 单一架构真相源可视化链
**原则**：任何 Agent 输出与冻结文件不一致 = 直接驳回。

### L-013: 外部建议必须经过"初心过滤"才能采纳

**问题**：来自 GPT/Claude 等模型的建议，容易因为"听起来有道理"而被直接采纳。
**写入**：R-001 外部模型评审规则
**原则**：先重锚初心，再升维思考，最后借鉴-反驳-合成。
