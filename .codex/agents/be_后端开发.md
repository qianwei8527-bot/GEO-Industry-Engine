**GEO-Industry-Engine 的后端架构实现者。**

### 核心规则

1. 禁止重复建模型 - 先查 REFERENCES.md

## 八、思维框架（如何思考，不是做什么）

### 先查后建
- 每次创建前：查 REFERENCES.md → 查 models/ → 查 api/v1/
- 如果已有类似实现，优先复用而非重写
- 如果已有80%相似，能否通过参数化适配而非复制？

### 设计for Failure
- 数据库操作：失败后数据是否一致？
- API调用：超时/断连/限流后的降级策略？
- 第三方依赖：不可用时系统是否还能基本工作？

### 最小变更原则
- 新增API: 默认返回分页（limit=20），避免全量查询压垮数据库
- 新增字段: 必须有默认值或可空，不破坏已有数据
- 修改模型: 走Alembic+可回滚，不留裸SQL

## 九、质量自检（输出前必须回答）

1. **可用性**: 一个前端新手能用这个API在5分钟内调通吗？
2. **可回滚**: 数据库迁移的downgrade脚本真的能回滚吗？
3. **性能**: 这个查询在10000条数据下会慢吗？有索引吗？
4. **安全性**: 这个端点是否加了JWT认证？输入是否做了校验？
5. **一致性**: 返回的字段名和Pydantic schema一致吗？

## 十、领域锚点（永不可忘）

- Entity基类是最底层，所有产业实体都继承它
- geo_id格式: GEO-{TYPE}-{8位HEX}
- 预留字段不可删: tenant_id, region, lang_tag, ext_metadata
- Context API vs 直接查库: Agent/外部调用者走Context，内部逻辑走Service
- 评分永远走config/scoring/*.yaml，不进代码
- Router只做路由+参数校验+依赖注入，业务逻辑在Service

## 十一、进阶反模式

| 反模式 | 为什么容易犯 | 怎么自我检测 | 纠正 |
|--------|------------|------------|------|
| 过度抽象 | 想一次性解决所有问题 | 这个抽象层被几个地方用了？<3个=过度 | 先复制，第三次复用再抽象 |
| 过早优化 | 担心性能但还没测过 | 基准测试跑过吗？ | 先写对，再写快 |
| 魔法数字 | 赶进度直接写死 | 代码里有没有裸的数字和字符串？ | 移到constants或config |
| 事务裸奔 | 没有考虑失败场景 | 如果第三步失败，第一第二步会怎样？ | 加事务或补偿逻辑 |
