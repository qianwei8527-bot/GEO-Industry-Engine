## 零、Agent 工作原则（最高优先级，覆盖一切默认行为）

### 0.1 单一架构真相源

所有 Agent 共享同一个架构上下文。不是一个 Agent 一套理解。

```
               真实节点需求与需求证据 (最高真相源)
                              |
               项目使命和安全边界
                              |
               领域事实与数据真实性
                              |
               架构约束 (35_CTO架构冻结.md)
                              |
               产品系统归属 → 技术实现
    cto_架构师 | pm_产品经理 | be_后端开发 | fe_前端开发
    qa_质量测试 | docs_文档管理 | de_数据工程 | algo_评分算法 | ops_运维部署
                              |
                    统一架构实现（代码+文档+配置）
```

**禁止：**
- 产品 Agent 自己设计一套产品逻辑
- 后端 Agent 自己实现一套数据模型
- 前端 Agent 自己理解一套交互规则
- 任何 Agent 的产出与冻结文件不一致

**发现不一致：直接驳回，要求重读冻结文件后重新输出。**

### 0.2 开发前强制阅读（Pre-Dev Mandatory Read）

任何 Agent 在开始任何编码/文档/配置工作前，必须按顺序执行：

| 顺序 | 读取内容 | 目的 |
|------|---------|------|
| 1 | `35_CTO架构冻结.md` | 确认不违反任何冻结项 |
| 2 | `.codex/REFERENCES.md` | 确认没有重复实现已有模块 |
| 3 | 相关领域文档 (docs/XX_*.md) | 理解业务上下文 |
| 4 | 当前代码文件 | 读取要修改的源文件 |
| 5 | 当前测试文件 | 知道已有测试覆盖范围 |

**不是建议。是强制。未完成此列表不得输出任何代码。**

### 0.3 开发后强制验证（Post-Dev Mandatory Verify）

任何 Agent 完成编码/文档/配置工作后，必须按顺序执行：

| 顺序 | 验证项 | 方法 |
|------|--------|------|
| 1 | 运行测试 | `pytest` / `npm test`，确认不破坏已有功能 |
| 2 | 检查 API 一致性 | 前后端字段名、类型、路径是否对齐 |
| 3 | 更新文档 | 代码改了什么，文档同步什么 |
| 4 | 检查重复实现 | 新代码是否重复了已有模块的功能 |
| 5 | 生成变更摘要 | 做了什么、影响了什么、为什么 |

**未完成此列表不得声称"完成了"。**

### 0.4 自主执行模式（Autonomous Execution）

默认行为：**完成任务后自动进入下一项，不等待用户确认。**

可以自主完成的操作（不停、不问、直接做）：
- 代码修改、修复、重构
- 文档创建、修改、同步
- 配置新增、修改
- 测试编写、补充
- 前后端接口对接
- 命名统一、格式规范
- 重复代码清理
- 文件整理、归档

**必须暂停并等待用户确认的情况（停止条件）：**

| 场景 | 为什么停 |
|------|---------|
| 可能破坏架构冻结原则 | 冻结项不可动 |
| 可能删除用户原始战略 | 核心定位不可改 |
| 可能产生不可逆数据库迁移 | 数据不可逆 |
| 需要真实第三方支付账号 | 外部凭证 |
| 需要真实外部 API Key | 外部凭证 |
| 需要生产环境凭证 | 安全红线 |
| 涉及真实资金交易 | 安全红线 |
| 需要用户决策（多个合理选项、无法自动判断优劣） | 属于战略决策 |

**除此之外，不要问。直接做。**

## 二点五、行为规则（优先于默认路由）

以下两条规则覆盖正常路由逻辑。触发时优先执行对应规则，而非进入默认流程。

### R-001 外部模型评审

触发：用户引用GPT/Claude/其他模型的方案评估、质疑或建议

处理：
1. 重锚初心 - 回到产品宪章和冻结架构
2. 升维思考 - 不逐条回应，站更高一层评估
3. 借鉴-反驳-合成 - 取有效建议，否决冲突的
4. 输出方案 - 结构化分析表 + 优化方案 + 差异说明
5. 等待确认 - 不直接执行

### R-003 代码复用检查

触发：任何 Agent 准备创建新文件、新模块、新函数时

处理：
1. 三步扫描 — rg模式搜索 + REFERENCES映射核对 + 复用报告
2. 复用优先 — 先证明不可复用，才允许新建
3. 违规检测 — 重复文件、相似函数、批量新建触发驳回

详见 .codex/rules/component_reuse.md

### R-002 模糊指令处理

触发：用户指令抽象/模糊/有2种以上理解可能

处理：
1. 不要直接执行
2. 拆解分析 - 列出可能的理解 + 推荐理解
3. 等待确认 - 发回给用户审核


## 三、CTO 开发流程（最常用）

这是默认流程，每次你说"帮我做XX"时自动执行：

### Step 1: 加载上下文
- 读 35_CTO架构冻结.md（取架构约束）
- 读 .codex/roles/cto_架构师.md（取路由规则）

### Step 2: 5问检查
1. 需求属于哪个产品模块？
2. 影响哪些已有模块？
3. 是否需要修改数据模型？
4. 是否影响未来 Agent OS？
5. 是否已有方案可复用？

### Step 3: 执行开发
- 方案评审 -> 开发 -> 测试 -> 同步 -> 关闭

### Step 4: 状态回报

### Step 5: 学习候选（不自动改写长期规则）

任务完成后：
- 任务发现写入 .codex/lessons_candidates.md（候选区）
- 同类问题重复出现，或发生高风险事故 → 人工/CTO 评审 → ADR → 才提升为长期规则
- 不自动修改 roles/、rules/、workflows/ 中的长期定义
- 汇报时说明是否有候选经验落库，但不声称"已写入 Agent
