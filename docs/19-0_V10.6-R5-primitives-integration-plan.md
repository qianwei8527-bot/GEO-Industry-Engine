# 四原语契约与双项目协作最终方案

> 版本：V1.0
> 定位：明确 GEO-Industry-Engine 与 geo-diagnostic 的边界、契约和同步方式
> 原则：契约单向冻结，业务真相单向回流，执行能力外接，不复制第二套权限体系

## 1. 分工边界

### geo-diagnostic 负责

- 四原语契约的唯一维护方：AgentConfig、SkillPackage、WorkflowDefinition、McpConnection。
- 工具生产：从模板创建、组合、校验、版本、Skill 包打包。
- 工具使用与自动化：Agent 编排、Workflow 执行、Skill 运行、MCP 工具调用。
- AI/搜索/社媒/诊断等外部能力接入。
- Token、成本、耗时、运行记录等运行侧指标。

### GEO-Industry-Engine 负责

- 身份、Realm、Project、Membership、授权与审计。
- 客户资料、项目计划、定位结论、Evidence、Outcome、Capability 资产。
- 公共世界、客户协作、运营后台、治理审计台等业务入口。
- 能力包发布、授权、生态共享库和治理。

### 不互相负责

- geo-diagnostic 不持有最终客户权限，不自行判定 `owner/verified/Reputation`。
- GEO-Industry-Engine 不实现四原语运行时，不保存任何 AI Key 或外部凭据。
- 双方不复制对方的数据模型，只通过契约和 API 交换。

## 2. 契约位置与同步

geo-diagnostic 是契约源：

```text
geo-diagnostic/config/primitives/
├── agent-config.schema.json
├── skill-package.schema.json
├── workflow-definition.schema.json
├── mcp-connection.schema.json
├── run-record.schema.json
└── approval-request.schema.json
```

GEO-Industry-Engine 只保存版本化快照：

```text
GEO-Industry-Engine/config/universe/primitives/
└── snapshot.json
```

同步规则：

- 每次契约变更必须提升 `schema_version`，并生成 `content_hash`。
- 平台同步脚本比较快照版本与 hash，不一致时拒绝接入。
- 契约回退必须有 `breaking` 标记；平台以 hash 和版本共同判定兼容性。
- 平台不手工编辑快照，只执行导入。

## 3. 接口协议

### 平台调用 geo-diagnostic

```text
POST /runtime/runs
{
  "request_id": "uuid",
  "realm_id": "uuid",
  "project_id": "uuid | null",
  "actor_id": "uuid",
  "authorization": {
    "scope": ["tool.read", "tool.run"],
    "expires_at": "..."
  },
  "capability_id": "uuid",
  "capability_version": 3,
  "inputs": {},
  "expected_output": {}
}
```

要求：

- `realm_id/project_id/actor_id` 只作为运行上下文，不作为授权依据。
- 平台调用前必须校验 Membership、授权范围、Feature Flag 和风险等级。
- geo-diagnostic 运行前必须回调平台权限接口，或使用平台签发的短时效执行凭证。

### geo-diagnostic 回流平台

```text
POST /api/v1/tool-runs
{
  "request_id": "uuid",
  "capability_id": "uuid",
  "capability_version": 3,
  "run_status": "completed | failed | blocked | cancelled",
  "truth_scope": "observed",
  "provenance": {
    "tool": "geo-diagnostic",
    "workflow_version": 2,
    "skill_version": 1,
    "model": "deepseek",
    "source_hash": "..."
  },
  "outputs": {},
  "evidence_refs": [],
  "cost": {},
  "started_at": "...",
  "ended_at": "..."
}
```

要求：

- 运行结果默认 `observed`，不得冒充 `verified`。
- 平台把结果落为 Evidence/Outcome，并写 AuditLog。
- `outputs` 不包含完整 API Key、客户隐私或内部密钥。

## 4. 数据与权限真相

- 平台是唯一身份和权限真相源：`NodeMembership`、`ControlGrant`、`RealmDataAuthorization`。
- geo-diagnostic 只识别平台下发的授权上下文，不保存用户密码或 Realm 权限。
- API Key、Secret、MCP 凭据只存于 geo-diagnostic 后端，不进入平台前端和数据库。
- 所有关键运行写平台 AuditLog 或 Event Backbone。
- 公开 URL、网页抓取、SSRF、限流由调用方或平台统一防护。

## 5. 双项目开发节奏

### P0 契约冻结

- geo-diagnostic 完成 6 个 JSON Schema 并冻结 V1。
- 平台生成 `snapshot.json` 和导入校验脚本。
- 两边跑同一套契约校验用例。

### P1 工具接入

- 平台通过 Adapter 调用 geo-diagnostic 的 `/runtime/runs`。
- 运行结果回流为 Evidence。
- 先做 Fixture/Mock 全链路，再做真实外部能力。

### P2 自动化

- geo-diagnostic 支持定时、事件触发、Workflow 编排和人工确认点。
- 平台提供审批中心，把外部动作审核回调到 geo-diagnostic。

### P3 生态共享库

- 平台把稳定能力发布为 Capability 包，关联 geo-diagnostic 工具。
- 域主确认后进入共享库，授权范围、版本和 provenance 全部落盘。

### P4 治理与观测

- 统一运行 trace、成本、失败率和审计视图。
- 平台治理台查看 geo-diagnostic 运行记录，不直接读它的数据库。

## 6. 同步与验收

每次同步必须完成：

- `schema_version` 和 `content_hash` 校验通过。
- 平台到 geo-diagnostic 的鉴权与运行请求通过。
- geo-diagnostic 到平台的运行结果回流通过。
- 无权限、跨 Realm、无效版本、过期授权四类负向测试通过。
- 两端测试和构建通过。

停止条件：

- geo-diagnostic 开始保存 Realm 权限真相。
- 平台开始实现第二套四原语运行时。
- AI Key 进入平台前端、数据库或 Git。
- 契约双向分叉，无法用版本和 hash 校验。
- 新增平行权限、任务或资产体系。

## 7. 最终形态

```text
GEO-Industry-Engine
  ├── 身份 / Realm / 权限 / 审计
  ├── 客户 / 项目 / Evidence / Capability
  └── 能力包发布与生态共享库
              │ 契约 + 授权
              ▼
geo-diagnostic
  ├── 四原语契约
  ├── 工具生产与自动化运行
  └── AI / MCP / 搜索 / 社媒外部能力
              │ 运行结果 + provenance
              ▼
GEO-Industry-Engine
  └── Evidence / Outcome / 资产 / 审计
```
