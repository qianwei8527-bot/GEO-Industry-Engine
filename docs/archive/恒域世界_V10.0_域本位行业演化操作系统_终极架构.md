# 总论 名称、定位与总架构判定

## 0.1 “节点”“态”和“域”的最终裁决

“节点（Node）”只描述关系网中的位置；“态（State）”只描述某一时刻的表现。二者都不能单独承担身份、认领、控制、权利、责任、历史和生命周期。V10.0 正式采用“域”为根名称：

> **域（Realm）是具有持续身份、边界、控制关系、可安装能力、事件历史和生命周期，并能与其他域组合、交换、治理和演化的数字存在。**

域不是地理区域，也不是普通数据库记录。它是恒域世界中所有可独立识别与持续演化对象的统一封装协议。现实中的人、企业、品牌、产品、知识、Skill、工具、数据资产、项目、组织、规则和行业，都可以在有用时被域化；没有独立权利、事件或生命周期的内容，不必强行实例化。

| **术语（English）**      | **回答的问题**         | **正式职责**                                     |
|--------------------------|------------------------|--------------------------------------------------|
| 域（Realm）              | 它是谁                 | 身份、边界、控制、责任、历史和谱系               |
| 域构形（Realm Form）     | 它怎样组成             | 原生、模组、封装、群落、镜像五种组合形式         |
| 域态（Realm State）      | 它现在怎样             | 生命周期、事实、权限、资源、能力、风险等状态向量 |
| 域位（Realm Position）   | 它在关系网何处         | 指定世界、时间和观察者下的网络投影               |
| 域关系（Realm Relation） | 它与谁怎样作用         | 所属、提供、需求、交易、影响、引用、治理         |
| 域主（Realm Owner）      | 谁在现实中主张或控制它 | 认领、授权、参与、建设、责任与收益主体           |

因此不是删除“节点”，而是把它放回关系投影层：**域是主体，构形是身体，域态是当下表达，域位是关系投影，事件是生命记录，域主是现实权利与责任入口。**现有代码中的 `Node`、`Entity`、`node_id`、`entity_id` 在兼容期保留，通过别名与适配器迁移，不进行破坏性重命名。

## 0.2 五种基础域构形

所有新形态都必须带“域”字，以便识别其共同根协议：

1.  **原生域（Primitive Realm）：** 最小可独立寻址单元，如一个身份主张、一项能力定义或一条可治理规则；
2.  **模组域（Modular Realm）：** 可安装、许可、复用和替换的能力单元，如 Skill、工具、模型、工作流；
3.  **封装域（Capsule Realm）：** 具有独立身份、控制权、内部模块和生命周期的完整主体，如个人、企业、品牌、产品；
4.  **群落域（Collective Realm）：** 多个域以成员、协议、资源和共同目标形成的组织、联盟、平台或行业；
5.  **镜像域（Mirror Realm）：** 对现实对象或系统进行持续映射的数字候选、影子或孪生体。

构形不是价值等级。一个域可以升级、降级、拆分、合并、释放模组或派生后代，但必须保留来源、许可、贡献和责任谱系。

## 0.3 恒域世界究竟打造了什么

> **恒域世界是一套可复制、可配置、可演化的行业运行壳。它以域为基本单位，连接现实域主、AI、工具、需求、能力、项目、交易和结果，把域主的真实协作过程沉淀为可授权、可验证、可追溯、可组合、可资产化的行业信用与数据。**

它不是一个先验行业数据库，不是替行业发明规则的管理机构，也不是把 GPT、豆包或 Codex 包装成聊天入口。它建立的是行业级运行环境：

- 让域主带着自己的身份、数据、能力、品牌和需求进入；
- 让内置或外部 AI、Skill、工具在明确权限和上下文中工作；
- 让连接升级为项目、合同、交付、验证、交易和结算；
- 让每次真实活动形成事件、证据、结果、贡献、信誉、荣誉与资产；
- 让行业版图从域主真实协作中逐步显现、修正和完善；
- 让验证过的行业壳复制并差异化演化为新的行业世界。

恒域世界最终沉淀的不是“AI 生成内容的数量”，而是：**真实域主 + 真实需求 + 真实协作 + 真实项目 + 真实结果 + 长期信誉 + 授权行业资产所共同形成的行业记忆。**

## 0.5 域主是谁，为什么使用恒域世界

域主不是平台里的普通“账号”。域主是对某个域提出认领、控制、经营、参与或建设主张的现实个人、企业、机构、品牌团队或被授权代理。一个企业域可以由多人共同操作，一个现实人也可以在不同世界以不同角色参与多个域。

域主使用恒域世界，必须立刻获得可感知的现实收益：

1.  **带走自己的数字身份和上下文：** 数据不再散落在多个 AI 对话、表格和供应商系统；
2.  **完成工作：** 使用内置或外部 AI、Skill、工具诊断问题、生产内容、执行任务和交付项目；
3.  **找到可信合作：** 基于需求、能力、证据和履约记录形成连接候选，而非黑箱广告排名；
4.  **建立品牌：** 把品牌事实、内容、产品、引用、项目和结果组合成可验证的品牌域；
5.  **积累而非清零：** 每次协作、交易、学习和结果沉淀为成长、信誉、荣誉、知识与数据资产；
6.  **获得行业视野：** 看见自身在指定行业世界中的能力缺口、需求缺口、连接缺口和未来选择；
7.  **控制数据和退出：** 能查看、授权、撤回、纠正、申诉、导出和停止使用自己的数据。

域主留在恒域世界的理由不能是“平台锁住了数据”，而应是：**历史越真实、协作越多、结果越可验证，域的上下文、信任、效率和品牌资产越难被一次性工具替代。**

## 0.6 为什么域主会信任恒域世界

第一信任入口不是平台声称“AI 更懂你”，而是域主先使用自己的数据，并能看见数据如何被使用。正式信任阶梯为：

    域主声明
      → 系统观察
      → 对手方确认
      → 证据支持
      → 第三方验证
      → 项目结果验证
      → 多次真实履约
      → 分场景信誉

任何一层都不能冒充下一层。`synthetic` 只用于模拟；`observed` 只作为线索；只有满足结构化主张、证据有效性、主体一致性和生产边界的 `verified` 事实，才可影响正式信用、生产投影和关键决策。

域主拥有以下不可被产品条款模糊掉的权利：可见权、知情权、授权权、撤回权、导出权、纠错权、申诉权、来源追踪权、评分解释权、退出权。删除或撤回不等于删除依法必须保留的账务和审计记录，但系统必须明确剩余范围与依据。

## 0.7 平台中立与利益冲突边界

深圳市恒域世界科技有限公司可以同时是平台经营者、恒域世界-GEO 发起方、GEO 域主、品牌/服务提供方和工具创造者，但这些身份必须在数据与决策上分开。平台不得：

- 因自身商业利益暗中提高自营域、工具、服务或品牌的曝光与评分；
- 自己提交主张、自己验证主张、再自己授予信誉；
- 修改竞争域的事实、规则或行业概念；
- 使用域主未授权的私有数据训练模型、服务竞争者或形成不公平优势；
- 把平台运营规则伪装成行业共识；
- 把连接、接受、支付或游戏奖励直接写成信誉。

每个重要动作必须记录：`actor_domain_id`、`current_role`、`world_id`、`authority_scope`、`decision_scope`、`conflict_of_interest`、`evidence_refs` 与时间版本。

## 0.8 行业、规则和工具从哪里来

恒域世界只能创造通用协议、技术能力、治理程序、安全边界和法律合规机制，不能替行业创造事实、业务标准、价值判断或工具需求。

- **行业概念**来自真实域主对角色、场景、目标、痛点、能力、产品、证据与结果的共同使用和验证；
- **行业规则**由有权参与的域主提出、讨论、试行、验证、批准、版本化和申诉；
- **行业工具**来自真实任务中的重复痛点，由域主提出需求，可由平台、域主或外部开发者实现；
- **行业数据**主要来自域主在恒域世界内完成的项目、交付、验证、交易和结果，也可在授权和来源明确时接入外部数据；
- **行业世界**不是平台预先填满的模板，而是这些事实在长期协作中形成的群落域。

平台规则分为两类：公司在法律责任下维护的技术、安全、隐私、账务和反滥用不变量；域主共同形成的行业业务规则。前者保护系统和参与者，后者不得由平台单方冒充行业权威。

## 0.9 AI、Skill、工具和外部平台的正式位置

GPT、豆包、Codex、行业模型、搜索、CRM、支付、设计软件和自建工具都属于可替换的工具或模型提供方。它们可以通过接口、MCP、API、Connector 或 Skill Contract 接入，也可以由恒域世界内部孵化和发布。

恒域世界的不可替代部分不是某个模型，而是行业运行时：身份和授权、长期上下文、规则版本、事实与证据、任务编排、多方协作、项目责任、结果验证、交易结算、贡献归因、信誉和资产沉淀。工具负责“完成动作”，恒域世界负责回答“为谁、在什么行业和规则下、使用什么数据、承担什么责任、产生什么结果、如何验证并归属谁”。

只有同时满足下列一项以上的能力，才进入平台核心：需要真实身份或授权；需要多方参与；需要长期历史或分场景信誉；涉及权利、责任、价值和结算；需要跨工具编排；产生可验证结果或可复用资产；真实活动会完善行业版图。其余功能优先交给可替换 Skill 或外部工具。

# 第一篇 宪章与统一域语法

## 执行摘要

### V10.0 最高结论

恒域世界的根结构是“一个通用行业壳 + 多个由域主共同装载的行业世界”。最高法则不是连接中心论，也不是平台中心论，而是：

> **万物皆可域化；每个域都是自身可观测世界的坐标原点。域主以真实需求进入，借助人、AI 与工具完成真实项目；项目产生事实、证据、结果、交易、贡献、信誉和资产；这些可追溯积累推动域成长，并共同演化行业世界。**

一个企业通常是封装域，可安装身份、品牌、能力、产品、需求、信任、知识、资产和工具模组；企业员工或代理人根据授权操作。一个 Skill 通常是模组域；形成独立品牌、客户、责任和生命周期后可以升级为封装域。一个行业是长期稳定形成的群落域，不是平台创建的一张分类表。

### 八重闭环

1.  **域生命闭环：** 环境 → 感知 → 变量 → 向性 → 行动 → 事件 → 状态 → 新环境；
2.  **域成长闭环：** 学习/能力 → 产品 → 项目 → 结果 → 信誉/资产 → 新机会 → 再成长；
3.  **域主价值闭环：** 自有数据 → 诊断 → 工具执行 → 可验证收益 → 数据继续沉淀；
4.  **品牌增长闭环：** 品牌事实 → AI 可见度 → 内容/证据缺口 → 生产发布 → 引用/需求 → 项目结果 → 品牌信任；
5.  **行业形成闭环：** 域主 → 需求/能力 → 协作/交易 → 事实/结果 → 标准候选 → 共建规则 → 行业世界；
6.  **能力生产闭环：** 重复任务 → Skill 候选 → 实现/测试 → 发布/安装 → 结果评估 → 升级/回滚；
7.  **世界经济闭环：** 探索/任务 → 组队 → 交付 → 验证 → 结算/分配 → 资产/荣誉 → 新探索；
8.  **治理进化闭环：** 观察 → 规则/模型候选 → 仿真/影子验证 → 域主审批 → 新版本 → 校准/申诉/回滚。

自我成长不等于系统可以自动制造事实、规则或信誉。所有生产变化都必须版本化、可解释、可验证、可回滚，并经过对应权利主体授权。以下技术摘要保留 V9 已冻结的域结构与动力协议，同时受本节的域主主权、现实项目和行业共建原则约束。

### 最终判断

恒域世界引擎 的底层法则正式升级为：

> 万物皆可成为域；每个域都是自身可观测世界的坐标原点。域通过模块形成身体，通过环境获得处境，通过变量表达变化，通过向性选择方向，通过影响彼此塑造，通过事件积累生命，通过价值交换成长，通过释放与组合繁衍世界，并由来源链保持可信。

“万物皆域”不等于所有东西完全同质，也不等于数据库必须为每个字节建立永久记录。它表示所有需要被独立识别、引用、组合、控制、交易、验证、复制或追溯的存在，都使用同一套域协议。

V10.0 使用两组正交协议描述域，并增加三条跨域运行协议。

结构协议回答“它由什么构成”：

1.  Entity Kernel：稳定身份与治理入口；

2.  Entity Genome：版本化结构和规则；

3.  Installed Modules：安装了哪些能力模块；

4.  Entity Form：当前组合形态；

5.  Entity Facet：在当前语境中的用途和角色。

动力协议回答“它怎样活着并改变”：

1.  State Variables：当前值和生命周期；

2.  Dimension Space：变化发生在哪些坐标轴；

3.  Entity Horizon：它能看见和作用到哪里；

4.  Environment Field：外部机会、资源、约束和扰动；

5.  Orientation Vector：趋近、回避、吸收、释放或连接的倾向；

6.  Influence Field：域间有方向、有维度、有时效的影响；

7.  Evolution Trajectory：过去真实发生的多维移动；

8.  Action Cone：现在可采取的行动集合；

9.  Possible Worlds：带假设的未来分支。

跨域运行协议回答“域怎样共同生活、生产和交换”：

1.  Rule Domain Protocol：域进入不同世界、组织、空间和项目时，如何继承并遵守有效规则；

2.  Capability Protocol：Skill、Tool、Model、Workflow 和 Agent 如何被注册、组合、执行、评估和进化；

3.  Economic Protocol：产品、数据、能力与贡献如何计量、授权、交易、结算、分账和审计。

因此，一个企业可以是 CapsuleEntity，同时安装 Identity、Capability、Offering、Demand、Trust、Asset 等模块；同一个企业在客户、服务商、监管者和合作伙伴的局部世界中拥有不同距离、影响和角色。一个产品可以先作为 ModuleEntity 被封装，形成独立客户、版本和责任边界后升级为 CapsuleEntity。一次交易可以从 Event 开始，在出现协议、争议、支付、交付与结果生命周期时升级为 Engagement Entity。

### 域本位世界的关键修正

“每个域都是世界中心”不是说每个域拥有最高权力或价值，而是说任何 World Projection 都必须声明观察原点。一个域只能看到权限、关系、语义和时间允许它看到的世界。

Universal Fact 不随观察者改变；Entity World 则是以指定域、指定 World Version、指定 as_of 和权限为参数形成的局部投影。大量局部世界在共同需求、交易、语言、标准和信任上长期交叠，才会形成 CollectiveEntity、IndustryEntity 和更大的 World。

### 微内核模块化的关键修正

“万物皆域”如果没有模块契约，会变成无限表、无限类型和无限例外。V10.0 采用稳定 Entity Kernel 加可安装 Module：内核只保存身份、控制、版本、事件、政策与谱系，能力、产品、需求、Skill、工具、数据、知识、信任、环境、影响和未来都由版本化模块提供。

同一 Entity Genome 可以实例化无数具有独立 Entity ID 的封装域；已有封装域也可以释放、许可、复制或派生内部模块生成新域。两者都不能复制他人的事实历史，必须保存来源、贡献、许可和父谱系。

### GPT 类比的正确结论

GPT 与本架构在“统一基础单元、层层组合、根据上下文动态激活关系”方面相似，但底层并不相同。

GPT 把输入切分为 Token，并通过 Transformer 的参数与 Attention 计算上下文关系，目标是根据已有序列预测后续 Token。GPT 中的概念通常是分布式表示，并不是拥有永久 Entity ID、所有权、事件账本和来源谱系的显式域。OpenAI 对 GPT-4 的公开技术报告也只确认其为预测下一 Token 的 Transformer-style 模型，并未公开完整内部架构。

恒域世界引擎 则是持久现实系统：域必须拥有身份、控制权、版本、事件、事实来源、权限和责任。GPT 适合成为域世界的感知、解释、推理与行动助手，但不能代替域事实层。

### 六重闭环

V10.0 同时运行六条闭环：

1.  域动力闭环：环境 → 感知 → 变量 → 向性 → 行动 → 事件 → 状态 → 新环境；

2.  域成长闭环：身份 → 能力 → 产品 → 需求 → 连接 → Engagement → Outcome → 信任/资产 → 新成长；

3.  世界涌现闭环：局部世界交叠 → 稳定关系 → 共同语言和标准 → Collective/Industry → 新域和新环境；

4.  模型进化闭环：观察 → 模式候选 → 仿真/影子验证 → 人工审批 → 配置新版本 → 校准与回滚。

5.  能力生产闭环：重复任务 → Skill Candidate → 工具/模型实现 → 测试/仿真 → 发布/安装 → Outcome 评估 → 升级/回滚；

6.  世界经济闭环：探索/需求 → 任务/组队 → Skill 执行 → 产品/交付 → Evidence/Outcome → 账本结算/分配 → 资产与成长。

自我进化不等于系统可以自动修改事实或信誉。所有生产规则变化都必须版本化、可解释、可验证、可回滚。

## 第一章 架构使命与产品初心

### 1.1 恒域世界是什么

恒域世界不是普通知识图谱、企业黄页、SEO 工具、社区、交易商城、单一行业数据库、AI 聊天入口或虚拟游戏。它是：

> **供行业各方使用 AI 与工具、发现和连接供需、协同交付项目、完成交易、建立品牌，并把真实过程沉淀为成长、信用、荣誉、知识、数据和资产的行业运行基础设施。**

它使每个域主能够回答：我是谁；我控制或参与哪些域；我带来了什么自有数据；过去完成过什么；现在拥有什么能力、产品、关系和信誉；谁需要我、我需要谁；能调用哪些 AI、Skill 和工具；正在承担哪些项目、权利和义务；结果如何验证；贡献和收益如何分配；我的品牌如何被人和 AI 看见并信任；未来有哪些带依据的可能路径。

每一个问题都从当前域出发，而不是从平台管理员或固定行业分类出发。域主页（Realm Home；现有代码 `Entity Home`）是域自己的操作系统，行业世界是帮助域理解环境、协作与规则的共享镜头。

### 1.2 商业、品牌与生态必须同步成长

平台不能要求域主先无偿“贡献数据”再等待未来价值。第一次进入就应完成一个现实任务：导入品牌数据、诊断 AI 可见度、解决一个内容或证据缺口、找到一个合作方、运行一个 Skill、管理一个项目或验证一个结果。数据是有价值活动的数字副产品，不是平台先收集后寻找用途的原料。

品牌是恒域世界的主要支柱之一。品牌域把身份、内容、产品、案例、外部引用、项目结果、客户确认和长期信誉组合起来；它既服务企业自身增长，也为 AI 和行业参与者提供可验证、可授权的可信上下文。

### 1.3 世界优先，AI 加速（World First, AI Accelerated）

恒域世界保存事实、身份、授权、关系、事件、权利、责任和来源；AI 负责感知、抽取、解释、匹配、规划、执行和复盘。系统不依赖某一个模型存在，AI 也不能越过真实性边界制造 `verified` 事实、行业规则或正式信誉。

### 1.4 一个封装域，多个世界（One Capsule, Many Worlds）

平台优先把一个真实个人、企业或品牌封装域做完整，而不是先制造大量空域。该域通过安装模组、发生事件、学习、生产、协作、交易、验证结果和释放内部域，逐步产生能力域、产品域、品牌域、案例域、数据域、知识域、关系域和未来域。

同一域可以同时进入恒域世界-GEO、恒域世界-科技特长生或其他行业世界，但每个世界的角色、规则、权限和信誉语境分别计算。大量真实封装域反复协作后，行业地图和行业规则才从事实中涌现。

### 1.5 域主采用与留存判定

任何计划开发的功能必须先回答：它能否让域主更快完成真实任务；能否增加可验证结果；能否减少跨工具切换和重复输入；能否沉淀域主可控制的长期资产；能否提高后续协作效率；能否通过真实活动完善行业世界。若答案都是否定，该功能不得因为“看起来像未来”而进入近期路线。

## 第二章 四十条第一性原理

### 2.1 万物域法则

任何需要被独立识别、引用、组合、控制、交换、验证或追溯的存在，都可以域化。

### 2.2 域本位法则

每个域都是自身可观测世界的坐标原点。中心是观察视角，不是权力、真理或价值特权；任何投影都必须声明 observer_entity_id。

### 2.3 微内核模块法则

所有域共享稳定 Entity Kernel，业务能力通过版本化 Module 安装。模块可以组合、替换、释放和迁移，但不得修改内核不变量。

### 2.4 有用实例化法则

万物皆可域化，不等于万物都必须实例化。只有产生独立身份、关系、事件、权利、价值或审计需要时，才建立正式域。

### 2.5 组合封装法则

复杂域由其他域组合形成。封装隐藏复杂度，但不得消灭内部域的来源、贡献、许可和历史。

### 2.6 事件生命法则

域不是靠字段数量变得鲜活，而是靠真实事件形成经历。当前状态必须由事件和有效事实推导。

### 2.7 时间连续法则

域必须同时表达过去、现在与未来：过去是不可静默改写的事件，当前是可重建状态，未来是带假设与概率的意图、计划、场景或预测。

### 2.8 环境相对法则

环境不是全局常量。域环境由观察原点、时间、权限、世界版本、关系距离和影响渠道共同决定，必须作为可重建投影而非静态字段。

### 2.9 变量显式法则

任何状态、增长、Gap、预测和决策必须说明使用哪些变量、变量属于哪个维度、如何测量、何时有效、来源是什么。禁止把隐含假设伪装成事实。

### 2.10 向性方向法则

向性表达域的意图和趋避倾向，方向表达事件发生后的真实移动，轨迹表达历史变化。Intent、Direction 和 Outcome 不得混为一体。

### 2.11 影响向量法则

影响必须有 source、target、channel、dimension、polarity、magnitude、latency、duration、confidence 和 source facts。影响力不是单一总分，也不等于 Reputation。

### 2.12 关系语境法则

域价值不是孤立属性，而由它与其他域、需求、世界和时间的关系共同决定。

### 2.13 价值生长法则

连接只有进入真实价值交换并形成结果，才可能成为成长。浏览、注册、内容数量、付款或 completed 状态都不能单独证明价值。

### 2.14 证据主张法则

Evidence 证明来源真实性，Claim 表达结构化主张，Binding 判断主张在某一语义世界中是否成立。三层不得合并。

### 2.15 来源谱系法则

释放、复制、合并、吸收和派生必须保留 origin、parent、contributor、license、revision 和 canonical hash。

### 2.16 数据资产法则

数据首先属于产生它的域及合法参与者。平台只能在授权、脱敏和治理边界内形成公共产业资产。

### 2.17 可配置进化法则

域类型、Facet、状态机、关系、评分、世界本体、Agent 权限和预测模型必须版本化配置；已发布版本不可静默改变。

### 2.18 未来诚实法则

未来可以建模、推演和校准，但不能被写成已经发生的事实。预测必须携带时间范围、假设、概率、置信度、模型版本和来源清单。

### 2.19 宪章最高法则

恒域世界宪章（Hengyu Constitution）冻结真实性、域主基本权利、安全、账本守恒、来源谱系和申诉底线。任何平台标准、World Rule、组织规则、市场规则、任务规则或 Realm Policy 都不得关闭这些不变量。

### 2.20 嵌套规则域法则

域进入某个 World、组织、空间、市场、项目或 Engagement，即进入相应 Rule Domain，并在域内遵守已经发布且对其有效的规则。下级规则可以更严格或更具体，但不得越过上级宪章、现实法律与不可让渡权利；规则必须可见、版本化、非追溯生效，并提供退出、申诉或争议处理路径。

### 2.21 能力可执行法则

能力不只是一段描述。正式 Skill 必须声明输入、输出、前置条件、工具与模型依赖、数据边界、权限、成本、评估、版本和回滚。Skill、Tool、Model、Workflow、Agent 与 Product 必须分离，才能替换执行器而保留业务能力。

### 2.22 价值守恒法则

任何货币、积分、额度、贡献、资源用量与收益分配都必须进入对应账本；转移必须成对、幂等、原子、可审计和可对账。Money/Credit、Contribution/Royalty、Trust/Reputation、Experience/Achievement、Usage/Cost 五类账不得互相伪装或自动换算。

### 2.23 真实成长游戏法则

探索、任务、组队、挑战、装备、技能树、奖励和成就可以成为世界交互机制，但必须服务真实需求、学习、协作、交付和成长。完成任务不自动等于结果有效，奖励不自动等于信誉，付费不可以买到真实性。

### 2.24 开放互操作法则

恒域世界、行业世界及域主都可以自研工具，也可以接入 GPT、豆包、Codex 和未来模型、MCP、API、SaaS 与外部数据。架构必须供应商中立；所有外部调用记录 Provider、Model/Tool Version、Prompt/Rule、权限、成本、Trace 与数据去向。对外提供的不是裸数据库，而是带 schema、来源、truth、许可、用途、时效和撤回规则的 DataProductEntity。

### 2.25 现实主体分离法则

现实主体、登录账户、数字域、认领记录和控制授权必须分离。认领不等于所有权，控制不等于受益，操作不等于最终责任；任何生产动作必须能回答谁授权、谁执行、谁承担责任以及如何撤销。

### 2.26 状态非主体法则

“态”只能描述域在指定时间、世界、观察者和规则下的状态向量，不能取代持续身份。状态变化不能新建或删除主体；主体的身份、事件和责任历史不会因为状态归零而消失。

### 2.27 行业模板演化法则

行业不是一张分类表，而是需求、供给、能力、产品、交易、信任、规则、知识和结果长期稳定交叠形成的群落域与世界。每个 `恒域世界-{行业}` 必须继承通用 Universe Contract，再发布自己的版本化 World Genome。

### 2.28 相似只产生候选法则

新行业可以从结构、角色、交易和能力最相似的已验证行业复制模板，但相似度只能产生 draft/synthetic 候选。新行业的概念、规则、证据要求和状态基线必须重新验证，禁止复制旧行业事实冒充新行业事实。

### 2.29 多维价值法则

单一“域总分”式的价值不存在。域价值至少区分使用、交换、可信、知识、网络、选择权和公共价值；每个维度都必须声明观察者、世界、时间、来源和计算规则。交易只能强化其中部分维度。

### 2.30 体验不污染事实法则

任务、等级、XP、成就、排行和虚拟奖励属于体验表达，不能直接改写 Evidence、Claim、Reputation、Capability、Outcome、Money 或生产 World State。游戏机制只能消费可信事实并生成独立体验事件。

### 2.31 先活域后世界法则

第一开发优先级永远是一个真实封装域的完整生命闭环。组织、行业、市场、金融、游戏和预测只有在前一层产生真实 Outcome 后才能进入 production；否则只能处于 architecture、simulation 或 observation。

### 2.32 架构保留法则

终极架构不因当前尚未实现而删除未来必要系统，也不因已有代码存在而把临时实现写成永久本体。所有能力通过 Keep、Adapt、Migrate、Refactor、Stop 五态归位，并用 ADR 记录理由、兼容期和退出条件。

### 2.33 域主主权法则

域主对其合法控制的数据、权限、品牌表达和退出路径拥有可执行权利。平台只能在授权、合同、公共来源或法律依据范围内处理，不能以“建设行业”为由默认占有。

### 2.34 现实需求驱动法则

能力、工具、连接、产品和行业概念必须从域主的真实场景、目标、痛点、项目和结果中产生。平台可以发现、整理和辅助实现，不得脱离现实需求凭空设计行业用途。

### 2.35 行业共建法则

行业事实、业务标准和价值判断由有资格的域主共同提出、验证、批准和修订。平台提供议事、版本、投票、试行、申诉和执行基础设施，不垄断行业解释权。

### 2.36 项目数据生成法则

恒域世界的高价值数据优先来自真实项目中的授权、行动、交付、确认、争议、结果和结算。静态导入数据可作为起点，但不得冒充履约历史和结果证据。

### 2.37 声明不等于验证法则

域主自己的数据是第一信任入口，不是自动可信终点。自我声明、系统观察、对手方确认、证据支持、第三方验证和项目结果验证必须分层存储与传播。

### 2.38 工具可替换法则

模型、Skill、Agent 与 SaaS 提供方必须可替换。平台核心只保存跨工具仍然成立的身份、上下文、权限、规则、项目、证据、结果、账本、贡献、信誉和资产。

### 2.39 平台中立与角色分离法则

平台经营者、自营服务方、工具创造者、行业发起人、行业域主和规则召集人属于不同角色。任何决策必须声明当前角色、权限范围和利益冲突；平台不得自证、自评、自荐或暗中歧视竞争域。

### 2.40 品牌可信成长法则

品牌不是宣传字段，而是由身份、内容、产品、案例、外部引用、项目结果、客户确认、信誉和权利共同组成的持续域。AI 可见度只能作为观察和增长入口，不能替代真实能力、履约与信任。

## 第三章 统一域协议与微内核

### 3.1 域（Realm；现有代码 Entity）的正式定义

域是恒域世界中具有稳定标识、可治理边界、模组组成、事件历史和局部世界的可寻址存在单元。`Realm` 是 V10.0 的英文架构名；现有代码、表和 API 中的 `Entity` 作为兼容别名保留。一个正式域至少包含：

- Entity ID：全局稳定身份；

- Archetype：采用哪一种域基因谱；

- Form：结构形态；

- Installed Modules：已经安装和启用的模块；

- Controller：谁拥有、管理或被授权控制；

- Revision：当前内容与结构版本；

- Event Ledger：发生过什么；

- State Vector：当前多维状态；

- Variable Set：状态、环境、控制、扰动、目标与派生变量；

- Dimension Schema：变量所在的配置化坐标体系；

- Entity Horizon：可见、可知、可达与可影响的边界；

- Environment Field：当前相关外部条件；

- Orientation / Influence / Trajectory：向性、影响与演化轨迹；

- Facets：在不同世界中的用途与角色；

- Relations：与其他域怎样连接；

- Provenance：来源与派生谱系；

- Policy Bundle：权限、许可、状态机和 Truth Boundary。

名称只是域的 Label，可以重复和修改；Realm ID（兼容 `Entity ID`）才是身份。Account 负责登录，Controller 负责控制，Realm 表达在恒域世界中持续存在的对象，三者不能等同。

### 3.2 域九件套命名

| **中文名称** | **英文名称**                          | **职责**                                           |
|--------------|---------------------------------------|----------------------------------------------------|
| 域核         | Realm Kernel（Entity Kernel）         | 不变量：ID、起源、基因谱、控制权和当前版本         |
| 域基因谱     | Realm Genome（Entity Genome）         | 可版本化的结构模板、允许 Facet、状态机、规则与接口 |
| 域封装体     | Realm Capsule（Entity Capsule）       | 域组合形成的治理边界与可对外身份                   |
| 域模组       | Realm Module（Entity Module）         | 可安装、可复用、可释放并声明输入输出的能力单元     |
| 域切面       | Realm Facet（Entity Facet）           | 域在特定世界、关系或用途中的角色表达               |
| 域记忆       | Realm Memory（Entity Memory）         | Event Ledger、事实变更与经历                       |
| 域视界       | Realm Horizon（Entity Horizon）       | 域可见、可知、可达和可作用的动态边界               |
| 域表达态     | Realm Expression（Entity Expression） | 指定时点由事实和事件投影出的可见状态               |
| 域谱系       | Realm Lineage（Entity Lineage）       | 来源、贡献、复制、派生、合并、版本和许可链         |

### 3.3 域描述语法

任何域都使用同一语法描述：

    Entity = Kernel
         + Genome@Version
         + Modules[]@Version
         + Form
         + Facets[]
         + StateVector
         + VariableSet
         + DimensionSchema
         + Horizon
         + EnvironmentField
         + OrientationVector
         + InfluenceField
         + Trajectory
         + AgencyMode
         + Components[]
         + Relations[]
         + EventLedger
         + Lineage
         + PolicyBundle

可读表达采用：

    [Form] / [Primary Facet] / [Lifecycle State] / [Truth State]

例如：

- CapsuleEntity / Actor / active / verified：已认领并运行的真实企业；

- ModuleEntity / Capability / released / verified：可复用且有证据的能力模块；

- ModuleEntity / Knowledge / released / observed：公开但尚未完成验证的方法草稿；

- ModuleEntity / Skill / released / verified：经过测试、审批并具有明确运行边界的生产 Skill；

- CapsuleEntity / DataProduct / active / observed：可授权分发但 truth distribution 尚非全 verified 的数据产品；

- CapsuleEntity / RuleDomain / active / verified：具有合法 Controller、规则版本和成员边界的治理空间；

- MirrorEntity / Forecast / active / hypothesis：对未来路径的预测域；

- EventEntity / Engagement / completed / observed：已经记录但结果尚未验证的项目事件。

### 3.4 Entity Kernel：必须稳定的最小内核

Entity Kernel 只承担跨所有域都成立的不变量：

- Entity ID、origin 和 current revision；

- controller、delegation 与 ownership policy；

- genome version 与 module manifest；

- event ledger pointer 与 canonical hash；

- truth、access、reuse 和 evolution boundary；

- lineage root 与 correction mechanism。

Kernel 不直接保存行业专属业务字段。个人、企业、产品、项目和行业的差异都通过 Module、Facet、Genome 和 Composition 表达。

### 3.5 Entity Module：域生命的功能器官

Entity Module 不是代码包的同义词，而是拥有业务语义、状态、事件与权利边界的可安装协议。首批模块族包括：

1.  Identity Module：名称、标识、主体声明和认证；

2.  Memory Module：事件、经历、故事和修正；

3.  Capability Module：能力声明、证据、等级和过期；

4.  Offering Module：产品、服务、版本和交付条件；

5.  Demand Module：场景、目标、痛点、缺口和优先级；

6.  Engagement Module：协议、项目、交易、交付和争议；

7.  Trust Module：Evidence、Claim、Verification 和 Reputation；

8.  Asset Module：数据、内容、许可、收益与贡献；

9.  Knowledge Module：经验、方法、案例、反思和复用；

10. Environment Module：视界、环境观察、信号和约束；

11. Dynamics Module：变量、向性、影响和轨迹；

12. World Module：Concept、Binding、Projection、State 和 Industry；

13. Future Module：Intent、Plan、Scenario、Forecast 和 Counterfactual；

14. Agent Module：感知、解释、规划、工具、执行和复盘；

15. Policy Module：Rule Domain、角色、权限、义务、制裁、退出和申诉；

16. Skill Runtime Module：Skill、Tool、Model、Workflow、Trace、Evaluation 和 Rollback；

17. Economy Module：Asset Unit、Account、Order、Ledger、Settlement、Royalty 和 Reconciliation；

18. World Interaction Module：Quest、Party/Guild、WorldInstance、XP、Achievement 和 Reward；

19. Data Exchange Module：Data Product、Connector、Subscription、Usage、SLA 和 Revocation。

### 3.6 Module Contract

每个 Module Definition 必须版本化声明：

    module_code / module_version
    compatible_archetypes / dependencies / conflicts
    input_contract / output_contract
    state_variables / dimensions
    accepted_events / emitted_events
    provided_facets / relation_types
    truth_boundary / access_policy / reuse_policy
    applicable_rule_domains / required_authority / approval_points
    cost_budget / economic_events / usage_meter
    risk_level / sandbox_policy / data_destination
    install_rule / activate_rule / release_rule
    migration_rule / rollback_rule
    config_hash / publisher / published_at

Module Installation 必须保存 entity_id、module_version、config、installed_by、installed_at、activation_state 和 installation_hash。已发布安装历史不可静默修改。

### 3.7 Genome、Module、Facet 与 Form 的边界

- Genome 决定域允许安装什么、怎样迁移和哪些内核规则不可破坏；

- Module 提供可运行能力、状态变量和事件接口；

- Facet 表达模块在某一语境中的用途和角色；

- Form 表达域当前怎样组合；

- Capsule 表达控制与责任边界；

- Expression 表达指定时间和观察原点下看见的状态。

### 3.8 现实主体、账户、域与控制权

<img src="media/02_owner_control_roles.png" alt="现实主体、域主、账户、域和角色授权链" />

现实主体、域主、账户、域和角色授权链

工程上禁止再把“一个 ID”混成一个对象：

| **对象**                     | **作用**                               | **关键边界**                                 |
|------------------------------|----------------------------------------|----------------------------------------------|
| 现实主体（Real Actor）       | 现实个人、企业、机构或依法成立的组织   | 承担现实权利与责任                           |
| 登录账户（Account）          | 认证、会话、设备、凭证和登录安全       | 一个现实主体可有多个账户，账户不等于域       |
| 数字域（Realm）              | 恒域世界中持续存在的数字主体           | 一个主体可认领多个域，一个域可被多人授权运营 |
| 认领记录（Entity Claim）     | 谁基于什么证据主张该域                 | 认领可撤销、可争议，不自动产生全部所有权     |
| 控制授权（Controller Grant） | 允许谁在何范围、期限、世界和预算内行动 | 必须版本化、最小权限、可撤销、可审计         |

控制角色进一步分为：认领者（Claimant）、控制者（Controller）、运营者（Operator）、管理者（Steward）、受益人（Beneficiary）、观察者（Observer）和责任主体（Accountable Actor）。同一现实人可以承担多个角色，也可以由不同人员分担；系统不限制现实团队规模，但必须知道每个生产动作的授权链。

“域主”是产品语言中的总称，不替代上述精确法律和系统角色。域主可以是 Claimant、Controller、Steward、Beneficiary 的任意合法组合；一旦发生生产动作，必须解析为具体授权角色。

本项目发起人的多重身份必须明确分开：

| **角色**            | **可以做什么**                           | **不能因此获得什么**               |
|---------------------|------------------------------------------|------------------------------------|
| 公司创始人          | 决定公司经营、预算和产品方向             | 不能单方定义行业事实               |
| 恒域世界平台发起人  | 维护通用架构、技术协议和安全边界         | 不能让平台规则冒充行业规则         |
| 恒域世界-GEO 发起人 | 召集首批域主、启动试点和产品运营         | 不能垄断 GEO 行业解释权            |
| GEO 行业域主        | 提交自身需求、能力、数据、项目与规则建议 | 不能查看或处置其他域主私有数据     |
| 规则共建召集人      | 发起议题、组织讨论、记录版本与决议       | 不能自己提案、自己验证、自己批准   |
| 品牌/服务提供方     | 发布产品、承接项目、建立品牌资产         | 不能获得自营推荐和自证信誉         |
| 工具创造者          | 发布 Skill、工具和数据产品               | 不能绕过沙箱、评估、许可和利益披露 |
| 数据处理者          | 按授权处理、转换和输出数据               | 不能扩大用途、永久占有或私自训练   |

所有高风险动作保存 `actor_domain_id / current_role / world_id / authority_scope / decision_scope / conflict_of_interest / evidence_refs / occurred_at`。同一个登录账户切换角色时必须显式显示当前身份，不能在后台静默切换。

企业域可以包含部门、岗位、项目、产品和资源，也可以引用员工自己认领的个人域。企业规则只约束合同、岗位、项目、资产和合法授权范围内的行为；员工的身份、私人数据和与企业无关的能力不自动归企业所有。员工创建的代码、内容、Skill、数据和知识必须按劳动关系、项目协议、许可和贡献记录判断归属，不能用“在企业域内创建”自动推断所有权。

### 3.9 数字候选、数字影子、数字镜像与数字孪生

系统从网络发现或 AI 分析形成的对象不能直接称为真实域，更不能直接称为数字孪生：

1.  **域候选（Entity Candidate）：** 尚未完成稳定身份和主体确认的发现对象；

2.  **数字影子（Digital Shadow）：** 来自公开或外部数据的单向数字表达，通常尚未认领；

3.  **数字镜像（Digital Mirror）：** 指定观察者、时间和规则下形成的派生状态或投影；

4.  **数字孪生（Digital Twin）：** 与现实主体或过程按明确频率和保真度持续同步，并具有授权反馈边界的数字表达。

Web 抓取、用户输入和 AI 分析默认只能形成 candidate、observed 或 synthetic。升级为 verified 必须经过 Evidence→Claim→Binding；升级为 Digital Twin 还必须声明 twin_subject、synchronization_channel、frequency、fidelity、drift_policy、feedback_authority 和责任人。

同一 Genome 可以实例化无数独立域；一个域可以安装多个 Module；同一个 Module 可以提供多个 Facet；任何实例都必须拥有独立 Entity ID、事件历史和控制权。

## 第四章 域构形（Realm Form）：五种结构形态

Entity Form 只回答“怎样组成”，不回答“用来做什么”。同一 Form 可以承担多个 Facet。

### 4.1 原生域（Primitive Realm；兼容 AtomEntity）

在当前业务边界内不再拆分、需要独立寻址的最小单元。例如一个结构化 Claim、一份许可证、一个时间点信号或一个配置版本。

原子是相对概念：当新的治理、复用或审计需求出现时，它可以升级为更复杂形态。

### 4.2 模组域（Modular Realm；兼容 ModuleEntity）

拥有独立 Entity ID、Controller、版本、来源和生命周期，可被多个域引用、安装或吸收的组件域。例如一门课程、一套方法论、一个数据集、一个工具包或一个 Agent Tool 封装。

**ModuleEntity 不等于 Entity Module。** ModuleEntity 是“域当前怎样组成”的 Form；Entity Module 是安装到 Entity Kernel 上的功能契约。一个 ModuleEntity 可携带一个或多个 Entity Module，也可被引用而不安装。

### 4.3 封装域（Capsule Realm；兼容 CapsuleEntity）

由多个域构成，拥有稳定边界、控制者、对外身份、责任和独立生命周期的复合域。个人、企业、服务商、品牌、成熟产品和 Agent 可以采用该形态。

封装域对外看似一个整体，对内仍保留成员、组件、来源和贡献链。

### 4.4 群落域（Collective Realm；兼容 CollectiveEntity）

由成员关系、规则或共同目标形成的动态集合，例如项目团队、产业联盟、区域生态、行业网络和合作共同体。成员可变化，集体本身拥有治理规则和事件历史。

### 4.5 镜像域（Mirror Realm；兼容 MirrorEntity）

由其他域和事件投影形成，不取代来源事实。例如快照、世界投影、数字孪生、场景、模拟、预测和报告。MirrorEntity 必须保存 source manifest 与生成规则。

### 4.6 Form 升级与降级

域形态可以演化，但必须通过显式事件完成：

- 原始内容被反复复用后，从 AtomEntity 升级为 ModuleEntity；

- 产品形成独立客户、版本、责任和资产后，从 ModuleEntity 升级为 CapsuleEntity；

- 项目联盟形成稳定治理后，从临时关系升级为 CollectiveEntity；

- World State、报告和预测始终属于 MirrorEntity，不得冒充来源事实。

## 第五章 域切面（Realm Facet）：域的用途与角色

Facet 是可叠加、可配置、可随世界变化的语义切面。域不需要复制成多个实体，只需在不同语境中挂载不同 Facet。

### 5.1 身份与行动 Facet

| **Facet**  | **中文名**   | **说明**                       |
|------------|--------------|--------------------------------|
| Identity   | 身份切面     | 名称、标识、认证、公开资料     |
| Actor      | 行动主体切面 | 可以发起目标、需求、承诺和行为 |
| Controller | 控制切面     | 管理、授权、委托和撤销权限     |
| Role       | 角色切面     | 在指定 World 中承担的角色      |
| Intent     | 意图切面     | 域主动表达的未来目标与约束     |

### 5.2 价值 Facet

| **Facet**  | **中文名**    | **说明**                                   |
|------------|---------------|--------------------------------------------|
| Capability | 能力切面      | 域能做什么以及证据覆盖                     |
| Tool       | 工具切面      | 可调用的原子执行能力、接口与运行约束       |
| Skill      | 技能切面      | 完成某类工作的可复用方法、依赖、评估与版本 |
| Workflow   | 工作流切面    | 多个 Skill、Tool、Agent 和审批的有序编排   |
| Model      | 模型切面      | 推理、生成、识别或预测执行器及其能力边界   |
| Resource   | 资源切面      | 可被使用、授权、交换或消耗的要素           |
| Offering   | 产品/服务切面 | 能力与知识的可交换封装                     |
| Demand     | 需求切面      | 场景、目标、痛点和缺口                     |
| Engagement | 价值交换切面  | 协议、参与者、项目、交付和里程碑           |
| Outcome    | 结果切面      | 对交付后变化的结构化主张                   |

### 5.3 信任 Facet

Evidence、Claim、Verification、Reputation 和 Certification 继续分离。一个域可以同时是 Evidence 的载体、Claim 的主体和 Certification 的持有者，但每个验证关系必须独立记录。

### 5.4 资产 Facet

Data、Content、Knowledge、Case、License 和 Contribution 用于表达域沉淀的数字资产、内容资产、知识资产、案例资产和权利结构。

### 5.5 世界与智能 Facet

Concept、Rule、Policy、Standard、RuleDomain、World、Signal、Scenario、Forecast、Recommendation 和 Hypothesis 用于解释环境、约束行为、表达未来与支持决策。DecisionProposal 与 DecisionExecution 必须分离：AI 可以生成带来源的决策候选，只有持有相应 authority 的主体才能批准执行。

### 5.6 动力学 Facet

| **Facet**   | **中文名** | **说明**                                         |
|-------------|------------|--------------------------------------------------|
| Environment | 环境切面   | 域所处的外部条件与作用通道                       |
| Variable    | 变量切面   | 能被观测、控制、扰动或派生的变化量               |
| Dimension   | 维度切面   | 定义变量在哪个意义空间中变化                     |
| Orientation | 向性切面   | 域对目标、风险、资源和其他域的趋近或远离倾向     |
| Influence   | 影响切面   | 通过指定通道改变其他域状态或选择空间的可观察作用 |
| Trajectory  | 轨迹切面   | 域在多维空间中的历史运动路径                     |
| Action      | 行动切面   | 在授权与约束下执行可追踪操作                     |
| Constraint  | 约束切面   | 限制可行动作、组合或资源分配的条件               |
| Opportunity | 机会切面   | 由域目标与环境结构共同产生的可行价值空间         |

这些 Facet 使“生命”从比喻变成可计算对象：环境不再是页面背景，方向不再是一句文案，影响不再是一个粉丝数。

### 5.7 Facet 不是永久类型

一个课程在企业 A 看来是 Resource，在服务商 B 看来是 Offering，在专家 C 的成长路径里是 Learning Module，在行业世界里又可能是 Capability Provider。Facet 随语境变化，Entity ID 与来源历史不变。

# 第二篇 域生命、环境与价值代谢

## 第六章 状态、变量、维度与轨迹

域状态必须按维度分离，禁止把 truth、生命周期、权限和可用性压缩成一个 status 字段。

### 6.1 生命周期状态 Life State

    seed → registered → claimed → active → released
                             ↘ dormant → active
    released → superseded / retired / revoked

- seed：已创建最小身份壳，内容可能不完整；

- registered：进入 Entity Registry；

- claimed：由合法 Controller 认领；

- active：持续发生有效事件；

- released：已向指定范围发布，可被发现或复用；

- dormant：暂时不活动但历史保留；

- superseded：被新版本替代；

- retired：正常停止使用；

- revoked：因权利、真实性或治理原因撤销。

### 6.2 Truth State

沿用并扩展现有边界：synthetic、observed、verified、disputed、revoked。future、intent、plan、forecast 和 hypothesis 不得混入 Truth State，它们属于 Epistemic State。

### 6.3 Epistemic State：认知状态

- unknown：尚无足够信息；

- candidate：候选解释或待验证结构；

- hypothesis：需要未来证伪的假设；

- estimated：基于模型估计的当前值；

- forecast：带时间范围的未来概率；

- recommended：系统建议；

- planned：由主体承诺的计划。

### 6.4 Access State：可见与授权状态

private、team、counterparty、ecosystem、public、licensed。所有读取、复制和推理权限均由 Policy Bundle 决定，公开可见不等于可自由复制。

### 6.5 Control State

unclaimed、claimed、delegated、shared、locked。控制权可以转移或委托，但必须产生可审计事件。

### 6.6 Reuse State

bound、reference_only、licensed_copy、forkable、open。个人身份、信誉和部分证书通常为 bound；公开方法、模板和数据集可按授权成为 forkable 或 open。

### 6.7 Variable System：变化必须显式

一个变量必须是定义良好的可观察或可控制量，不是任意 JSON 字段。

| **变量类型**         | **作用**               | **例子**                           |
|----------------------|------------------------|------------------------------------|
| State Variable       | 表达域当前状态         | 可用产品数、能力等级、未完成需求数 |
| Environment Variable | 表达域所处条件         | 区域需求、政策状态、模型平台变化   |
| Control Variable     | 域可主动调整           | 预算、价格、投入时间、发布频率     |
| Disturbance Variable | 外部扰动且不由域控制   | 竞争者动作、算法变更、法规变化     |
| Target Variable      | 意图或计划希望改变的量 | 获得首个 verified Outcome          |
| Derived Variable     | 根据明确规则派生       | 需求覆盖率、证据有效率             |
| Latent Variable      | 目前无法直接观测       | 合作意愿、新市场接受度             |

Variable Definition 至少包含 `variable_code / dimension_code / value_type / unit / scale / source_rule / valid_time / scope / aggregation_rule / truth_status / confidence / null_rule / not_applicable_rule`。潜变量必须标注为 estimated/hypothesis，不得冒充观测事实。

### 6.8 Dimension Registry：维度是变化的语义坐标

Kernel 只冻结维度注册协议，不冻结一个永久的全球向量。首批基础维度包括：

1.  Identity & Control：身份、控制、责任与权限；

2.  Time & Lifecycle：时间、存续、活性与阶段；

3.  Capability & Resource：能力、工具、人才、资本与供给；

4.  Offering & Supply：产品、服务、交付和可获得性；

5.  Demand & Objective：场景、目标、痛点与缺口；

6.  Engagement & Value：合作、交易、贡献、结果与分配；

7.  Trust & Evidence：证据、主张、验证、争议与信誉；

8.  Data & Knowledge：数据、知识、版权、许可与复用；

9.  Relation & Influence：关系、距离、通道、方向和作用；

10. Environment & Risk：区域、政策、市场、技术、机会和风险；

11. Agency & Action：意图、权限、决策、行动与可行域；

12. Future & Possibility：信号、趋势、场景、概率与未来分支。

World Version 可以添加行业维度，但必须声明它与基础维度的映射、单位、适用对象、Evidence Requirement 和退役规则。

### 6.9 Entity Expression：当下的可重建表达

Entity Expression 是在 `observer_entity_id + as_of + world_version + policy_scope` 下对多维变量的投影。它是 MirrorEntity，不是新事实；必须保存 source manifest、聚合规则、unknown、excluded 与 source drift。

### 6.10 Evolution Trajectory：历史轨迹

Trajectory 是域状态在多维空间中经时间形成的可追溯路径，由事件和表达重建，不是一条 AI 自动拟合的“命运曲线”。它区分已观测轨迹、计划轨迹、场景轨迹和预测轨迹，四者的 Truth/Epistemic State 不得混用。

### 6.11 Vitality Signals：域活性信号

活性不是单一等级，而是一组可解释指标：最近有效事件、活跃关系、价值交换、结果验证、知识复用、能力变化、环境响应和未来意图。任何综合指数都必须说明分量、规则版本和不适用条件。

## 第七章 域本位世界、域视界与环境场

### 7.1 每个域都是自己世界的坐标原点

“中心”只表示观测、解释和行动的坐标原点，不表示具有全局权力、绝对真理或更高价值。人、企业、产品、知识、项目、产业和 WorldEntity 都可在自己的视界中理解环境，但必须共享同一 Universal Fact Layer。

### 7.2 Entity World 的正式定义

    EntityWorld(observer_entity_id, world_code, world_version, as_of, policy_scope)
    = Self + Installed Modules + State Variables + Horizon
    + Environment Field + Orientation + Incoming/Outgoing Influence
    + Action Cone + Evolution Trajectory + Possible Worlds

EntityWorld 是按观察主体构建的可重建 MirrorEntity。两个域面对同一个事实，可因权限、距离、目标、知识和世界版本不同而获得不同投影；但投影不得改写事实。

### 7.3 Entity Horizon：域能看见和触达的边界

| **Horizon**         | **回答的问题**                       |
|---------------------|--------------------------------------|
| Perception Horizon  | 哪些信号已进入感知范围？             |
| Knowledge Horizon   | 域拥有哪些有来源的知识？             |
| Relation Horizon    | 当前能看见哪些直接或间接关系？       |
| Transaction Horizon | 哪些价值交换机会实际可达？           |
| Influence Horizon   | 哪些域可能影响它，它可能影响谁？     |
| Action Horizon      | 在权限、资源和时间下哪些行动可执行？ |

Horizon 的扩张与收缩都是事件。权限撤销、许可到期、知识过期和关系中断会使视界收缩，不能只记录“增长”。

### 7.4 Environment Field：环境是域相对感知的作用场

环境不是一张全局配置表，而是对指定 observer 有潜在或已实现作用的条件集。至少分为：内部环境、直接关系环境、行业环境、区域/社会环境、信息环境、时间环境与未来信号环境。

### 7.5 Environment Observation

每次环境观测至少记录：

    observer_entity_id
    environment_entity_id / environment_ref
    channel / distance / relevance
    affected_dimension / affected_variable
    effect_type: opportunity | constraint | risk | neutral
    truth_status / epistemic_state / confidence
    evidence_refs / source_manifest
    valid_from / valid_until / observed_at

相同政策对不同企业可能是机会、约束或不相关；影响类型是域与环境的关系属性，不是环境域的固定标签。

### 7.6 Agency Mode：四级行动模式

| **模式**   | **中文名** | **能力边界**                               |
|------------|------------|--------------------------------------------|
| Record     | 记录型     | 被读取、引用和验证，不主动行动             |
| Responsive | 响应型     | 在规则触发时更新状态或发出信号             |
| Actor      | 行动型     | 能表达目标、需求、承诺并承担责任           |
| Agentic    | 代理型     | 在授权范围内感知、规划、调用工具和执行任务 |

Agency Mode 不等于智能高低。企业域可以是 Actor，但其内部 Agent 只在委托范围内拥有 Agentic 权限。任何 Agent 行为都必须回写到责任主体、任务、工具、输入、输出和审批记录。

### 7.7 Action Cone：当前可行动作集

Action Cone 由意图、Agency Mode、权限、可用 Module、资源、关系、环境约束和时间窗口共同计算。它输出 `allowed / requires_approval / unavailable / unknown`，不用一个“行动力分数”简化。

### 7.8 全局事实与局部世界

Universal Fact Layer 保存可共享事实；Entity World 保存域本位的解释。关系、机会、风险、优先级和“近/远”通常是 observer-relative，不得写回对方域成为全局属性。

### 7.9 不设全局绝对中心

Universe 可以拥有平台入口、治理机构和主世界，但它们不是本体论中的唯一中心。任何全局地图都是指定规则和时点的聚合 MirrorEntity，必须允许切换 observer、scope 与 world version。

## 第八章 Entity Dynamics：向性、影响、组合、释放与变异

### 8.1 Orientation Vector：域的向性

向性是域在指定目标、时间和环境下对行动方向的可解释倾向，可包括 approach、avoid、absorb、release、connect、compete、cooperate、learn 与 invest。它来自 Intent、Constraint、Value Preference 与环境信号，必须标注主体明示、行为观测或模型估计。

### 8.2 方向、向性与结果分离

- Direction 是某次状态变化的已观测方向；

- Orientation 是行动前的倾向，可以改变；

- Plan 是主体承诺的步骤；

- Recommendation 是系统建议；

- Outcome 是事后对变化的主张。

向性不得被当成已发生结果，也不得被 AI 推断成域的永久性格。

### 8.3 Influence Vector：影响是带通道与方向的作用

    source_entity_id / target_entity_id
    channel / affected_dimension / affected_variable
    polarity / magnitude / latency / duration
    potential_or_realized
    truth_status / confidence
    source_event_ids / evidence_refs
    valid_from / valid_until

potential influence 只表示可触达或可能作用；realized influence 必须存在目标变量改变与可接受的支持链。未证实因果时只写 `correlates_with / may_influence`。

### 8.4 影响力不是单一分数

影响必须按对象、世界、维度、时间、通道和真实状态展示。发布量、粉丝数、交易额或 Reputation 不能直接等同于影响；负向、延迟、短期和长期影响必须分开。

### 8.5 域动力学循环

    Environment Signal → Perception → Variable Update → Orientation
    → Action Cone → Action / Connection / Engagement
    → Influence & Outcome → Event Ledger → State / Trajectory
    → Learning / Module Change → New Horizon

这个循环是每个 Actor/CapsuleEntity 的通用生命机制。不同人、企业、产品和行业只是安装了不同 Module、使用了不同 Dimension Schema 与治理边界。

### 8.6 七种组合操作

| **操作** | **英文**    | **语义**                                       |
|----------|-------------|------------------------------------------------|
| 引用     | reference   | 使用对方身份或内容，不复制、不转移控制权       |
| 包含     | contain     | 把域作为可见成员纳入封装，成员保持独立身份     |
| 嵌入     | embed       | 把指定版本快照嵌入封装，来源仍可追溯           |
| 吸收     | absorb      | 经授权将能力、知识或资源转化为自身组成或状态   |
| 委托     | delegate    | 授予行动权，不改变所有权                       |
| 释放     | release     | 将内部、休眠或私有组成变成可独立寻址域         |
| 派生     | fork/derive | 创建新 Entity ID，保留父域、差异、许可和贡献链 |

### 8.7 合并与拆分

merge 创建新的 CapsuleEntity 或 ModuleEntity，原域默认保留；split 从封装中释放一组域。任何合并与拆分都必须记录参与者、版本、来源、权利和结果，不能通过数据库覆盖假装历史从未发生。

### 8.8 实例化、复制与派生

- Genome Instantiation：继承结构、模块契约和初始状态机，不继承原域的事实、信誉、控制权和经历；

- Licensed Copy：在许可下复制指定资产内容，创建新实例和使用事件；

- Fork/Derive：新建 Entity ID，保留父域、差异、贡献和许可链；

- Release：从 Capsule 内部将潜在组成转为可独立寻址域。

“一个封装域变成无数域”应通过上述受治理操作实现，不通过自动遍历所有字段来爆炸建点。

### 8.9 五类变异

1.  State Transition：变量和状态的正常改变；

2.  Configuration Mutation：域实例配置变更；

3.  Composition Mutation：组成域、关系或控制边界改变；

4.  Module Mutation：Module 安装、卸载、激活、替换或版本迁移；

5.  Genome Evolution：域类型契约发布新版本。

前四类改变实例；只有第五类改变可被新实例继承的 Genome，必须经过 Evolution Candidate、Simulation/Shadow Run、审批、版本发布和回滚机制。

### 8.10 域谱系

每次 release、fork、merge、absorb 或 transform 至少写入：

    origin_entity_id
    parent_entity_ids
    source_revision_ids
    transformation_event_id
    contributors[]
    license_or_policy
    canonical_hash
    created_by / created_at

复制不是同一个身份。相同内容可通过 canonical hash 去重，但每个具有独立控制、关系或生命周期的实例必须拥有自己的 Entity ID。

## 第九章 Event Ledger：事件让域拥有生命

### 9.1 EventEntity 定义

EventEntity 是在特定时间发生、涉及一个或多个域、可能产生状态变化的可审计记录。它采用对象中心事件模型：一个交易事件可以同时关联买方、卖方、产品、协议、交付、资金和 Outcome，而不必强制归入单一“订单案例”。

### 9.2 统一事件结构

    event_id / event_type
    occurred_at / recorded_at
    participants[{entity_id, role}]
    inputs[] / outputs[]
    relations_changed[]
    variables_changed[{variable_code, before_ref, after_ref, direction}]
    dimensions_affected[]
    environment_refs[] / influence_refs[]
    source_refs[]
    truth_status
    scope
    rule_version / config_hash
    rule_domain_ids[] / policy_decision_ref
    capability_run_refs[] / ledger_transfer_refs[]
    caused_by / correlates_with

caused_by 只能在因果关系得到验证时使用；普通时间先后或模型推断使用 correlates_with / may_influence。

### 9.3 关键事件族

- 身份：EntityRegistered、EntityClaimed、ControlDelegated；

- 模块：ModuleInstalled、ModuleActivated、ModuleDeactivated、ModuleReleased、ModuleMigrated；

- 组合：EntityContained、EntityAbsorbed、EntityReleased、EntityForked、EntityMerged；

- 感知：EnvironmentSignalObserved、VariableObserved、VariableCorrected、HorizonExpanded、HorizonContracted；

- 向性：IntentChanged、OrientationChanged、ActionConeChanged；

- 影响：InfluenceAttempted、InfluenceObserved、InfluenceRealized、InfluenceExpired；

- 能力：CapabilityClaimed、CapabilityVerified、CapabilityExpired；

- 产品：OfferingPublished、OfferingVersioned、OfferingRetired；

- 需求：DemandObserved、DemandVerified、DemandChanged；

- 连接：CandidateProposed、Qualified、Accepted、Rejected；

- 价值：AgreementSigned、EngagementStarted、MilestoneCompleted、DeliveryAccepted；

- 结果：OutcomeClaimed、OutcomeVerified、OutcomeDisputed；

- 资产：DataGenerated、KnowledgeDrafted、KnowledgePublished、AssetLicensed；

- 成长：GrowthMilestoneReached、PathReplanned、TrajectoryCheckpointed；

- 世界：WorldPublished、EntityWorldProjected、ProjectionGenerated、GapDetected、ForecastEvaluated。

- 规则：DomainEntered、PolicyAccepted、PolicyDecisionMade、ObligationFulfilled、SanctionApplied、AppealResolved、DomainExited；

- Skill/工具：SkillCandidateCreated、SkillPublished、SkillInstalled、CapabilityRunStarted、ToolCalled、ArtifactProduced、RunEvaluated、SkillRolledBack；

- 经济：AccountOpened、HoldCreated、TransferPending、TransferPosted、TransferVoided、SettlementCompleted、RefundPosted、RevenueShared、Reconciled；

- 世界参与：QuestPublished、PartyFormed、WorldInstanceStarted、QuestMilestoneCompleted、AchievementGranted、InstanceClosed；

- 数据交换：DataProductPublished、SubscriptionActivated、DataDelivered、UsageMetered、LicenseExpired、DistributionRevoked。

### 9.4 过去不可静默重写

错误通过 Correction Event、更正后的 Revision 或撤销事件处理。状态可以变化，原始记录不能删除后重写为“更好的历史”。

## 第十章 Entity Memory、State 与 Story

### 10.1 三种记忆

1.  Event Memory：发生过的事实事件；

2.  Operational Memory：任务上下文、过程、临时决策和工具结果；

3.  Knowledge Memory：经审核、可复用的经验、案例、方法论和模型。

Agent Runtime Memory 不自动成为 Entity Knowledge。只有经过来源确认、反思、审核和适用范围标注的内容，才能进入知识资产。

Memory 通过 Memory Module 提供，但记忆条目可以是 AtomEntity、ModuleEntity 或对 Universal Fact 的引用。系统必须分离“我发生过”、“我知道”、“我相信”与“我预计”。

### 10.2 Entity Expression

Entity Expression 是指定 observer、as_of、world_version 与 policy_scope 的状态投影，不是新的 Universal Fact。它至少展示：身份、模块、变量、能力、信任、价值、关系、资产、环境、向性、轨迹与 Action Cone，并列出 source manifest。

### 10.3 Entity Story

Story Engine 将事件按阶段和因果证据组织为人能理解的经历，但故事文本只是解释视图。任何叙述都必须能够回到事件、Claim 和 Evidence。

## 第十一章 域成长操作系统

<img src="media/03_realm_growth_loop.png" alt="域从环境、项目、结果到成长或消退的生命闭环" />

域从环境、项目、结果到成长或消退的生命闭环

### 11.1 成长定义

成长不是注册时间、内容量、浏览量或统一等级，而是域在至少一个有价值维度上发生可追溯、可验证的状态变化：

- 身份成长：被认领、验证并完善责任边界；

- 能力成长：获得或提高可证明的能力；

- 产品成长：把能力转化为更成熟的 Offering；

- 信任成长：增加真实、有效、相关的 Evidence 与 Outcome；

- 价值成长：解决更复杂需求并形成更高质量结果；

- 网络成长：形成可持续合作关系；

- 资产成长：沉淀可控制、可复用的数据与知识；

- 认知成长：更准确地理解位置、差距和未来路径。

成长必须表达为“在某环境、某时间窗口和某些维度上的可证变化”。同一次变化对一个域是成长，对另一个域可能是偏离；判断必须引用域的 Intent 与显式目标，不由平台代替所有主体定义“更好”。

### 11.2 域养分

域吸收的不是抽象“数据”，而是有来源、有权利、有适用范围的其他域：能力模块、知识模块、工具、课程、合作关系、产品、反馈、Evidence、Outcome 和世界信号。

### 11.3 Growth Path

Growth Path 由当前 Expression、Intent、Target Variables、Gap、Environment Field、Orientation、Action Cone、可获得域、约束、里程碑和时间窗口构成。不同域使用不同 Genome，不强制统一 L1-L5。

### 11.4 成长闭环

    认识自己 → 表达目标 → 识别 Gap → 获取/组合域
    → 行动与价值交换 → 产生结果 → 验证与复盘
    → 沉淀信任/数据/知识 → 更新能力与产品 → 进入下一阶段

## 第十二章 产品、交易、数据、知识与能力养料

### 12.0 项目是养料转化器

产品、交易、数据、知识、Skill、资本本身不会自动让域成长。项目域（Project Realm；兼容 Engagement Entity）把需求、参与者、授权、工具、里程碑、交付、确认、争议、结果和结算放入一条共同时间线，是各类养料进入域生命的主要转化器。

高价值数据优先由项目产生：谁提出什么需求、使用哪些自有数据、谁调用什么工具、谁作出决定、交付什么、谁确认、结果怎样、争议如何处理、价值如何分配。没有项目上下文的行为日志只能是原始记录，不能直接成为能力、信誉或资产。

### 12.1 产品：Offering Facet

产品不是孤立商品表，而是域把能力、知识、资源和交付方式封装成的可交换价值载体。Offering 必须关联：所有者、目标场景、解决的问题、输入、输出、能力、Evidence Requirement、版本、价格或交换条件、历史 Engagement 与 Outcome。

Offering 可以是 CapsuleEntity 对外发布的 Facet，也可在获得独立 Controller、客户、版本、责任与生命周期后升级为 CapsuleEntity。产品所安装的 Capability/Knowledge/Tool Module 与所依赖的 Provider Entity 必须分开，以允许版本、替换、许可和贡献追踪。

品牌不是产品的营销附属字段。品牌域独立组合多个产品域、内容域、案例域、渠道域、引用域和结果域，并通过授权关系指向其经营主体。产品的真实交付可增强品牌的某一场景可信度，但品牌声量、AI 可见度和付费曝光不能反向证明产品能力。

### 12.2 交易：Engagement Entity

交易的核心是价值交换，不等于支付。购买、咨询、课程、联合研究、数据授权、项目交付、转介、公益贡献和学习均可进入统一 Engagement 生命周期：

    Demand → Candidate → Qualified Connection → Agreement
    → Engagement → Milestone → Delivery → Outcome Claim
    → Evidence Verification → Reputation / Asset / Growth

法币支付通道、电子签署、发票、税务与 KYC/AML 由合规适配器提供，但 Order、Agreement、Hold/Escrow、Transfer、Settlement、Refund、Revenue Share 和 Reconciliation 必须进入 GEO 的受控经济账本。价值事实不依赖支付才能成立，支付事实也不能反过来证明价值。

每个 Engagement 同时是：一段共同时间线、一组约束与承诺、一次域间影响、一批数据来源、一个可能的知识候选与一次产品反馈。交易不是成长终点，而是新域、新事件和新关系的生成器。

### 12.3 数据：Entity Data Asset

每一次合法事件都可能产生数据，但并非每条日志都是资产。资产化至少要求：来源、所有者、贡献者、用途、权限、质量、时间、保留期和撤回规则。

数据经过 `raw record → governed dataset → reusable data product → licensed asset` 四级进化。原始事件不离开事实层；数据产品以 ModuleEntity 发布，并保存 schema、lineage、quality、policy、freshness 和 usage events。

### 12.4 知识：Knowledge Entity

知识生命周期：

    Experience → Record → Evidence/Claim → Reflection
    → Knowledge Candidate → Review → Published Knowledge
    → Reuse → Outcome Feedback → Revision

知识可以被引用、安装、许可、fork 和吸收。每次复用应产生 Usage Event，使贡献者获得可解释的影响记录，而不是平台吞没来源。

### 12.5 六类养料如何回到域

| **养料**   | **进入域的方式**                           | **改变什么**                      | **不能自动改变什么**        |
|------------|--------------------------------------------|-----------------------------------|-----------------------------|
| 产品       | 安装/引用 Offering 与 Capability Module    | Action Cone、可交付能力           | Truth、Reputation           |
| 交易       | 参与 Engagement 与 Milestone               | 经历、关系、数据和潜在 Outcome    | 需求已解决、信誉已提高      |
| 数据       | 生成或授权 Data Asset                      | 记忆、洞察和决策输入              | 所有权、可复用性            |
| 知识       | 安装、复用、fork 或内化 Knowledge Module   | 知识视界、能力候选和行动方法      | 已证明能力、已验证结果      |
| Skill/工具 | 安装 Skill、连接 Tool/Model、执行 Workflow | Action Cone、生产效率和可交付范围 | 结果真实性、执行授权        |
| 资本/贡献  | 收入、额度、分成、贡献份额和使用权         | 可行动资源、投资能力和收益权      | Reputation、Truth、公共权力 |

只有事件、结构化 Claim、Evidence 和合法的状态迁移才能把“吸收养料”转化为真实成长。

### 12.6 能力沉淀与产品化

域在真实任务中反复使用的操作步骤，可以从 Workflow Candidate 逐步沉淀为 SkillEntity；Skill 与 Tool、知识、数据、交付模板组合后，可以形成 ProductEntity；产品持续生成且达到授权、质量与复用要求的数据，可以进一步发布为 DataProductEntity。整个进化过程保存来源、贡献、版本、依赖、成本、Outcome 和许可，防止平台把个人或企业的生产经验无偿吞没。

### 12.7 价值沉淀与再投入

收入、分成、贡献权、平台额度和外部支付属于不同资产类型。域可以把合法收益重新投入 Skill、工具、数据、合作和探索，扩大 Action Cone；但资本只能扩大可行动空间，不能购买 verified Truth、强行改变 Reputation 或绕过 Rule Domain。

# 第三篇 可信世界、行业演化与未来

## 第十三章 恒域世界通用可信网络

### 13.0 信任对象必须分开

平台信任、域主身份信任、数据来源信任、Evidence Authenticity、Claim Support、能力信任、项目履约信任、交易信用和行业规则合法性是不同对象。恒域世界不得把它们压成一个全局总分。

域主进入系统的信任阶梯为：

    域主声明 → 系统观察 → 对手方确认 → 证据支持
    → 第三方验证 → 项目结果验证 → 多次真实履约 → 分场景信誉

每个层级保存来源、适用世界、适用场景、有效期、撤回与争议状态。信誉必须回答“在什么能力、什么项目类型、什么时间窗口和什么证据下可信”，不能回答抽象的“这个域是不是好”。

### 13.1 三层验证冻结

    Evidence Authenticity ≠ Claim Support ≠ World Binding Validity

- Evidence：来源和内容是否真实；

- EvidenceClaim：证据是否支持一个结构化主张；

- Binding：主张能否映射到指定 World Concept。

### 13.2 Trust Passport

每个域可生成可信护照视图，展示身份、能力 Claim、Evidence、verified Outcome、认证、争议、撤销和信誉分量。它不是一次性证书，也不能用单一总分替代证据链。

可信护照属于域主可查看、解释和导出的派生视图。域主可以纠错和申诉；平台不得把未公开的私有证据暴露给观察者，也不得因域主退出而伪装成从未发生过的账务或争议历史。

### 13.3 信任传播边界

- 被 verified 企业包含的产品不会自动 verified；

- 付款不会自动增加信誉；

- Connection accepted/completed 不等于需求解决；

- Knowledge 被大量阅读不等于其主张真实；

- World Projection 不得提高来源域的 truth_status；

- synthetic/observed 不得静默进入 production baseline。

- 平台自营服务不能由平台同一利益角色完成 Claim 验证；

- 一个世界中的信誉不能无条件复制到另一个世界；

- 域主声明可启动核验流程，但不能直接成为 verified production 信用。

## 第十四章 恒域世界需求、项目与价值网络

### 14.1 Demand creates Connection

需求由 Actor、Scenario、Objective、Pain、Existing Solution 和 Missing Capability 组成。高分候选只是待解释、待验证的 ConnectionCandidate，不是自动推荐。

### 14.2 Connection becomes Engagement

ConnectionCandidate 经过资格、信任、双方意愿和人工决策后，可以创建 Agreement 与 Engagement。只有 Engagement 承载真实交付、责任、里程碑与 Outcome。

### 14.3 价值分配

每次 Engagement 记录：谁提供什么、谁贡献什么、谁承担风险、谁获得什么、哪些资产被许可、哪些结果已验证。V10.0 的 Economic & Ledger Engine 只结算已定义、已授权的价值关系，不反过来定义价值，也不允许支付事件直接升级 Truth、Outcome 或 Reputation。

## 第十五章 域本位世界（Realm-Centric World）与行业形成

### 15.1 行业世界与域视界必须分开

行业世界（Industry World；现有代码 `WorldEntity`）是带 Context/Rule Facet 的群落域或镜像域：它封装由域主共同确认的概念、规则、成员关系、环境维度、投影和状态，具有版本与事件历史。域视界（Realm World；现有代码 `EntityWorld`）是以某一 `observer_entity_id` 为原点的局部投影。前者提供共享语义与治理语境，后者回答“这个域此刻看见什么、受什么影响、能做什么”。

行业世界不拥有来源域，也不能把加入世界解释成放弃数据和主体权利。个人、企业、品牌和产品可以同时进入多个行业世界，并在不同世界中拥有不同角色、规则、权限和信誉解释。

### 15.2 两个真实行业赛道与实现状态

恒域世界-GEO 与恒域世界-科技特长生都是现实行业赛道，不因当前数据库中是否存在 synthetic fixture 而改变。行业真实性、世界契约状态和数据真实性必须分开：

| **对象**            | **现实定位**                 | **当前工程定位**                                                        | **进入 production 的条件**                              |
|---------------------|------------------------------|-------------------------------------------------------------------------|---------------------------------------------------------|
| 恒域世界-GEO        | 首个产品世界与优先商业验证场 | 已有 C6—C8 基础，需按域主价值链重定向                                   | 真实 GEO 域主、自有数据、项目、交付和 verified Outcome  |
| 恒域世界-科技特长生 | 可并列发展的真实行业世界     | `edu_tech_admission` 当前仅是 World Contract 的 draft/synthetic fixture | 真实学生/家长/学校/机构等域主、合法授权、真实需求与证据 |

`synthetic` 只描述某条测试数据或快照的真实性，不得被写成“科技特长生行业是虚构的”。同理，拥有真实行业名称也不意味着当前测试数据已经 verified。

### 15.3 行业世界基因（World Genome）

每个 WorldEntity 的 Genome 版本化定义：Concept、Relation、Role、Dimension Extension、Variable Definition、Environment Channel、Evidence Requirement、Binding Rule、Projection Rule、State Aggregation、Gap Rule 和 Forecast Feature。已发布版本不可修改。

### 15.4 行业概念究竟从哪里来

垂直行业概念不应由开发者、YAML、平台创始人或 LLM 凭空决定。开发者只能实现表达能力，AI 只能发现和整理候选，最终生产语义必须有现实来源和域主治理。概念来源必须分类并记录：

1.  Participant Vocabulary：参与域在真实需求、产品、项目和交付中反复使用的术语；

2.  Evidence-backed Facts：EvidenceClaim 及 verified Outcome 能支持的对象、能力与关系；

3.  External Standard：专业机构、法规、标准、学术或开放词汇，必须保存来源和版本；

4.  Operational Necessity：为实现交易、授权、交付、审计或治理而必需的平台概念；

5.  Model Candidate：AI 或聚类发现的候选术语，只能进入 candidate/synthetic，不能直接发布。

Concept 生命周期为 `observed term → concept candidate → evidence review → domain-owner review → trial use → versioned publish → usage monitoring → revise/merge/deprecate`。每个概念保存 `provenance_type / source_refs / proposed_by / represented_domain / reviewed_by / conflict_disclosure / decision_reason / effective_version`。

平台可以提供基础通用概念，如身份、授权、项目、交付、证据、结果、支付和争议；这些是跨行业运行协议。GEO 排名因子、科技特长生资格判断、行业服务标准等业务概念必须由相应世界的真实域主和权威来源共同确认。

### 15.5 五张世界镜头

1.  生态位置地图：域是谁、在哪里、与谁相关；

2.  成长能力地图：域缺什么、怎样获得能力与信任；

3.  商业价值地图：谁付钱、买什么、谁创造和获得价值；

4.  区域生态地图：区域主体、资源、政策、供需和机会；

5.  未来演化地图：展示信号、场景、概率和假设，不把预测画成事实。

### 15.6 行业不是分类，而是形成中的 CollectiveEntity

<img src="media/04_domain_owner_industry_loop.png" alt="真实域主与真实项目驱动行业形成闭环" />

真实域主与真实项目驱动行业形成闭环

IndustryConcept 只是分类词；IndustryEntity 才是由真实域、关系、事件和规则形成的产业共同体；IndustryWorld 是观察和解释该共同体的版本化语义镜头。三者不能混为一张 industry 表。

一个行业只有同时出现以下结构，才开始从“概念标签”变成真实 IndustryEntity：

1.  一组持续、重复且可识别的共同问题或需求；

2.  能够响应这些需求的能力、产品、服务与资源供给；

3.  多次真实 Engagement、交付、交易和结果；

4.  逐渐稳定的角色分工、上下游关系和价值分配；

5.  被参与者共同使用的术语、标准、流程和评价方式；

6.  能够验证身份、能力、产品和结果的信任机制；

7.  人才、资本、数据、知识与新进入者的持续流入；

8.  即使单个企业退出，网络仍能够继续运转和产生新域。

因此，平台不能因为配置文件里写了一个行业名称，就声称该行业已经真实存在；它只能先建立 IndustryConcept 或 synthetic Industry Fixture。

### 15.7 行业形成生命周期

    signal → emerging → forming → established → expanding
                                     ↘ transforming → recombining
                                     ↘ declining / dormant

- signal：出现零散需求、技术、政策或事件信号，尚未形成稳定网络；

- emerging：出现多个互相感知的参与域与早期产品；

- forming：供需、交易、角色和语言开始重复，边界仍不稳定；

- established：价值链、角色、信任与复用机制可以持续重现；

- expanding：域、区域、产品和需求快速扩张；

- transforming：技术、规则或需求变化正在改写原结构；

- recombining：原行业域与其他行业域拆分、合并或形成新行业；

- declining / dormant：需求和价值交换持续萎缩，但历史与资产保留。

行业状态是带来源的 MirrorEntity / Industry Expression，不是永久标签，也不能由单一规模分数决定。

### 15.8 Industry Formation Engine

行业形成引擎从 Universal Fact Layer 读取域和事件，形成以下结构性观察：

- Demand recurrence：相似场景、目标和痛点是否持续出现；

- Supply formation：能力与 Offering 是否形成多样化供给；

- Engagement density：真实项目和交易是否重复发生；

- Outcome evidence：是否存在可验证结果而非宣传；

- Role specialization：是否出现稳定的上游、基础设施、工具、服务、认证与需求方角色；

- Language convergence：参与者是否逐步采用共同概念和接口；

- Trust infrastructure：Evidence、标准、认证、争议和信誉机制是否形成；

- Asset accumulation：数据、知识、案例和方法能否复用；

- Reproduction capacity：新人能否学习、进入、获得资源并完成第一笔价值交换；

- Resilience：单个关键域退出后，网络是否仍能运行。

还必须观测域本位动力：多个域的 Horizon 是否开始重叠，Orientation 是否对共同目标收敛，Influence 通道是否稳定，环境扰动是否导致新角色、新模块与新交易模式。行业的形成是许多 EntityWorld 反复交叠后的稳定模式，不是平台从顶层画出的树形目录。

引擎输出 evidence-backed signals、unknown、excluded、formation stage candidate 和 source manifest，不自动宣布“新行业成立”。IndustryEntity 的认领、命名、边界和 production 发布必须经过行业参与者与治理流程确认。

### 15.9 行业形成事件

IndustrySignalObserved、CommonDemandClustered、RoleEmerged、ValueChainStabilized、StandardProposed、StandardAdopted、TrustInstitutionFormed、IndustryPublished、IndustryBoundaryChanged、IndustrySplit、IndustryMerged 和 IndustryDormant 等事件构成行业自己的 Timeline。

行业拆分、合并或改名不重写历史。新 IndustryEntity 通过 derives_from、split_from、merged_from 和 overlaps_with 保存谱系。

### 15.10 GEO 产业自身的形成

geo_ecosystem 必须用上述标准证明自己：AI 搜索可见度需求是否重复出现，工具、内容基础设施、服务商、测量认证、企业需求方和专家是否形成稳定角色，是否存在真实 Engagement 与 Outcome，术语和方法是否开始收敛，新参与者能否进入并创造价值。

恒域世界不只描绘一个已经完成的 GEO 行业，也要记录 GEO 产业从 signal、emerging 到 forming 的真实形成过程。这将成为未来复制其他垂直行业时最有价值的产业形成知识。

恒域世界-GEO 的发起人同时可能是平台发起人、GEO 域主、品牌方、服务方和工具创造者。这些角色可以共同启动试点，但不得以发起身份替代其他域主，不得把自己的方法直接发布为行业规则，也不得让自营项目跳过独立验证。

### 15.11 恒域世界-{行业}复制与演化协议

<img src="media/05_shell_worlds_tools.png" alt="恒域世界行业壳加载多个行业世界并连接外部工具" />

恒域世界行业壳加载多个行业世界并连接外部工具

每个行业的基础域类型、证据要求、角色和交易结构不同，但不从空白开始，也不能把某个行业整库复制。复制单位分为四层：

1.  **通用域内核（Universal Entity Kernel）：** 身份、控制、事件、状态、来源、权限、账本、模块与谱系，所有行业共享；

2.  **通用世界契约（Universal World Contract）：** 版本、Concept、Relation、Binding、Projection、State、Gap、Rule 和发布不可变；

3.  **行业基因包（Industry Genome Pack）：** 经相应行业域主验证的概念、角色、能力、需求、产品、证据要求、环境维度、规则、指标和连接器；

4.  **行业事实实例（Industry Fact Instance）：** 真实参与者、交易、项目、结果和历史，只属于该行业事实层，禁止复制。

新行业的派生顺序：

    一组真实域主提出真实行业需求
    → 选择结构最相似的已验证 Industry Genome
    → 复制为 draft / synthetic 分支
    → 计算概念、角色、能力、流程和规则差异
    → 采集新行业域主语言与真实 Evidence
    → 域主治理确认 Concept / Relation / Evidence Requirement
    → 用最小真实域闭环验证
    → 发布不可变 World Version
    → 持续观察行业形成与版本演化

行业相似度只能用于选取“从哪里开始改”，不能决定“什么是真的”。相似度建议拆为需求结构、角色结构、能力结构、交付流程、证据结构、规则强度、资产形态和价值网络八个向量；任何综合相似度都必须展示分量和来源，不作为行业排名。

一个新行业只有完成以下最小闭环才允许进入 production：至少三个相互独立且利益不同的真实域主、一个已认领真实封装域、一个 verified 身份或能力 Claim、一个真实 Demand、一个合格 Connection、一个 Agreement/Project、一项实际交付和一个可验证 Outcome。若只有一个发起人和测试数据，只能称为行业候选世界，不能宣称形成了行业共识。

### 15.12 恒域世界-GEO 的行业基因包

恒域世界-GEO 的初始域包括：企业、品牌、个人专家、GEO 服务商、内容生产者、工具、模型、AI 搜索平台、数据源、产品、Skill、项目、需求、证据、标准、机构、政府与区域。它的初始角色包括需求方、技术基础设施、内容基础设施、工具方、策略服务方、测量认证方、渠道、交付方、研究者和治理者。

恒域世界-GEO 的第一真实价值循环不是科技特长生，而是：

    企业出现 AI 搜索可见度或可信引用需求
    → 系统诊断其身份、内容、证据、竞争与能力缺口
    → 生成可解释改进路径
    → 企业自行或连接服务商、Skill、工具执行
    → 形成内容、知识、发布、引用、线索或业务结果
    → Evidence / Claim / Outcome 验证
    → 企业、服务商和平台沉淀数据、能力、案例与信誉

恒域世界-科技特长生不是 GEO 的子行业，也不是为了演示而虚构的赛道。它共享通用域内核，但必须由该赛道的真实域主重新确认角色、能力、证据、合规、未成年人授权、交易与结果规则，不能复制 GEO 事实、信誉或业务标准。

## 第十六章 Future Engine：可预知未来但不伪造未来

### 16.1 六层未来能力

| **层级** | **能力**           | **输出域**                       |
|----------|--------------------|----------------------------------|
| F0       | 历史重放           | Timeline / Story                 |
| F1       | 当前状态估计       | Estimated State Mirror           |
| F2       | 趋势与信号检测     | Signal Entity                    |
| F3       | 未来事件与关系预测 | Forecast Entity                  |
| F4       | 场景与反事实推演   | Scenario / Counterfactual Entity |
| F5       | 行动规划与资源配置 | Recommendation / Plan Entity     |

F0–F5 不是必然升级的成熟度分数。系统可以在某个域/某个维度上只做 F1，在另一个维度上进行 F4；能力范围必须随数据、环境可观测性与风险改变。

### 16.2 FutureEntity 家族

- IntentEntity：主体主动表达想去哪里；

- PlanEntity：已经承诺的步骤和资源；

- ScenarioEntity：一组一致假设下的可能世界；

- ForecastEntity：某事件或状态在时间窗口内的概率；

- CounterfactualEntity：如果采取某行动可能发生什么；

- RecommendationEntity：基于目标、约束和证据的行动建议；

- HypothesisEntity：尚待未来数据验证的解释。

### 16.3 Possible Worlds：未来是分支而非一条线

每个 EntityWorld 可带有若干受治理的 Possible World，每个分支包含：环境假设、扰动变量、可控变量、域向性、计划行动、可能影响、目标变量区间、概率/信心、不适用条件与 source manifest。

Scenario 只说明“在这组假设下可能怎样”；Forecast 才对某个可验证目标提供时间范围和概率；Recommendation 则必须回到域的 Action Cone。三者不得混为一段 AI 文字。

### 16.4 预测完整性

每个 ForecastEntity 必须记录：observer、target node/variable、dimension、environment assumptions、orientation assumptions、horizon、as_of、features、model_version、training_window、source_manifest、probability、confidence_interval、applicability、generated_at 和 calibration_status。

### 16.5 未来校准闭环

当时间窗口结束，系统生成 ForecastEvaluation Event，对比预测与真实结果，记录命中、偏差、缺失因素和适用范围。模型只因长期校准表现获得晋级，不因单次“看起来正确”进入生产。

### 16.6 预测禁区

- 数据不足时返回 unknown，不强行给概率；

- 相关性不得伪装成因果；

- 对个人或企业的高影响预测必须可解释并允许申诉；

- AI 文本不能成为预测依据的唯一来源；

- 未来域永远不能进入 verified fact baseline。

## 第十七章 自我成长与自我进化

### 17.1 四种进化

1.  Entity Evolution：域通过事件、吸收、释放和价值交换改变自身；

2.  Knowledge Evolution：经验通过复用和结果反馈迭代为更可靠知识；

3.  World Evolution：概念、关系、规则和 Gap 随事实变化发布新版本；

4.  System Evolution：模型、权重、Agent 流程和产品配置经验证后升级。

还需区分 Module Evolution 和 Genome Evolution：前者改变可安装功能契约，后者改变类型结构和不变量。一个域因学习安装知识模块，不等于整类人或企业的 Genome 被系统自动改写。

### 17.2 Governed Evolution Pipeline

    Observed Pattern
    → Evolution Candidate
    → Evidence Review
    → Simulation / Shadow Run
    → Human Approval
    → Versioned Release
    → Production Monitoring
    → Calibration / Rollback

系统可以自动发现候选、生成解释、执行仿真和监测效果，但不能自动把候选规则发布到 production，也不能自动提高 Evidence、Claim、Outcome 或 Reputation 的真实性等级。

### 17.3 Evolution Memory

每次规则演化保存：旧版本、新版本、触发信号、假设、审批者、测试集、影响范围、效果、回滚条件和实际结果。失败的演化同样是知识，不应被删除。

## 第十八章 配置化架构：Registry 系统

### 18.1 配置对象

以下能力必须通过 YAML/数据库配置与版本管理实现：

- Entity Archetype 与 Form 约束；

- Entity Module Contract、依赖、冲突、安装与迁移；

- Facet Schema 与必填字段；

- Variable Definition、Dimension Schema 与单位；

- 生命周期与状态机；

- Evidence Requirement；

- Offering、Demand、Engagement 和 Outcome 流程；

- World Ontology、Binding、Projection、Gap 与 Forecast Feature；

- 评分分量、阈值和不适用条件；

- Agent Role、Tool、数据权限、审批和预算；

- Skill/Workflow Contract、Model Provider、Connector、Sandbox、Evaluation 与成本；

- Rule Domain、Policy、Role、Permission、Obligation、Sanction、Exit 与 Appeal；

- Asset Unit、Order、Settlement、Revenue Share、Usage Meter 和市场机制；

- Quest、WorldInstance、Party/Guild、XP、Achievement、Reward 与 Season；

- Data Product schema、license、purpose、SLA、distribution 与 revocation；

- UI Entity View 与行业模板。

### 18.2 八个核心 Registry

1.  Genome Registry：定义域类型、Form 约束和 Kernel Invariants；

2.  Module Registry：定义功能模块、依赖、事件、Facet 和安装规则；

3.  Dimension Registry：定义变量、维度、单位、量表与映射；

4.  World Registry：定义概念、角色、关系、证据需求、环境通道和投影。

5.  Policy Registry：定义 Constitution、Rule Domain、Policy、权限求交、义务、制裁与申诉；

6.  Capability Registry：定义 Skill、Tool、Model、Workflow、Connector、依赖、测试、风险与发布；

7.  Economic Registry：定义 Asset Unit、Ledger Rule、计费、分账、结算、退款与市场模板；

8.  Interaction Registry：定义 Quest、WorldInstance、Party/Guild、XP、Achievement、Reward 与 Season。

Registry 之间通过稳定 code 和版本引用，禁止互相复制 schema。

### 18.3 配置版本纪律

所有生产配置固化 version、hash、publisher、published_at、effective_from、compatibility、migration 和 rollback_target。相同规范化配置产生一致 hash；发布后修改必须创建新版本。

### 18.4 可配置不等于无约束

Entity ID、Event Ledger 不可静默改写、Evidence-Claim-Binding 分离、verified Outcome 才能影响信誉、Future 不等于 Fact、宪章优先、五账分离和双重记账等法则属于 Kernel Invariants，不能被行业、域、游戏、Skill 或商业配置关闭。

# 第四篇 智能生产、规则治理、金融与游戏体验

## 第十九章 AI 与 Agent 架构

AI 在恒域世界中是能力，不是统治者、事实源、行业权威或最终责任主体。平台的目标不是再做一个通用聊天机器人，而是让任意合规模型在域主授权、行业语境、项目责任和可信数据链中发挥作用。

### 19.1 AI 的五种职责

1.  Perception：从授权来源发现候选域、关系、事件和 Claim；

2.  Interpretation：解释 Entity State、Gap、来源链和变化；

3.  Planning：生成 Growth Path、Scenario、Recommendation 和任务计划；

4.  Execution：在授权范围内调用工具、编排流程和创建草稿；

5.  Reflection：复盘 Engagement、提炼 Knowledge Candidate、校准 Forecast。

AI 运行在 Entity Module 之上，不绕过 Entity Kernel。Perception 产生 candidate observation，Interpretation 产生带 source manifest 的 MirrorEntity，Planning 只能在 Action Cone 内创建 Plan/Recommendation，Execution 必须通过 Agent Module 的权限和审批接口。

### 19.2 GPT 与 Entity Universe 的边界

GPT 的 Token、Embedding、Attention 和模型参数属于认知计算层，不直接成为生产域事实。模型输出首先是 synthetic 或 candidate；只有外部 Evidence、结构化 Claim、责任主体与验证流程满足条件，才能进入更高 Truth State。

### 19.3 AgentEntity

当一个 Agent 拥有稳定身份、Owner、Role、Tool 权限、预算、记忆、事件史和责任边界时，它可以注册为 CapsuleEntity / Agentic。Agent 生成的任何域都必须追溯到 Agent、Owner、模型、Prompt/Rule、Tool Call 和 Source。

### 19.4 不建立虚拟公司幻觉

优先复用现有 Agent、TaskExecutor、Tool 和 Memory。只有出现独立权限、独立责任、独立数据边界或独立长期目标时才新增 Agent。Agent 数量不是智能指标。

### 19.5 AI 不可替代性筛选

任何拟进入平台核心的 AI 功能都先接受七问：是否需要真实身份/授权；是否需要多方协作；是否依赖长期历史/信誉；是否涉及权利、责任或价值；是否需要跨工具编排；是否产生 verified Outcome 或可复用资产；是否通过真实活动完善行业地图。若均否，优先由外部模型或普通 Skill 完成，不建设重型平台功能。

## 第二十章 Skill、工具、模型与数据生态

恒域世界不只描述产业世界，还必须参与产业生产。系统既能自研和发布工具、Skill、Workflow 与数据产品，也能连接 GPT、豆包、Codex、MCP、外部 SaaS、数据库和未来模型；但“能调用”只是接入层，“在谁的授权下、为哪个真实任务、使用什么数据、受什么行业规则约束、产生什么结果、责任归谁”才是架构层。

### 20.1 能力域命名

| **域**                 | **正式定义**                                         | **典型实例**                     |
|------------------------|------------------------------------------------------|----------------------------------|
| ModelEntity            | 提供推理、生成、识别、预测或多模态能力的版本化执行器 | GPT、豆包、行业模型              |
| ToolEntity             | 可被调用的原子执行能力                               | 搜索、抓取、制图、代码执行、发布 |
| SkillEntity            | 完成一类工作的可复用方法契约                         | GEO 诊断、内容规划、项目评估     |
| WorkflowEntity         | 多个 Skill、Tool、Agent、数据与审批的编排            | 企业 GEO 增长闭环                |
| AgentEntity            | 在 Owner 授权和预算内组织行动的代理主体              | 研究 Agent、Codex 编码 Agent     |
| ConnectorEntity        | 恒域世界与外部模型、工具、平台和数据源的受控连接     | MCP、REST、Webhook、数据库适配器 |
| ArtifactEntity         | 一次运行产生的具体成果                               | 报告、内容、代码、设计、数据集   |
| ProductEntity          | 具有用户、版本、价格、交付标准和责任边界的价值封装   | GEO 监测产品、咨询产品           |
| DataProductEntity      | 可授权、订阅、交换和撤回的数据输出                   | 行业需求指数、域验证 API         |
| DecisionProposalEntity | 带来源、假设、备选项和风险的决策候选                 | 产品优先级、资源配置建议         |

这些名称是 Form/Facet/Contract 的组合，不要求每一种都建立孤立真相表。Tool、Skill 和 Workflow 通常先以 ModuleEntity 存在；形成独立控制、客户、责任和生命周期后，可以升级为 CapsuleEntity。

### 20.2 Skill Contract

正式 Skill 不是提示词别名，至少包含：

    skill_id / skill_version / publisher / license
    purpose / trigger / input_schema / output_schema
    preconditions / required_tools / allowed_models
    required_data / authority_scope / decision_scope
    execution_steps / stop_conditions / approval_points
    cost_policy / timeout / retry / idempotency
    evaluation_rules / test_cases / risk_level
    truth_boundary / privacy_policy / data_destination
    compatibility / rollback_version / config_hash

Skill 描述“如何可靠完成一类工作”；Tool 负责原子动作；Model 提供认知计算；Agent 负责在授权内选择和编排；Workflow 固化跨 Skill 流程；Product 对用户承担交付责任。任何一层都不得偷渡另一层的权利。

### 20.3 Capability Runtime & Skill Foundry

能力运行时负责：Skill/Tool/Model 注册、依赖解析、权限与沙箱、模型路由、预算与配额、执行 Trace、人工审批、失败补偿、Outcome 评估和版本回滚。

Skill Foundry 负责把真实工作沉淀为生产力：

    重复任务或高频 Demand
    → Workflow/Skill Candidate
    → Codex、开发者或 Agent 实现
    → 静态检查与自动测试
    → simulation / shadow run
    → 人工或治理审批
    → versioned release
    → 域安装与生产执行
    → Outcome、成本和风险评估
    → 升级、降级、合并、fork 或 rollback

系统可以自己发现候选、生成代码、编写测试和提出升级，但不能自动获得生产权限，也不能因为一次执行成功就把 Skill 标记为可靠或把结果标记为 verified。

### 20.4 模型与工具网关

架构对供应商保持中立。每个 ModelProviderAdapter 声明 capability、context window、tool support、latency、cost、region、data retention、training policy、availability 和 fallback；每个 ToolConnector 声明认证方式、数据范围、读写能力、幂等性、风险级别、速率限制和撤销方式。

GPT、豆包和未来模型是可替换 ModelEntity；Codex 更适合作为具备工作区、代码、测试和审查能力的软件工程 Agent/Tool 接入，而不是被简化为普通文本模型。MCP、REST、SDK、消息流和文件交换都通过 ConnectorEntity 进入统一 Trace。

每次调用至少固化：provider、endpoint、model/tool version、skill/workflow version、prompt/rule hash、input/output artifact refs、tool calls、token/resource usage、cost、actor、authority、approval、started/ended_at、error 和 data destination。

### 20.5 决策完整性

Skill 可以生产分析、预测和 DecisionProposal，但不能自动拥有决策权。正式决策分为：

    Decision Context → Options → Evidence / Assumptions
    → Decision Proposal → Authorized Approval
    → Decision Execution → Outcome → Review

高风险决策必须声明决策主体、授权来源、影响范围、可逆性、审批门槛和执行窗口。AI 输出属于 candidate/synthetic intelligence；没有责任主体、Evidence 与授权，不得直接写入生产事实、账本或不可逆外部系统。

### 20.6 Data Product Protocol

经授权的恒域世界数据可以服务其他平台、模型和域主，但不能直接暴露内部数据库，也不能把“平台可访问”误解为“平台拥有”。正式 DataProductEntity 至少携带：

    data_product_id / owner / publisher
    schema_version / world_version / as_of
    source_manifest_hash / truth_distribution
    coverage / unknown / excluded / freshness
    privacy_level / license / allowed_purpose
    training_allowed / redistribution_allowed
    revocation_policy / retention / price / sla
    delivery_channel / usage_meter / audit_endpoint

数据开放分五级：Private Vault、Authorized Sharing、Ecosystem Data、Licensed Data Product、Public Commons。个人私域数据、受限 Evidence、商业秘密和内部决策记录默认不得用于外部模型训练；训练、缓存和二次分发必须获得独立许可。

可形成的对外产品包括：域身份与资质验证 API、GEO 行业能力图谱、需求与供给缺口、产品与服务知识图谱、行业环境信号、可信内容接口、模型 RAG 数据源、行业评测集与基准集。

### 20.7 Skill Economy 与贡献归因

Skill、Tool、Workflow、Product 和 Data Product 都可以发布、许可、订阅和计费。每次使用记录创作者、维护者、数据贡献者、模型/工具成本、平台服务、实际 Outcome 与退款/争议，使 Economic & Ledger Engine 能按规则分账。

Skill 的安装量、调用量和收入不等于质量；质量来自适用场景、测试、失败率、真实 Outcome、风险和用户反馈。贡献收益也不自动成为 Reputation，避免资本和流量反向污染 Trust Foundation。

### 20.8 恒域世界成为行业级 AI 运行时

一个真实 Demand 可以调用多个内置或外部 Skill、模型和工具生成内容、代码、设计、产品、知识、数据与决策候选；这些成果经域主确认、Evidence、Outcome、许可和贡献治理后重新进入域。平台不要求所有工具由公司开发，每个行业世界、组织域和域主都可以拥有自己的工具目录、白名单、预算、数据边界和运行策略。

系统的数据也可以通过 Data Product、API、MCP、订阅或受控导出提供给其他平台。输出必须携带来源、truth distribution、许可、用途、时效、撤回、训练许可和使用计量；域主能知道谁在什么目的下使用了什么数据，并按协议获得归因或收益。

恒域世界提升 AI 应用到行业高度的关键，是把一次性生成变成“域主上下文 → 行业规则 → 工具编排 → 项目交付 → 结果验证 → 信誉/资产沉淀”的长期闭环。

## 第二十一章 规则域、宪章与嵌套治理

“谁进入谁的合法治理范围，就遵守谁已公开且有效的规则”被工程化为 Rule Domain Protocol。它借鉴国家、组织、社区、市场、游戏世界和计算机权限系统的共同结构，但平台不是现实国家，域也不是可以凌驾法律、合同和基本权利的任意主权体。域主自治来自真实控制、成员同意或合法授权，不来自平台授予的虚拟主权。

### 21.1 五级规则结构

| **层级**                     | **制定者**                                   | **主要内容**                                | **边界**                   |
|------------------------------|----------------------------------------------|---------------------------------------------|----------------------------|
| 恒域世界宪章（Constitution） | 公司承担法律责任并接受治理监督               | Truth、域主权利、安全、账本、来源、申诉底线 | 所有下级不可关闭           |
| 平台技术与安全标准           | 平台技术/安全/合规责任角色                   | 身份、数据、接口、交易、模型、审计、反滥用  | 不得包装成行业业务规则     |
| 世界/行业规则                | 具备代表性和资格的行业域主治理域             | 概念、角色、证据、准入、交付、行业标准候选  | 仅在该 World/版本有效      |
| Organization / Space Rule    | 企业、项目、市场、Collective、World Instance | 成员、任务、资源、协作、奖励与行为规则      | 仅约束合法进入者和受控资源 |
| Entity Policy                | 域 Controller                                | 自身数据、资产、Agent、工具、可见性和子域   | 不得扩张到无控制权对象     |

现实法律、监管和司法命令始终位于系统规则之上；恒域世界宪章只能约束平台内部实现及参与合同，不能宣称取代国家法律。

行业规则不得因为写入 YAML 就获得权威。正式共建流程为：

    真实项目暴露问题
    → 域主或机构提出规则候选
    → 披露代表身份与利益冲突
    → Evidence / 外部标准审查
    → 多方讨论与异议记录
    → observation / simulation / limited trial
    → 有权域主批准并发布不可变版本
    → 执行、监测、申诉、复核
    → 修订、废止或回滚

平台负责程序完整性、版本、权限、审计和技术执行；不因托管投票和配置而拥有行业规则内容。

### 21.2 RuleDomainEntity 与 PolicyEntity

RuleDomainEntity 是具有 scope、controller、members/resources、parent_domain、policy_bundle 和生命周期的治理空间。PolicyEntity 表达一组版本化规则：Permission、Prohibition、Obligation、Condition、Sanction、Remedy 和 Appeal Route。

    policy_id / version / issuer / authority_source
    domain_id / subjects / resources / actions
    effect: allow | deny | obligate
    conditions / effective_from / expires_at
    priority / parent_policy / legal_basis
    sanction / remedy / appeal_route
    config_hash / published_at / supersedes

### 21.3 进入、接受、退出与继承

域通过 EnterDomain、JoinOrganization、AcceptAgreement、InstallModule、AccessResource 或 StartQuest 进入规则域。系统必须在进入前展示适用规则、版本、重要义务、数据用途、费用、退出条件和申诉渠道，并记录 PolicyAccepted/PolicyBound 事件。

规则修改只能生成新版本。对存续 Agreement 或已开始 Quest 是否适用新规则，必须由兼容策略和双方协议决定；禁止静默追溯生效。退出规则域不会删除已经合法发生的事件、义务、欠款、许可和审计记录。

### 21.4 权限求交与冲突决议

有效权限采用最小授权：

    effective_permission
    = subject_authority
    ∩ resource_policy
    ∩ active_rule_domains
    ∩ legal_and_constitutional_constraints

任何适用的 explicit deny 优先于 allow；所有适用 obligation 必须满足；未明确授权的高风险动作默认拒绝。下级域可以收紧权限，不能扩大上级禁止事项。只有持有明确 override authority 的上级治理或争议裁决流程，才能撤销局部禁止。

### 21.5 域自治与子域生成

任何具备 Controller Facet 的域，都可以在其控制范围内制定 Entity Policy、创建子 Rule Domain、定义成员角色、任务、资源使用、Skill 白名单、数据边界和奖励方式。例如企业可以建立内部项目域，专家可以定义知识许可，Skill 发布者可以限定模型和数据用途，Collective 可以定义成员治理。

自治权来自真实控制、合同授权或上级委托，不来自“域存在”本身。域不能为不属于自己的人、资产、数据和关系单方面立法，也不能通过子域逃避上级规则。

### 21.6 执行、制裁与修复

Policy Decision 保存 request、actor、resource、action、context、applicable policy versions、decision、reason 和 trace。执行手段按风险递进：提示、要求补充义务、限流、暂停、撤销授权、冻结待结算资产、退出域、争议处理；任何影响 Reputation、资金或公开身份的动作都必须有事实依据、授权、通知和申诉路径。

规则执行事件不能直接伪造 Truth。违规事实经 Evidence/Claim 验证后，才能进入相应 Law/Trust 流程；域内惩罚、平台限制与跨域 Reputation 必须分开。

### 21.7 治理域也被治理

规则制定者、管理员、审核员和自动执法 Agent 都是受约束域。所有高风险规则发布、例外授权、冻结、处罚和资金处置必须记录 authority、reason、source facts、policy version、审批者和可复核 Trace。最高规则不是最高管理者的任意意志，而是对管理者同样有效的制度边界。

## 第二十二章 金融、账本与价值守恒

金融系统不是在 Marketplace 旁边增加一个 payment 表，而是为 Universe 建立价值守恒、权利分配、交易安全和经济记忆。它首先是受治理的记账与结算系统，不宣称自己是银行、证券交易所或法币发行机构。

### 22.1 五账分离

| **账本**                      | **记录什么**                                | **是否可转移** | **绝不能自动换成什么** |
|-------------------------------|---------------------------------------------|----------------|------------------------|
| Money / Credit Ledger         | 法币映射、平台额度、应收应付、托管和结算    | 依资产规则     | Truth、Reputation、XP  |
| Contribution / Royalty Ledger | 创作、数据、Skill、渠道、维护等贡献份额     | 依协议         | 所有权、真实性         |
| Trust / Reputation Ledger     | 经受控 Law Mutation 形成的信誉事件          | 不作为货币转让 | 余额、购买力           |
| XP / Achievement Ledger       | 学习、探索、任务和里程碑记录                | 默认不可转让   | 专业资质、法币、信誉   |
| Usage / Cost Ledger           | API、模型、工具、存储、算力、人工和资源成本 | 不作为货币流通 | 信誉、贡献、专业能力   |

Token/API Call、存储、算力和工具调用进入 Usage / Cost Ledger。它用于成本、预算、配额和单位 Outcome 成本核算，不因名称中有 token 就变成货币。

### 22.2 核心经济对象

- AssetUnitEntity：币种、平台额度、积分、资源单位或授权份额的定义；

- EconomicAccount：属于域、域或托管关系的账户；

- Ledger：同一资产类型和会计规则下的不可变账簿；

- Transfer / Posting：成对的借贷或价值转移；

- Hold / Escrow：待履约、待审核或待争议解决的冻结；

- Order / Quote / Invoice：购买意向、报价和应收凭据；

- Settlement / Payout：交付后结算和对外付款；

- RevenueShare / Royalty：按贡献、许可和协议分配收益；

- Refund / Chargeback / Adjustment：退款、撤销和纠错；

- Reconciliation：与支付渠道、银行、发票和内部事实对账。

### 22.3 账本不变量

1.  每个 Transfer 必须在同一 Ledger/Asset Unit 中同时产生等额相反的 debit 与 credit；

2.  已 posted 记录不可覆盖，只能通过反向或调整分录修复；

3.  所有写入必须使用 idempotency key、expected state 和唯一外部引用；

4.  pending 只能 post、void 或 expire，不能同时进入两个终态；

5.  余额限制、透支、冻结和限额在原子事务内验证；

6.  不同资产单位不得直接相加，兑换必须通过显式 Exchange/Conversion Agreement；

7.  账本事件必须关联 actor、authority、agreement/order、rule version 和审计时间；

8.  业务数据库、支付渠道与总账定期 reconciliation，差异不得静默抹平。

### 22.4 交易生命周期

    Demand / Offering
    → Quote / Order
    → Agreement / Rule Domain
    → Authorization / Hold / Escrow
    → Engagement / Milestones
    → Delivery / Outcome Claim
    → Acceptance / Dispute
    → Settlement / Revenue Share / Royalty
    → Invoice / Payout / Reconciliation

支付可以发生在交付前、里程碑、订阅周期或交付后，但支付时点不改变 Truth Boundary。Outcome 未 verified 时可以按合同结算，系统必须明确“合同接受”与“事实验证”的区别。

### 22.5 Skill、工具、数据和内容计费

支持一次性购买、订阅、按调用、按用量、按席位、按结果条件、授权费和收益分成。每次 SkillRun 可以拆解模型、工具、数据、人工、平台与创作者成本；DataProduct 使用记录 consumer、purpose、volume、license 和 expiry；内容、方法与代码复用记录来源和 Royalty Rule。

费用计算规则必须版本化并在执行前可知。模型成本变化可以触发新价格建议，但不得静默改变存续订单。高风险“按结果付费”必须定义可验证 Outcome、归因窗口和争议规则，防止系统用相关性冒充因果。

### 22.6 域发行的局部单位

域或 Rule Domain 可以在授权范围内创建 Local Credit、Point、Quota、Ticket 或 Contribution Unit，用于访问、奖励、投票、配额和内部结算。UnitDefinition 必须声明 issuer、scope、supply rule、transferability、expiry、redemption、reserve、legal classification 和 prohibited use。

任何可兑换法币、面向公众流通、承诺收益或具有金融属性的单位，都必须先完成法律与合规评估，并通过持牌支付/金融机构处理。平台不得把积分包装成存款、证券或未经许可的虚拟货币。

### 22.7 合规边界

法币保管、银行卡、跨境支付、KYC/AML、税务、发票和退款保护优先交给持牌外部 Provider；GEO 保存业务订单、授权、账本镜像、分配规则和 reconciliation，不自行承担未经批准的金融机构角色。隐私、财务数据和审计数据采用更严格 Rule Domain、最小权限、加密、保留期限和双人审批。

### 22.8 钱不能定义价值与信誉

付款只证明发生了支付；收入只证明获得了经济回报；高价只证明交易条件。它们可以成为域经历、商业能力和环境信号，但不能单独证明产品有效、Claim 真实、需求解决或主体可信。金融系统必须服务价值网络，不能反过来控制 Truth Foundation。

## 第二十三章 游戏化世界机制

恒域世界引擎 与游戏相似，不是因为要把产业做成娱乐，而是游戏长期解决了复杂世界中的探索、规则、角色、任务、协作、成长、资源、风险、奖励和叙事问题。V10.0 将其吸收为 World Interaction Protocol，而不是在页面上堆积分、徽章和排行榜。

### 23.1 游戏概念与真实产业对象映射

| **游戏概念**  | **恒域世界引擎 对象**                         | **真实含义**                         |
|---------------|-----------------------------------------------|--------------------------------------|
| 玩家/角色     | PersonEntity、OrganizationEntity、AgentEntity | 参与者与其不同世界身份               |
| 世界/地图     | WorldEntity、EntityWorld、Industry Map        | 可探索的语义、关系与环境空间         |
| 迷雾          | Entity Horizon / Access State                 | 尚不可见、不可理解或不可触达区域     |
| 任务 Quest    | Demand + Goal + Constraints + Acceptance      | 可验收的真实工作或成长任务           |
| 副本 Instance | WorldInstance / Engagement                    | 有时间、参与者、规则和资源边界的场景 |
| 组队 Party    | 临时 CollectiveEntity                         | 为任务组成的协作关系                 |
| 公会 Guild    | 稳定 CollectiveEntity / Organization          | 长期成员、治理和共同资产             |
| 技能树        | Capability/Skill Graph                        | 可学习、安装、验证和组合的能力路径   |
| 装备          | Tool、License、Dataset、Template              | 扩展 Action Cone 的资源              |
| NPC           | 授权 AgentEntity                              | 引导、执行、解释或服务的智能代理     |
| 经验 XP       | verified/observed Learning & Work Events      | 不同 Truth 下的成长经历              |
| 成就          | Milestone / Certification / Outcome           | 带条件、证据和版本的里程碑           |
| 金币/市场     | Economic Ledger / Marketplace                 | 价值计量、交易、拍卖和结算           |
| 赛季          | Time-boxed World/Rule Version                 | 阶段性规则、主题和目标，不覆盖历史   |
| 公共挑战      | Mission / Industry Challenge                  | 多域共同解决的产业问题               |

### 23.2 Quest Contract

正式 QuestEntity 至少包含：issuer、beneficiary、world/domain、objective、prerequisites、participants、required skills/tools、rules、milestones、acceptance criteria、evidence requirements、budget/reward、risk、start/end、failure/exit、appeal 和 outcome policy。

Quest 可以来自 DemandEvent、Growth Path、行业 Gap、学习目标、公共 Mission 或 Engagement。AI 可以把模糊需求拆成 Quest Candidate，但只有授权主体能够发布涉及真实人员、预算、外部行动或公开承诺的生产任务。

### 23.3 任务、组队与副本生命周期

    Discover → Inspect Rules/Requirements → Apply/Accept
    → Form Party / Allocate Roles → Equip Skill/Tool/Data
    → Execute Milestones → Produce Artifact/Delivery
    → Submit Evidence/Outcome → Review/Dispute
    → Reward/Settlement → Asset/Knowledge/XP
    → Reflection → Unlock New Horizon/Quest

WorldInstance 为一次项目、课程、竞赛、沙盘、采购或客户交付创建隔离环境：固定 World Version、Rule Bundle、参与者、数据、工具、预算和时间。实例结束后释放合法成果和事件，但不把 simulation 状态泄漏到 production。

### 23.4 成长、解锁与技能树

域的能力树由 prerequisites、学习、实践、EvidenceClaim、Outcome 和认证共同解锁。学习完成可以获得 observed XP；通过结构化考核可以形成 Certification Claim；在真实项目中形成 verified Outcome 后，才可能验证生产能力。任何付费只能购买学习资源或考试机会，不能直接购买能力状态。

解锁不是平台奖励幻觉，而是 Action Cone 的真实变化：获得新 Skill、Tool License、数据权限、协作资格、预算或 Rule Domain 准入后，域确实能采取此前不能采取的行动。

### 23.5 Mechanics、Dynamics 与 Experience

游戏机制按三层治理：Mechanics 是规则、资源、任务、奖励和状态机；Dynamics 是域在运行中形成的竞争、协作、交易、联盟和策略；Experience 是参与者感受到的探索、掌握、创造、归属、影响和成长。系统只能直接配置 Mechanics，必须通过仿真、行为数据和用户研究观察真实 Dynamics 与 Experience，禁止把预期体验写成事实。

### 23.6 拍卖、市场与公共任务

Offering、数据许可、稀缺专家时间和项目席位可以使用固定价、报价、招标、竞价、反向拍卖或协商机制。所有市场机制必须声明价格规则、信息披露、竞价时限、撤回、反作弊、关联关系和结算方式。公共 Mission 可以由平台、行业组织、企业或政府机构发布，多个 Party 提交方案，由透明标准和授权评审选择。

### 23.7 Agent 与动态世界

AgentEntity 可以承担引导者、任务拆解者、资源推荐者、模拟对手、测试者和世界管理员，但必须受 Rule Domain、预算、工具权限和 Truth Boundary 约束。Agent 可以根据 World State 动态生成 Quest Candidate、学习路径和组队建议，不能操纵真实用户、制造虚假稀缺、私自下注或自动处置资金。

### 23.8 禁止的游戏化

- 不用连续签到、焦虑倒计时和虚假稀缺绑架用户；

- 不做赌博式 Loot Box、未成年人金融化或不可解释随机奖励；

- 不以 Pay-to-Win 购买信誉、资质、排名或真实性；

- 不以单一排行榜羞辱个人或制造零和竞争；

- 不用刷量、点击、内容数量和 Agent 调用量冒充成长；

- 不让 XP、金币、贡献、信誉和真实货币自动互换；

- 不让失败任务永久污名化域，必须保留环境、难度、责任和申诉语境。

游戏机制的成功标准不是“更上瘾”，而是域更容易理解世界、找到位置、组成团队、完成真实任务、获得公平回报，并把经历沉淀为能力、知识、资产和故事。

统一域主页、身份认领、已安装 Module、过去/现在/未来、能力、产品、关系、资产、Environment、Orientation、Action Cone、Growth Path 和可信护照。它回答“我是谁、我处在什么环境、我可以怎样成长”。

### 24.2 品牌域与 AI 可见度增长工作台

品牌域组合身份、产品、内容、案例、引用、项目结果、客户确认和权利。工作台保留“导入域主自有数据 → AI 可见度检测 → 诊断内容/证据/能力缺口 → 选择内部或外部 AI/Skill → 生产与发布 → 引用和市场监测 → 需求与项目 → 结果验证 → 品牌信任与资产”的闭环。所有内容、引用、结果和能力回到域主控制的品牌域，而不是停留在独立工具数据库。

### 24.3 GEO 产业导航与未来情报系统

整合域本位生态图、产业价值链地图、商业赚钱地图、运营流程地图、区域环境图、影响通道图、行业形成 Timeline、World State、Gap、信号、Scenario 和 Forecast。同一张图可切换 `observer_entity_id`，回答“世界正在怎样影响我，我又能影响谁”。

### 24.4 GEO 价值网络与交易系统

整合 Demand、Offering、ConnectionCandidate、Agreement、Engagement、Quest、Milestone、Delivery、Outcome、Order、Escrow、Settlement 和 Marketplace Match。法币通道仍通过合规适配器接入，但经济账本与价值分配已成为核心。它回答“谁需要谁，怎样共同创造价值并公平结算”。

### 24.5 GEO 信任、数据与知识资产系统

整合 Evidence、Claim、Verification、Certification、Reputation、Entity Asset Account、Universe Data Commons、Knowledge Entity、许可、贡献和复用。它回答“为什么可信，积累了什么”。

### 24.6 GEO 能力、Skill 与开发者系统

提供 Skill Registry、Tool/Model Gateway、Workflow Builder、Agent Runtime、Skill Foundry、Developer Platform、Data Product API 和运行 Trace。域可以安装能力、创建工具、接入 GPT/豆包/Codex、发布 Skill 与数据产品，并按照 Outcome、使用和贡献获得收益。

### 24.7 GEO 世界参与与经济系统

把地图、探索、Quest、Party/Guild、WorldInstance、Achievement、Marketplace、Order、Ledger、Escrow、Settlement 和 Revenue Share 组合成真实世界参与闭环。它回答“我可以去哪里、参加什么、与谁组队、遵守什么规则、如何完成任务、获得什么并怎样继续成长”。

### 24.8 跨世界智能认知与治理工作台

原 GEO 智能认知中心不再作为与六大系统争夺入口的独立孤岛，而成为跨系统 Intelligence Plane，并提供域主、行业治理者和平台责任角色各自隔离的驾驶舱：统一 Context、Decision、Forecast、Agent、Rule、Prompt、Config、Evaluation、利益冲突与审计。

### 27.2 PostgreSQL First

第一阶段继续使用 PostgreSQL、SQLAlchemy 和 Alembic。域与关系使用规范化表、JSONB 扩展字段、递归 CTE 和必要索引；只有真实规模和查询证明关系遍历成为瓶颈后，才增加图数据库投影，不进行双写真相源。

### 27.3 Event + Snapshot

关键事件采用 append-only；Entity Expression、World State 和搜索索引采用可重建快照。快照发布后不可覆盖，来源变化时标记 stale 并生成新版本。

### 27.4 内容寻址与去重

可复制的 Data/Knowledge/Content Module 保存 canonical hash。相同内容可以物理去重，但身份、控制、许可和使用事件仍按 Entity 实例记录。

### 27.5 三层数据边界

1.  Universal Fact Layer：域、事件、Evidence、Claim、Engagement、Policy Decision、Capability Run、Ledger Posting 等可审计事实；

2.  Derived State Layer：Expression、Trajectory、EntityWorld、World Projection、State Snapshot 和 Gap；

3.  Intelligence Layer：Candidate、Estimated、Scenario、Forecast、Recommendation 和 Evolution Proposal。

三层物理上可在同一 PostgreSQL 实例，但必须通过 schema/table contract、truth/epistemic fields、写入权限与测试保持单向边界：派生层和智能层不能反向提升事实层 Truth。

## 第二十九章 权限、治理与安全

### 29.1 权利分离

Owner、Controller、Manager、Contributor、Holder、Licensee 和 Viewer 是不同关系。用户注册账号不能自动取得某个企业或产品域的所有权；认领必须经过身份和授权验证。

### 29.2 隐私与可撤回

个人域采用最小披露、目的限制、可见范围、保留期限和撤回机制。派生域必须处理来源撤回、许可到期和删除请求，但审计系统可以保留合规所需的不可逆摘要和撤销事件。

### 29.3 争议与修复

支持 Entity Claim 争议、Evidence 撤销、关系纠正、Outcome 申诉、控制权转移和预测异议。修复通过事件与版本完成，不删除历史来制造一致性。

### 29.4 规则制定权分离

Constitution Publisher、Policy Author、Domain Administrator、Enforcement Agent、Appeal Reviewer 和 Auditor 不应默认由同一主体兼任。涉及资金冻结、公开处罚、身份撤销和高风险数据访问时，至少需要职责分离、双人审批或独立复核。

公司经营者、平台发起人、行业发起人、自营服务方、工具创造者和规则召集人也必须分离。自营域进入连接候选、评测、认证、争议或规则表决时，系统必须显示利益冲突并采用独立验证、回避或外部复核。

### 29.5 模型、Skill 与工具安全

外部模型和工具默认最小权限、最小数据、短期凭证、沙箱执行和网络白名单。Skill 安装前检查 publisher、signature/hash、dependencies、requested permissions、data destination、risk 和 rollback；运行时限制预算、时间、文件/网络范围和可调用动作。Prompt injection、供应链依赖、数据外传和越权 Tool Call 必须进入专门审计。

### 29.6 金融与经济安全

Ledger 写入、退款、分账、人工调整、提现和 reconciliation 采用幂等、原子事务、不可变记录、权限分离和异常监控。支付凭证不进入普通业务日志；真实法币由合规 Provider 托管。任何余额展示都必须指向 ledger state，不从订单状态或前端缓存推算。

### 29.7 数据输出与外部训练

DataProduct 发布前进行来源、隐私、许可、匿名化、重识别风险和用途评估。消费者必须接受 allowed purpose、retention、redistribution、training 和 revocation 条款；一旦来源撤回或 source drift，系统能够停止新分发、通知消费者并发布新版本或撤销事件。

| P2 真实项目工作台       | P1 产生真实需求             | Demand→Plan→Tool/Skill Run→Milestone→Delivery→Outcome Claim    | 一项真实 GEO 项目全链可追溯，所有展示可回源          | 只记录聊天和生成数量           |
| P3 可信结果与成长       | P2 有交付和确认             | Evidence→Claim→Outcome Verification→Timeline→Growth/Trust      | 至少一个 verified Outcome；未验证事实严格隔离        | completed 自动等于成功/信誉    |
| P4 连接与多方协作       | P2/P3 证明单域价值          | Capability/Offering、Connection、Agreement、Party、权限与争议  | 两个独立域主完成一次合作，责任、退出和贡献可审计     | 黑箱推荐、平台自营优待         |
| P5 交易与合规结算       | P4 有稳定里程碑与争议       | Order、持牌支付适配、五账、托管、结算、分账、退款、对账        | 双重记账平衡、幂等、对账闭环、钱不污染信誉           | 自发法币、积分金融化           |
| P6 知识/Skill/数据资产  | P2—P5 有可复用成果          | Knowledge、Skill Foundry、Data Product、许可、使用与收益归因   | 域主可控制复用与撤回，来源和贡献完整                 | 平台无偿吞没项目经验和数据     |
| P7 域主共建 GEO 世界    | 至少多个独立域主重复协作    | 概念候选、规则提案、代表/冲突、试行、World Version、行业地图   | 多方确认概念和至少一项规则；平台未单方造行业事实     | 把 YAML 或 synthetic 当共识    |
| P8 游戏化体验           | P0—P7 已有真实路径          | 新手任务、探索、组队、项目副本、里程碑、成就和荣誉             | 提高理解与真实完成率；体验账不污染事实               | 成瘾、赌博、Pay-to-Win         |
| P9 开放工具与数据生态   | P6 有受控资产               | API、MCP、Provider Gateway、Skill/Data Product 市场            | 外部调用可授权、计量、撤回、归因并可替换供应商       | 开放裸数据库                   |
| P10 世界状态与未来      | 有足够真实项目和环境变量    | World State、Signal、Scenario、Forecast、Calibration           | 分母为零诚实返回；回测、误差和不适用可报告           | 无数据预知未来                 |
| P11 受治理自我进化      | 前述模块有 production 反馈  | Evolution Candidate、Shadow Run、域主审批、发布、回滚          | 进化可解释、可回滚、不跨 Truth/Policy                | AI 自行修改最高规则            |
| P12 第二行业实装        | 恒域世界-GEO 形成可复用结构 | 恒域世界-科技特长生或另一真实行业 World Genome                 | 不复制事实层，重新获得真实域主、授权、需求和 Outcome | 按相似度自动发布行业           |

这条路线以域主的现实收益为主线。后端工程可以并行准备下一阶段的候选契约，但未通过硬验收的能力只能标记 architecture、draft、simulation 或 observation，不能进入 production。每阶段必须先有可招募的目标域主、明确任务、价值承诺和退出路径，再批准功能开发。

### 31.2 工程能力包与依赖

以下 EP0—EP13 完整保留 V7.2 的工程能力，不等同于产品上线顺序。工程包可以在依赖满足时并行，但必须服务上面的 P-1—P12 产品价值门。

### 工程包 EP0：V10.0 宪章、角色与适配设计

批准 V10.0 词汇、域主权利、公司/平台/行业/服务/工具/规则角色分离和冻结边界，审计现有 ORM/API/页面，把每个对象标注为 Form、Facet、Module、Variable/Dimension、State、Rule Domain、Ledger Boundary 和 Truth Boundary；输出适配矩阵、迁移 ADR、停止项与 contract tests。本阶段不大规模改表。

### 工程包 EP1：Entity Kernel、Policy 与 Registries

建立统一 EntityRef、Kernel Invariants、Genome/Module/Dimension Registry 和 Rule Domain/Policy Contract；让 Company、Provider、Person、Product、Evidence、Demand、World、Tool 与 Skill Candidate 获得稳定身份。

验收：同一主体不重复建域；规则继承和 explicit deny 可测试；Module 依赖/冲突可验证；Genome、Policy、Dimension 可发布、diff 和回滚。

### 工程包 EP2：Existing Model Adapter 与 Event Ledger

为 C7/C8 与现有产品对象建立 Entity Adapter；实现 contain、reference、absorb、release、fork、merge 和谱系；统一对象中心事件参与者，补 Entity Timeline、Policy Decision 与 as_of Expression。

验收：企业可以封装产品、能力、知识、Agent 和工具；释放模块后生成新 Entity ID 且可追溯贡献、许可和适用规则。

### 工程包 EP3：Entity Dynamics 与 EntityWorld

实现 Variable Observation、Trajectory、Horizon、Environment Observation、Orientation、Influence、Action Cone 与域本位 EntityWorld；保持 Universal Fact/Derived State 边界。

验收：同一 GEO 环境信号对两个企业得到不同但可追溯的机会/风险解释；切换 observer 不改变来源事实。

### 工程包 EP4：域主入口、品牌增长与十二视图域主页

实现 Owned Data Intake、Brand Realm、AI Visibility、Intent、Gap、Target Variable、Growth Path、Milestone、活性信号和十二视图域主页；接入 Evidence、Demand、Connection、规则域、Skill 和动力学数据。

验收：真实 GEO 企业能用自己的品牌数据完成一次诊断与改进；服务商能看到过去、当下、环境、方向、可行动作、当前规则和可能未来；任何显示内容可回到来源事件。

### 工程包 EP5：Capability Runtime & Skill Foundry

把现有 Agent Tool、Prompt、YAML 和 TaskExecutor 适配为 Tool/Skill/Workflow Candidate；建立 Provider Adapter、Model Router、Sandbox、Trace、Evaluation、Approval 和 Rollback。先接一个外部模型、Codex 类编码执行器和一个自研 Tool 形成最小闭环。

验收：同一 Skill 可替换模型执行；任何 Run 可还原输入、版本、工具、数据、权限、成本和产物；系统生成的工具未经审批不能进入 production。

### 工程包 EP6：Project、Offering、Quest 与 Engagement 闭环

以 Project Realm 为主时间线，统一 Capability、Offering、Quest、Agreement、Engagement、Party、Milestone、Deliverable 和 Outcome；桥接 Marketplace Match 与 ConnectionCandidate，先跑非资金或模拟结算。

验收：Demand 到 Quest/Engagement 再到 Outcome 全链可追溯，completed 不等于 success，组队和任务规则有明确 Rule Domain。

### 工程包 EP7：Economic & Ledger Foundation

先建立资产单位、账户、双重记账、Hold/Escrow、Settlement、Refund、Revenue Share、Usage Meter 和 Reconciliation，在 simulation 中验证不变量；再接持牌支付 Provider 的测试环境，禁止用订单状态推算余额。

验收：重复请求不重复扣款；每笔 posted 转移借贷平衡；Money/Credit、Contribution/Royalty、Trust/Reputation、Experience/Achievement 与 Usage/Cost 五账隔离；退款、分账和对账可审计。

### 工程包 EP8：资产、知识与 Data Product 复利

建立 Entity Asset Account、Knowledge Entity、License、Contribution、Reuse Event、DataProductEntity 和受控分发。把真实项目产生的数据和方法沉淀为私域资产，再选择性发布生态或授权产品。

验收：数据产品携带 schema、manifest、truth、license、purpose、usage 和 revocation；来源撤回能阻止后续分发。

### 工程包 EP9：World Interaction 与游戏机制

在 simulation/observation 中实现 Quest、Party/Guild、WorldInstance、Skill Tree、XP、Achievement、Market Mechanism 和 Season；先验证理解、协作和真实完成率，不以停留时长或上瘾率优化。

验收：付费不能购买能力、信誉和 Truth；simulation 奖励不进入真实账本；失败可退出、可复盘、可申诉。

### 工程包 EP10：域主共建的真实恒域世界-GEO

用多个利益独立的真实 GEO 企业、品牌、工具、Skill、服务商、需求、项目和结果共建 `geo_ecosystem` World；行业概念和规则经过提案、冲突披露、Evidence 审查、试行和域主批准后发布。生成五张世界镜头、Industry Formation State、World State、Gap、source chain 与公共 Mission。

### 工程包 EP11：Future Engine

先做历史重放、状态估计、信号和 Scenario，再逐步引入 Forecast 与 Counterfactual；建立预测评估和校准，不以准确率幻觉上线。

### 工程包 EP12：Governed Evolution

上线 Evolution Candidate、Shadow Run、审批、配置发布、监测和回滚；只有积累足够 production 事件后，系统才可以提出规则、Skill、模型路由和任务机制优化。

### 工程包 EP13：垂直复制与开放生态

从真实 GEO World 提取可复用 Genome、Skill 与 Rule Template，优先用于恒域世界-科技特长生或另一个具备真实域主的垂直行业；行业事实、域主信誉和业务规则不得复制。验证无需复制 Universal Fact Layer 后，再开放 MCP、Developer Platform、Skill/Data Product Marketplace 与跨平台授权接口。

## 第三十二章 第一条真实验收链

整个架构必须先通过一条“真实品牌域主获得现实收益”的 GEO 生态链验收。不能先以世界地图、社区、排行榜、金币或大模型聊天作为 MVP：

1.  招募一个有真实 AI 搜索可见度或可信引用需求的企业/品牌域主，明确其当前问题、成功标准、数据边界和退出权；

2.  负责人注册账号，验证现实主体，创建或认领企业域与品牌域，并接受当前恒域世界宪章、平台技术/安全标准和清晰的数据用途；

3.  系统建立 Claimant、Controller、Operator、Beneficiary 与 Accountable Actor，负责人可查看、授权、撤回、导出、纠错和申诉；

4.  域主导入自己的品牌资料、网站、产品、内容、客户案例和已有数据；每项数据保存所有者、来源、权限、用途、保留与训练许可；

5.  系统与外部工具生成 AI 可见度、内容、引用、竞争和证据观察；观察结果默认 observed，不冒充 verified；

6.  基于域主目标生成可解释的内容缺口、证据缺口、能力缺口和行动候选，域主选择一项真实 GEO 改进任务；

7.  该任务可以调用一个平台自研 Tool、一个外部模型（GPT/豆包等）和一个 Codex 类工程执行器，固化版本、权限、成本、输入输出和数据去向；

8.  把执行流程记录为 Workflow；重复且稳定后才提炼为 Skill Candidate，在 simulation/shadow 中通过测试和审批后发布 SkillVersion；

9.  执行产生内容、代码、页面、结构化数据或发布物，域主审批后对外发布，系统持续监测 AI 引用、访问、线索和业务信号；

10. 该任务形成一项可验证结果或诚实的未达成记录，品牌域沉淀事件、Artifact、Outcome Claim、知识候选和数据资产；

11. 当该品牌域产生或接收到进一步需求时，另一个独立服务方/工具方域主提供 Capability、Offering 和 Evidence，系统生成可解释 ConnectionCandidate 和 Quest Candidate；

12. 双方人工检查适用规则、数据用途、预算、利益冲突、退出与申诉条件，进入项目 Rule Domain，形成 Party、Agreement、Order、Project Realm 与 Engagement；

13. Economic Engine 创建对应账户、Quote、Hold/Escrow 或测试授权，不允许订单状态代替账本余额；

14. Agent 在授权范围内编排 Skill、GPT/豆包类模型、Codex/Tool 和受控数据执行任务；

15. 全部 SkillRun、ToolCall、Prompt/Rule Hash、输入输出、人工审批、成本和错误形成 Execution Trace；

16. 执行产生内容、代码、报告或数据 Artifact，并进入 Milestone/Delivery；

17. 交付形成 Outcome Claim，经 Evidence 验证或保持 observed，completed 不自动等于 success；

18. 按 Agreement 完成 Settlement、Refund 或 Revenue Share；Skill、数据和人工贡献进入 Contribution/Royalty Ledger；

19. 与外部支付 Provider 对账，重复回调不重复入账，posted 转移借贷平衡；

20. 若有充分支持，记录 realized Influence；若无因果支持，只记录结果与相关；

21. verified Outcome 按既有 Trust Foundation 触发受控 Reputation Event，付款、XP 和奖励不参与；

22. Quest 形成 XP/Achievement 或 Growth Milestone，但与 Money、Contribution 和 Reputation 分账；

23. 项目产生 Entity Data Asset、Knowledge Candidate、贡献记录和环境学习；

24. 经审核的知识被 release 为可许可 ModuleEntity，并安装到新域上；

25. 合法数据被封装为 DataProductEntity，携带 schema、manifest、truth、license、purpose、usage 和 revocation；

26. 一个外部平台在授权范围内调用该 Data Product，产生 Usage Event、费用和可撤回审计；

27. Offering 与 Skill 根据真实 Outcome 发布新版本，旧交付仍指向旧版本，并可完整 rollback；

28. 企业新 Entity Expression 与 Trajectory 显示能力、规则参与、经济资产、信任、视界、向性和世界位置变化；

29. 多个类似 Demand/Quest/Engagement 促使 `geo_ecosystem` 出现带来源的行业形成信号和公共 Mission；

30. Future Engine 生成多个 Possible World、Growth Path 和 Scenario，并在未来事件发生后校准；全程无 synthetic 泄漏到 production、无 AI 输出冒充 Truth、无局部规则越过宪章、无局部 EntityWorld 改写全局事实；

31. 域主可以导出企业/品牌域、项目时间线、资产清单、授权和可信护照，撤回非必要外部工具权限，系统说明依法或依约仍需保留的审计范围；

32. 验收访谈必须由域主回答：恒域世界是否比直接使用通用 AI 多带来真实收益；是否更信任数据处理；是否愿意再次运行项目、邀请合作方并共同建设 GEO 世界。三个答案不能由注册数和页面停留代替。

在这条链跑通以前，不开放公众余额、域发币、复杂拍卖、赌博式奖励、综合排名、3D 宇宙、大规模社区或跨行业预测商业化。

## 第三十三章 成功指标

### 33.1 域价值指标

- 域主首次价值时间（Time to First Verified Value）与首个真实任务完成率；

- 自有数据授权清晰率、导出成功率、撤回传播时效、纠错与申诉关闭时效；

- 品牌域的 verified 身份/产品/案例/引用/Outcome 覆盖，及 AI 可见度改进与真实业务结果的分离归因；

- 被合法认领并验证的活跃域；

- 有效 Capability 与 Evidence 覆盖；

- Offering 被真实 Demand 使用；

- Engagement 完成率与 verified Outcome 率；

- 可追溯资产完整率、知识复用率和贡献归因率；

- Growth Milestone 与下一阶段转化；

- 域主动回访、持续完善和重复协作。

- Module 安装/迁移成功率、知识视界扩展与 Horizon 收缩的可解释率；

- Environment Signal 到行动的反应时间，以及 Orientation—Action—Outcome 的偏差复盘率。

- Skill 安装后真实任务成功率、人工接管率、失败恢复率、成本和 Outcome，而不是调用次数；

- Quest 从发现、组队、完成到 verified Outcome 的转化，以及退出/申诉是否公平；

- 域收入、支出、贡献、数据授权和资产增长能否完整对账并由本人控制。

### 33.2 Universe 价值指标

- 独立域主重复项目率、邀请合作方率、跨工具编排节省的重复输入与时间；

- 行业概念/规则中具有真实域主来源、代表披露、Evidence 和异议记录的比例；

- 平台自营利益冲突披露率、回避/独立复核覆盖率和自证路径阻断率；

- verified 关系和 Outcome 数量；

- Demand 到合格连接、Engagement 和结果的转化；

- 未验证数据隔离率与 source drift 发现率；

- 公共知识被真实项目复用并产生结果的次数；

- World Gap 被真实域行动解决的比例；

- Forecast 的覆盖、校准误差和不适用返回率；

- 新垂直 World 的配置复用率，而不是复制表数量。

- 同一核心 Module 在不同 Form/World 中的受治理复用率；

- EntityWorld 的 source manifest 完整率、observer 切换一致性与局部解释泄漏到全局事实的阻断率；

- 新行业信号被确认、证伪、合并或升级的可追溯率；

- 行业参与域、价值交换、角色分工与知识复用是否形成自我再生产。

- Rule Domain 决策可解释率、越权阻断率、规则版本接受率、申诉处理时效与治理者违规审计率；

- Ledger 不平衡事件为零、幂等重复入账为零、reconciliation 差异发现与关闭时效；

- Skill/Tool/Model 供应商可替换率、Trace 完整率、外部数据泄漏阻断率与单位 Outcome 成本；

- Data Product 的合法授权使用、撤回传播、外部复用和收益归因；

- 游戏机制是否提升真实理解、协作、交付和成长，而不是只提高停留时长。

禁止用注册数、页面数、内容量、Agent 数量、AI 调用量、签到、在线时长、金币发行量或单一综合分替代真实价值指标。

## 第三十四章 明确禁止的方向

1.  不把统一 Entity 底座理解为所有域完全同质；

2.  不把每个字符串、字段或日志永久实例化为 Entity；

3.  不把“每个域是世界中心”曲解为全局权力、绝对真理或价值优越；

4.  不用单一全局投影取代 observer-relative EntityWorld；

5.  不把 ModuleEntity 与 Entity Module 混为一个概念；

6.  不通过自动拆分所有属性制造“域爆炸”；

7.  不把 User Account 等同于 Entity，也不允许未验证认领；

8.  不让封装删除内部域的来源、贡献和许可；

9.  不把复制内容冒充同一身份；

10. 不让 World、Projection、State 或 Forecast 改写来源事实；

11. 不用单一“影响力”或“生命力”分数取代对象、维度、时间、通道和来源；

12. 不用 LLM 生成 verified Evidence、Claim、Outcome 或 Reputation；

13. 不把支付、连接、浏览量或 completed 直接当作信誉；

14. 不建立没有真实业务价值的空生态和炫技 Dashboard；

15. 不用技术架构层替代六大用户系统和八大产品工作台；

16. 不为每个垂直行业复制 Universal Fact Layer；

17. 不在数据不足时输出伪精确预测；

18. 不允许系统无审批修改 production 规则与模型；

19. 不允许局部 Rule Domain 关闭恒域世界宪章、现实法律、基本权利、来源和申诉边界；

20. 不把平台类比国家后赋予平台无限权力，也不把域自治曲解为任意主权；

21. 不允许规则静默追溯生效、隐藏关键义务或阻止合法退出与申诉；

22. 不用订单状态、缓存或积分表计算法币余额，不覆盖 posted 账本记录；

23. 不让 Money、Contribution、Reputation 与 XP/Achievement 自动互换；

24. 不发行未经合规评估的可兑换代币、收益凭证或类存款产品；

25. 不让外部模型、Skill 或 Tool 获得超出任务的文件、网络、数据、资金和生产权限；

26. 不把 AI 决策候选直接变成不可逆决策、资金处置或真实世界行动；

27. 不向外部平台导出裸数据库、无来源数据或超出许可用途的数据；

28. 不用 Pay-to-Win、赌博式奖励、虚假稀缺、成瘾机制和刷量排行榜驱动生态；

29. 不把游戏任务完成、金币、付费或在线时长当作能力和信誉；

30. 不在真实闭环跑通前扩张公众余额、域发币、复杂拍卖、3D 世界、大规模社区和跨行业预测商业化；

31. 不把平台创始人的 GEO 观点直接写成行业事实、标准或规则；

32. 不把科技特长生测试数据的 synthetic 状态误写成该行业是虚构行业；

33. 不让平台自营服务自我验证、自我评分、自我推荐或暗中获得流量优势；

34. 不以建设行业为由默认取得域主数据所有权、训练权或二次分发权；

35. 不开发可由通用 AI 直接替代、又不能沉淀身份、项目、结果和资产的重型功能；

36. 不在真实域主第一次获得价值前建设宏大行业地图、复杂规则体系和综合评分；

37. 不把域主声明直接当作 verified，也不因使用域主自有数据而声称平台已经获得信任；

38. 不用注册量、内容量、AI 调用量和停留时长掩盖“域主没有获得现实收益”。

## 第三十五章 架构冻结与可演进边界

### 必须冻结

- 万物皆可域化；

- “域”是中文根名称，Realm 是英文架构名，Entity/Node 是现有代码兼容别名；

- 域主权利、平台中立、角色分离、利益冲突披露与退出路径；

- 行业事实、概念、业务规则和工具需求由真实域主及真实项目产生，平台只提供共建与执行基础设施；

- 公司主体为深圳市恒域世界科技有限公司，主品牌为恒域世界，首个产品世界为恒域世界-GEO；

- 恒域世界-GEO 与恒域世界-科技特长生都是现实赛道，数据 truth status 与行业真实性分开；

- 每个域是自己可观测世界的坐标原点，但不是全局真理中心；

- Entity Kernel + Genome + Module 是统一生命结构；

- Form、Facet、State、Variable/Dimension、Agency 正交分离；

- Entity ID、Controller、Event Ledger、Lineage 和 Policy Bundle；

- Universal Fact、Derived State 与 Intelligence 三层分离；

- Environment、Orientation、Influence 和 Trajectory 必须带 observer/time/world/source 语境；

- Evidence—Claim—Binding 三层分离；

- Demand creates Connection；

- Connection 经 Engagement 与 verified Outcome 才可能成为成长；

- Event 是历史，State 是投影，Future 是假设；

- WorldEntity 不拥有来源域；

- AI 不能制造 Truth；

- 恒域世界宪章对所有域和治理者生效，局部 Rule Domain 不得突破上级边界；

- 有效权限由主体授权、资源策略、活跃规则域和法律约束求交，explicit deny 优先；

- Skill、Tool、Model、Workflow、Agent、Product 和 Decision Authority 必须分离；

- 所有生产 Capability Run 必须版本化、可追踪、受权、可评估和可回滚；

- Money/Credit、Contribution/Royalty、Trust/Reputation、Experience/Achievement 与 Usage/Cost 五账分离；

- 经济转移必须双重记账、幂等、原子、不可覆盖和可对账；

- Game Mechanic 只能服务真实成长，不能购买 Truth、能力和信誉；

- 对外数据必须通过 DataProduct Protocol，不得暴露裸数据库或超范围用途；

- GPT、豆包、Codex 与未来模型属于可替换工具/模型，恒域世界核心是行业身份、上下文、权限、项目、证据、结果、账本和资产；

- 项目是需求、工具、交付、结果、交易、知识和数据进入域生命的主要转化器；

- 规则演化必须版本化、验证、审批和可回滚。

### 可配置演进

- Entity Genome、Facet 和界面组合；

- Entity Module、依赖、安装、激活和迁移；

- Dimension Extension、Variable Definition、Environment Channel、Orientation 与 Influence 计算规则；

- 行业 Concept、Role、Relation 与 Evidence Requirement；

- Growth Path 和 Milestone；

- Offering、Engagement 和许可模板；

- 评分分量、权重和阈值；

- World Projection、Gap 和 Forecast Feature；

- Agent Role、Tool、Workflow、Prompt 和审批；

- Model Provider、路由、成本、数据驻留、fallback 和 Tool 能力；

- Skill Contract、测试、风险、定价、许可、安装、评估和发布节奏；

- Rule Domain、角色、准入、义务、制裁、奖励、退出和申诉模板；

- Quest、WorldInstance、Party/Guild、Skill Tree、XP、Achievement 和 Season；

- Asset Unit、计费、订单、托管、分账、收益与市场机制，但不得破坏账本不变量；

- Data Product schema、分发渠道、SLA、价格、用途和保留策略；

- 数据保留、共享、授权和商业策略。

## 结语

恒域世界的终极形态不是一张越来越大的静态图，也不是由平台预先设计好的虚拟国家，而是一个让真实域主持续完成工作、建立品牌、协作交易、验证结果并共同演化行业的运行环境。

一个人或企业带着自己的身份、数据、经历、能力、关系和尚未释放的潜在域进入；企业把团队、品牌、产品、Skill、数据、知识和信誉封装成对外主体。每个域以自己为坐标原点感知环境与机会，同时在进入的行业、组织、市场和项目中遵守已公开且合法有效的规则。一次项目把多个域卷入共同事件，Agent 调用 GPT、豆包、Codex、自研工具或外部服务完成生产；交付产生结果、证据、数据、收益与知识；账本完成结算和贡献分配；资产在许可下被释放、复制、安装和改造，形成新产品、新能力与新域；多个域视界在长期交互中形成角色、标准、价值链和行业。

恒域世界不会替域主决定行业需要什么。它必须先证明：域主愿意带着自己的数据来，能够比单独使用通用 AI 更快得到现实结果，能够控制和带走自己的资产，能够找到可信合作并积累长期信誉；然后，这些域主才有理由邀请更多参与者并共同建设行业世界。

> **最终使命：让每个行业世界中的真实域主都能拥有可持续的数字主体，使用最合适的人、AI 与工具完成真实项目，公平交换价值，建立品牌与信誉，沉淀可控资产，看见带依据的多个未来，并共同完善自己的行业；先在恒域世界-GEO 中证明，再由相应域主共建其他恒域世界-{行业}。**

### B.2 它是不是数字孪生加元宇宙

有交集，但不等同。镜像域、环境感知、状态同步和未来模拟具有数字孪生特征；多世界、身份、探索、组队、任务、资产和经济具有元宇宙/游戏世界特征。恒域世界更准确的类别是：**域本位的行业演化操作系统（realm-centric industry evolution operating system）**。数字孪生和游戏化只是它的镜像协议与体验协议；真实身份、授权、项目、证据、交易、规则共建和资产沉淀才是主干。

### B.3 理论与标准参照

本架构借鉴但不复制以下思想与产品：

1.  OpenAI GPT：Token 是模型处理文本的基础单元；GPT-4 公开为预测下一 Token 的 Transformer-style 模型。参见 [OpenAI Token 指南](https://help.openai.com/en/articles/4936856-what-are-tokens-and-how-to-count-them) 与 [GPT-4 Technical Report](https://cdn.openai.com/papers/gpt-4.pdf)。

2.  Bruno Latour Actor-Network Theory：人类与非人类行动者、网络与封装。参见 [On Actor-Network Theory](https://www.bruno-latour.fr/sites/default/files/P-67%20ACTOR-NETWORK.pdf)。

3.  Wolfram Language：不同对象共享统一 Expression 结构，并通过 Head 区分类型。参见 [Wolfram Expressions](https://reference.wolfram.com/language/tutorial/Expressions.html)。

4.  Notion Block Model：页面、内容和数据库行由统一、可组合 Block 构成。参见 [The data model behind Notion](https://www.notion.com/blog/data-model-behind-notion)。

5.  Palantir Foundry Ontology：Object、Link、Action 与业务工作流语义层。参见 [Foundry Ontology overview](https://www.palantir.com/docs/foundry/ontology/overview)。

6.  OCEL 2.0 / Object-Centric Process Mining：一个事件可同时关联多个对象并表达对象变化。参见 [OCEL Standard](https://www.ocel-standard.org/)。

7.  W3C DID、Solid 与 Verifiable Credentials：主体标识、数据控制与可验证主张。参见 [DID 1.1](https://www.w3.org/TR/did-1.1/)、[Solid Protocol](https://solidproject.org/TR/protocol) 与 [VC Data Model 2.0](https://www.w3.org/TR/vc-data-model-2.0/)。

8.  W3C PROV-O：跨系统表达实体、活动、Agent 与来源关系。参见 [PROV-O](https://www.w3.org/TR/prov-o/)。

9.  IPLD：内容寻址、不可变版本、哈希验证、去重与 DAG 谱系。参见 [Benefits of Content Addressing](https://ipld.io/docs/motivation/benefits-of-content-addressing/)。

10. NIST Digital Twins：动态模型、状态估计、预测、仿真和决策支持。参见 [NIST Digital Twins](https://www.nist.gov/digital-twins)。

11. Temporal Knowledge Graph Forecasting：使用带时间事件图预测未来关系和事件。参见 [RE-NET 论文](https://arxiv.org/abs/1904.05530)。

12. Jakob von Uexküll 的 Umwelt：生命主体并非被动拥有同一个环境，而是在自身感知与行动结构中形成意义世界。V10.0 将这个思想工程化为 EntityWorld、Horizon 和 Environment Field，但用共享 Universal Fact Layer 防止滑向“每个域都有自己事实”。参见 [A Foray into the Worlds of Animals and Humans](https://xenopraxis.net/readings/uexkull_foray.pdf)。

13. J. J. Gibson 的 Affordance：环境提供的行动可能性相对于主体能力而存在。V10.0 的 Action Cone 由 Capability、权限、资源、环境和时间共同生成。参见 [The Ecological Approach to Visual Perception](https://www.taylorfrancis.com/books/mono/10.4324/9781315740218/ecological-approach-visual-perception-james-gibson)。

14. W. Ross Ashby 的 Cybernetics：用变量、扰动、反馈、调节与 variety 理解复杂系统。V10.0 的 Environment Signal → Variable → Orientation → Action → Outcome → Learning 闭环与其相呼应，但加入了 Truth、责任与来源治理。参见 [An Introduction to Cybernetics](https://ashby.info/Ashby-Introduction-to-Cybernetics.pdf)。

15. John H. Holland 的 Complex Adaptive Systems：许多可适应主体在局部交互中产生集体结构。V10.0 用它支持“行业是多个 EntityWorld 反复交叠后的涌现结构”，而不是事先画定的静态分类。参见 [Complex Adaptive Systems](https://pzs.dstu.dp.ua/DataMining/genetic/bibl/Holland%201992.pdf)。

16. OpenAI Skills、Plugins 与 MCP：Skill 封装指令、资源和脚本，MCP 连接模型与外部工具/上下文，Codex 可通过 SDK 或 MCP 进入可审计工程流程。V10.0 将其抽象为 SkillEntity、ConnectorEntity、Capability Run 与 Skill Foundry。参见 [Build Skills](https://learn.chatgpt.com/docs/build-skills)、[Model Context Protocol](https://learn.chatgpt.com/docs/extend/mcp)、[Codex SDK](https://learn.chatgpt.com/docs/codex-sdk) 与 [Codex with Agents SDK](https://learn.chatgpt.com/docs/mcp-server)。

17. 火山方舟/豆包：提供 API、Function Calling 与 MCP 等外部模型和工具连接能力，说明 Provider-neutral Gateway 在工程上可行。参见 [Function Calling](https://www.volcengine.com/docs/82379/1262342) 与 [MCP 简介](https://www.volcengine.com/docs/82379/1539085)。

18. W3C ODRL 2.2：用 Permission、Prohibition、Duty、Party、Asset 和 Constraint 表达可互操作政策。V10.0 的 PolicyEntity 和 DataProduct License 借鉴其结构。参见 [ODRL Information Model 2.2](https://www.w3.org/TR/odrl-model/)。

19. AWS IAM Policy Evaluation：主体策略、资源策略和组织边界共同决定有效权限，适用 explicit deny 优先于 allow。V10.0 把这一思想推广为 Rule Domain 求交，但增加现实法律、宪章、退出和申诉边界。参见 [Policy evaluation logic](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic.html)。

20. TigerBeetle 的 debit/credit 与 two-phase transfer：账户和转移保持财务不变量，pending transfer 通过 post、void 或 expire 进入终态。V10.0 将其作为 Economic Ledger 的工程参考，而不是绑定具体数据库。参见 [Debit/Credit](https://docs.tigerbeetle.com/concepts/debit-credit/) 与 [Two-Phase Transfers](https://docs.tigerbeetle.com/coding/two-phase-transfers/)。

21. MDA Framework：Mechanics 产生运行 Dynamics，并形成玩家 Experience。V10.0 用它约束 Quest、WorldInstance、Reward 与市场机制的设计和评估。参见 [MDA: A Formal Approach to Game Design and Game Research](https://aaai.org/papers/ws04-04-001-mda-a-formal-approach-to-game-design-and-game-research/)。

这些理论与产品分别实现了统一表示、模块组合、对象事件、主体世界、权限策略、Skill/Tool 调用、账本守恒、游戏机制、身份控制、来源追踪、复杂适应、数字孪生或预测的一部分。恒域世界的机会不是重复其中任一产品，也不是先完成“全能系统”，而是围绕真实 GEO 域主的品牌、需求、项目和结果，把这些分散思想逐步集成为一个可实施、可审计、可商业化且可持续进化的闭环。

## 附录 E 公司与品牌启用检查

本架构确认公司名称为“深圳市恒域世界科技有限公司”，主品牌为“恒域世界”，首个产品世界为“恒域世界-GEO”。`HENGYU WORLD` 只作为辅助英文表达，是否注册与使用由品牌策略另行确认，不替代中文主品牌。

架构确认不等于企业登记或商标核准。正式启用时按顺序完成：

1.  在拟注册所在地企业名称申报系统核验“恒域世界”字号及近似名称；

2.  在中国商标网按实际商品和服务类别检索文字、拼音、英文和图形近似；

3.  首批重点考虑软件与 SaaS、技术服务、数据服务、教育培训、商业咨询及线上平台相关类别，由专业代理人确认具体类别；

4.  同步检查主要域名、公众号、视频号、小红书、抖音及应用商店名称；

5.  先申请核心文字商标，再设计视觉标识；

6.  对外材料分别标注“公司已登记/申请中”“商标已注册/申请中”等真实状态，不以架构文档代替官方结果。

公开网络初筛只能排除明显冲突，不能代替官方审查。国家市场监督管理总局说明企业名称由申请人依法自主申报；国家知识产权局的商标网上查询需要账户登录，因此最终可用性必须以企业登记机关和商标审查结果为准。
