# 第四部分 · 运行时深度剖析（AGENTS.md）

## 4.1 最高原则（0.x）

### 0.1 单一架构真相源
- 定义：35_CTO架构冻结.md → 00_项目宪章 → 02_领域模型 → REFERENCES.md → 全部 Agent → 统一实现
- 价值：阻止"产品一套、后端一套、前端一套"的分裂
- 执行：发现不一致直接驳回，要求重读冻结文件

### 0.2 开发前强制阅读
| 顺序 | 内容 |
|------|------|
| 1 | 35_CTO架构冻结.md（不违反冻结） |
| 2 | .codex/REFERENCES.md（无重复实现） |
| 3 | 相关领域文档（业务上下文） |
| 4 | 当前代码文件 |
| 5 | 当前测试文件 |

### 0.3 开发后强制验证
| 顺序 | 内容 |
|------|------|
| 1 | 运行测试（pytest / npm test） |
| 2 | 检查 API 一致性（字段/类型/路径） |
| 3 | 更新文档 |
| 4 | 检查重复实现 |
| 5 | 生成变更摘要 |

### 0.4 自主执行模式
- 默认不停：代码/文档/配置/测试/联调/命名/清理 8 类操作直接做
- 停止条件：破坏冻结、删战略、不可逆迁移、真实支付/API Key/生产凭证/资金、需用户战略决策
- 评价：这是把"AI 团队"从工具变成运营系统的关键设计

## 4.2 自动路由

| 用户输入 | 流程 |
|---------|------|
| 开发XX / 加XX / 改XX | CTO 开发流程 |
| XX有bug / 修复XX | CTO 修复流程 |
| 测试XX / 审计代码 | QA 审计流程 |
| 更新文档 / 同步文档 | Doc 同步流程 |
| 应该怎么做 / 怎么选 / 解释 | 咨询/决策流程 |
| 当前状态 / 项目进度 | 状态报告流程 |

## 4.3 5 步开发流程

1. 加载上下文
2. 5 问检查（产品模块/影响模块/数据模型/Agent兼容/复用方案）
3. 执行开发（评审→开发→测试→同步→关闭）
4. 状态回报
5. 自动回溯（经验→Agent更新→CHANGELOG→汇报）

## 4.4 核心约束（继承冻结架构）

数据模型先于页面 · 评分走 YAML · Agent 走 Context API · Entity 继承体系 · 预留字段不可删 · API 统一格式

# 第六部分 · 通信协议（protocol.md）

## 6.1 设计目的
解决"PM说A、CTO说B、FE按C开发"的信息断层：交接不再靠隐式上下文。

## 6.2 复用检查（第零段，任何工作前）
- rg 三模式扫描（文件名/函数签名/API路径）
- REFERENCES.md 映射核对
- 输出发现项表 + 复用决定（直接复用/参数化/新建 + 新建理由）

## 6.3 六段式交接（Agent↔Agent 强制）

| 段 | 作用 |
|----|------|
| 任务理解 | 防止理解偏差 |
| 决策依据 | 防止理由丢失 |
| 影响范围 | 防止盲人摸象 |
| 依赖要求 | 防止假设不一致 |
| 风险提示 | 防止意外破坏 |
| 下一步行动 | 防止执行偏差 |

## 6.4 适用范围
- Agent→Agent 派发/返回/冲突裁决：必须六段式
- 同一 Agent 内部 / 与用户对话：不需要

## 6.5 违规处理
缺任一段 → 接收方要求补全，不得基于不完整信息继续。

# 第十二部分 · 审计发现（重点）

## 12.1 P0（必须立即修，影响系统可信度）

### F-01 版本标识与实际内容不一致
- 位置：AGENTS.md 标题仍为"v3.0"，但内容已包含 v4 级零号原则
- 影响：任何人（包括未来的 Agent）读标题会低估系统能力；版本管理失真
- 建议：标题统一为 v4.2，并在文末维护版本时间线

### F-02 文件引用仍指向旧名
- 位置：AGENTS.md Step 1 引用 `agents/CTO_AGENT.md`，文件已改名 `cto_架构师.md`
- 影响：按文档执行会读不到文件；新 Agent 可能误以为角色不存在
- 建议：全文 `rg` 检查旧文件名引用，逐一替换

### F-03 R-003 未进入运行时
- 位置：AGENTS.md "二点五、行为规则" 只列 R-001/R-002；component_reuse.md 存在但未被 AGENTS.md 引用
- 影响：复用检查可能无法自动触发，"避免重复造轮子"的目标落空
- 建议：在行为规则区补 R-003 条目
