## 一、决策一句话

**后端先行，前端最后完成。** 前端不是冻结，而是"降频维护 + 最后收口"。

---

## 二、背景与依据

### 2.1 为什么可以后端先行

- 项目宪章原则：数据模型优先于页面，产业实体是基础、页面是视图。
- 当前后端已 95% 就绪（模型/API/Context/Decision/MCP/领域服务），继续后端推进是顺势而为。
- 前端已有 60+ 页面骨架，不是从零开始；"最后做"指的是最后完成深度集成，不是最后才动手。

### 2.2 为什么不能无约束地"前端最后"

| 风险 | 后果 |
|------|------|
| 后端无契约自由发挥 | 前端最后对接时字段/语义对不上，返工 |
| 后端先行失去用户价值检查点 | 技术框架先建，真实需求后补，违反 Node Demand First |
| 前端长期不碰 | 脚手架腐烂、依赖过期、与后端脱节 |
| 设计系统继续漂移 | 前端最后做时不得不再做一次"代码 vs 设计文档"对齐 |

---

## 三、三条护栏（必须同时成立）

### 护栏 1：契约先行

- 后端每个模块产出 API 契约（路径/字段/分页/错误码/权限），进入 `08_API接口规范.md` 或配套契约文档。
- 前端后置阶段按契约直接实现，不做二次猜测。
- 验收：任何后端模块关闭前，契约文档必须存在。

### 护栏 2：Node Demand First 不丢

- 后端每个 API/表/引擎必须回答：哪个真实节点、什么场景、什么问题。
- 没有需求证据的接口不得进入 P0。
- 前端最后做不会放大风险，但后端先行会，所以这条是硬准入。

### 护栏 3：前端降频维护，不冻结

- 前端脚手架保持能编译、能启动。
- 后端每个 Sprint 结束，跑一次前后端冒烟（核心链路 ≥3 条：注册 → 搜索节点 → 查看画像）。
- 依赖升级走 L1 通道，不做大改。

## 四、阶段推进

| 阶段 | 内容 | 交付物 | 验收 |
|------|------|--------|------|
| A | 领域模型 + 节点生命周期 + Event Backbone + 数据真实性 | 模型、迁移、事件类型、真实/模拟数据隔离 | 核心闭环 API 可调用 |
| B | API 层（契约先行） | API 契约 + 端点实现 + 测试 | 契约文档齐全，测试通过 |
| C | 前端深度集成 + 设计系统对齐 | 前端全链路 + UI 设计系统同步 | 5 大核心链路可用，06 系列文档与代码一致 |

全程动作：前端保持可编译 + 每 Sprint 冒烟 3 条核心链路。
