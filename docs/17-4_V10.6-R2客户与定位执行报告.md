## 1. 只读审计结论

### 直接复用

- `ClientIntake`：客户提交与状态载体。
- `IntakeAnalysis`：分析、档案、定位的版本历史载体。
- `RealmRegistry`、`NodeMembership`：Realm 归属与权限真相源。
- `GeoProject`：项目草稿载体，通过 `metadata_json` 关联 Intake、档案版本、定位版本。
- `Evidence`：域主确认档案后生成 observed Evidence。
- `AuditLog`：R2 全部关键操作审计。
- `AppShell` 与 `/realm/{realm_id}/customers`：客户与定位正式入口。

### 仅需扩展

- `IntakeService`：新增审核、档案修改/确认、待补充、定位生成/确认、工作台读取。
- `GeoProjectService`：新增“从定位显式创建项目”与幂等触发。
- 新增 `PositioningService`：本地、可解释、可重复的定位草稿引擎。
- 新增 `config/universe/positioning.yaml`：通用经营阶段模板。

### 是否新增模型或迁移

未新增数据库模型，未创建迁移。客户档案版本、定位版本、项目关联全部复用现有 JSONB 字段与 `IntakeAnalysis.version`。

### 如何避免第二套体系

- 客户、定位、项目仍以 `ClientIntake / IntakeAnalysis / GeoProject` 为唯一载体。
- 权限仍由 `NodeMembership` + 后端校验决定，前端不自行判定。
- 不建立第二套 Realm、Task、Evidence、Outcome 或权限模型。

## 2. 状态机与数据契约

```text
待审核 → 审核中 → 待补充 → 档案已确认 → 定位草稿 → 定位已确认 → 项目已创建
```

`ClientIntake.metadata_json.flow_status` 保存流程状态；旧 `status` 字段保持兼容。每次域主修改档案或确认定位都会生成新的 `IntakeAnalysis` 版本，历史不被覆盖。

## 3. 后端实现

### 客户档案

- `start_review`：进入审核中。
- `update_profile`：修改字段并生成新版本，支持 `expected_version` 冲突保护。
- `confirm_profile`：确认档案，仅生成 observed Evidence，不升级 verified、不改 Reputation。
- `request_supplement`：进入待补充并保留补充原因版本。

### 本地定位引擎

- `PositioningService` 读取客户字段，输出行业位置、经营位置、定位结论。
- 规则版本与 `config_hash` 写入版本记录。
- 缺少输入时输出 `unknown`，不虚构行业排名或百分位。
- 同输入、同 config hash 得到相同定位哈希。

### 项目触发

- `create_project_from_positioning` 必须显式 `confirmed=true`。
- 创建最小项目草稿，关联 Realm、Intake、档案版本、定位版本、定位摘要与 config hash。
- 重复触发只返回已有项目。
- 不自动生成执行计划、任务、日程、提醒或 Agent 执行。

## 4. 权限与隔离

- 读取 Realm 工作区也必须具备有效 `NodeMembership`。
- 所有客户、档案、定位、项目接口均按当前用户、Realm、Intake、Project 重新校验。
- 跨 Realm 访问返回 403，不泄露对象是否存在。

## 5. 前端实现

- `client-positioning-workbench` 作为客户与定位工作面。
- 客户列表展示流程状态、档案版本、项目状态。
- 档案字段展示值、truth scope、来源、置信度。
- 支持编辑、确认、请求补充、生成定位草稿、确认定位、显式创建项目。
- 覆盖 loading、empty、partial、blocked、error、no-permission 六状态。
- 复用唯一 `AppShell`，未创建第二套壳层。
