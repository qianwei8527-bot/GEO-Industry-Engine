> 从24份文档到第一行生产代码：90天跑通核心闭环。

## 一、战略聚焦：90天目标

**目标：跑通 GEO Industry Intelligence Loop——输入一个企业 → 建立企业实体 → 关联行业/能力/关系/证据/事件 → AI 理解 → 输出企业画像和产业位置。**

### MVP 验证条件

| 步骤 | 验证条件 | 优先级 |
|------|---------|-------|
| 实体创建 | 自动/手动建立 Entity，返回 GEO ID | P0 |
| 行业归类 | 自动归入行业分类树 | P0 |
| 能力关联 | 系统填充或用户补充能力并附证据 | P0 |
| 关系识别 | 识别上下游/合作/竞争关系 | P0 |
| Event 记录 | 记录关键事件（融资/产品发布等） | P0 |
| AI 画像 | Context Engine 输出结构化企业上下文 | P0 |
| 可视化展示 | Dashboard 展示企业画像+产业位置 | P1 |

**不做的（即使文档里写了）：**
- 交易市场（延后）
- 认证体系 L2+（只做 L1 企业实名）
- 全功能产业地图（5 张图延后）
- Neo4j 图数据库（第一阶段只用 PostgreSQL）
- Agent 面板（Agent 跑后台，无独立 UI）

## 三、前置条件：模型一致性修复（Sprint 0.5 之前完成）

以下问题必须在进入编码前修复，否则 Sprint 1 会带着技术债起步。

### 1. Company 模型字段对齐

当前 Company 在 3 处定义中字段不一致：

| 来源 | 定义的字段 | 差异 |
|------|----------|------|
| 02_领域模型设计.md | name, industry, size, products, capabilities, relationships | 有 products/capabilities 关系字段 |
| 07_后端设计.md（当前代码） | name, industry_id, size, website, description, geo_score, owner_id | 有 geo_score, owner_id 字段 |
| 03_数据架构.md | name, industry_id, size, website, description, geo_score, contact_email | 有 contact, subscription 字段 |

**修复方案**：以 02（领域模型）为准统一字段定义。Entity Base Model 上线后 Company 继承 Entity，消除冗余字段。

### 2. 扩展性预留

在 Sprint 1 新建 Entity、Capability、Event、Relationship 前，在基类中预留：

| 预留字段 | 用途 | 实现方式 |
|---------|------|---------|
| tenant_id | 多租户隔离 | 所有核心表增加该字段，默认 nil |
| region | 多地区支持 | 预留 region 枚举，第一阶段不实现地区功能 |
| lang_tag | 多语言基础 | description/text 字段预留 lang 标记 |

预留 = 建表时带字段，但第一阶段不实现相关功能。

### 3. Doc->Code 映射表

建立 `.codex/REFERENCES.md`，帮助开发者理解文档到代码的对应关系：

```markdown
02_领域模型设计.md -> backend/app/models/
    Entity(基类)  -> 待创建 in Sprint 1
    Company       -> models/company.py (需补充关系字段)
    Industry      -> models/industry.py (已有)
    Capability    -> 待创建 in Sprint 1
    Event         -> 待创建 in Sprint 1
    Relationship  -> 待创建 in Sprint 1
```

## 四、90天开发计划（6-Sprint结构）

### Sprint 0.5：工程整理（Week 1）

目标：稳定地基。

| 任务 | 说明 | 优先级 |
|------|------|-------|
| 模型对齐 | 统一 Company 字段定义（02/03/07 对齐），消除重复定义 | P0 |
| 扩展性预留 | 在核心模型层增加 tenant_id、region、lang_tag 字段 | P0 |
| Doc->Code 映射 | .codex/REFERENCES.md 建立文档到代码模块的映射表 | P0 |
| 项目结构整理 | 后端/前端/agents 目录划分明确 | P1 |
| scripts 清理 | 活跃脚本移到 scripts/active/，其余归档或删除 | P1 |
| Docker 完善 | 确认 docker compose up 可用，所有服务正常启动 | P0 |
| 里程碑 | docker compose up 后后端 /health 返回 ok |

### Sprint 1：Core Model（Week 2-3）

目标：跑通数据闭环"输入一个企业 -> 建立实体 -> 关联关系 -> AI理解 -> 输出画像"。

| 模型 | 说明 | 优先度 |
|------|------|-------|
| Entity(Base) | 统一实体基类：geo_id, entity_type, name, description, is_verified | P0 |
| Company | 企业特有字段（网站、规模等），继承 Entity | P0 |
| Industry | 行业分类树（已有，保持不变） | P0 |
| Capability | 能力/标签，与 Company 多对多 | P0 |
| Evidence | 证据来源：类型、URL、可信等级 | P0 |
| Relationship | 关系：source->target，relation_type，weight | P0 |
| Event | 产业事件：类型、时间、影响等级 | P0 |
| Product | 产品/服务，继承 Entity | P1 |
| Person | 产业个人，继承 Entity | P1 |

注：评分系统从 V1 起使用 YAML 配置化（config/scoring/visibility.yaml 等），不做硬编码。

### Sprint 2：Context Engine + MCP Server（Week 4-5）

目标：建立 AI Agent 可以调用的上下文接口。Context Engine 是产业知识层到智能决策层的桥梁。

| 模块 | 功能 | 输出 |
|------|------|------|
| Context API | GET /context/company/{id} | 企业完整上下文（Entity + Capability + Relationship + Event） |
| Context API | GET /context/industry/{id} | 行业上下文（结构 + 头部企业 + 趋势） |
| Context API | POST /context/search | 自然语言搜索 -> 产业对象 |
| MCP Server | geo__search_company | 企业搜索 MCP 工具 |
| MCP Server | geo__search_industry | 行业搜索 MCP 工具 |
| MCP Server | geo__match_capability | 能力匹配 MCP 工具 |
| 配置化 | config/scoring/ 目录生效 | 评分权重 YAML 配置 |

验收标准：调用 /context/company/{id} 返回完整企业画像，MCP 工具可被外部 Agent 调用。
### Sprint 3：GEO Decision Engine + 评分体系（Week 6-8）

目标：9 个决策模型上线，评分引擎配置化运行。

| 模块 | 功能 | 说明 |
|------|------|------|
| Scoring Engine | GEOScore 计算 | 9 因子加权模型（YAML 权重可配置）|
| Trust Engine | TrustScore 计算 | 基于 Evidence 的信任评分 |
| Recommender | AI 推荐逻辑 | Context Engine 输出 + 评分排序 |
| GEO Index | 企业 500 / 行业指数 | 公开榜单 API |
| 评分配置 | config/scoring/*.yaml | visibility / trust / authority 三套配置 |

验收标准：输入企业 ID，系统返回 GEO Score + Trust Score + 排名 + 推荐理由。
### Sprint 4：Agent OS（Week 9-10）

目标：第一个 Agent 跑通"输入企业 -> 分析产业结构 -> 输出发展建议"。

| Agent | 功能 | 依赖 |
|-------|------|------|
| Context Agent（基础设施） | 读取 Entity/Industry/Capability，统一上下文供给 | Sprint 2 |
| Industry Analyst Agent（核心） | 输入企业，输出产业结构、关系、趋势、机会 | Context Agent |
| Data Filler Agent（辅助） | 自动化补充和验证数据 | --- |

验收标准：调用 Industry Analyst Agent -> 输入企业 ID -> 返回产业分析报告。
### Sprint 5：商业化应用层（Week 11-12）

目标：前端展示 + 对外访问控制。

| 模块 | 功能 |
|------|------|
| Dashboard | 企业画像展示 + 产业位置定位 |
| Industry Map | 关系展示（Graph View，Context Engine 的可视化）|
| GEO Scoring UI | 评分可视化 + 趋势图表 |
| API 访问控制 | Rate Limit / Auth / Pricing |
| 用户注册流程 | 注册 -> 添加企业 -> 查看 GEO Score |

验收标准：外部用户可注册、搜索企业、查看 GEO 评分。
### Sprint 边界规则

| 原则 | 说明 |
|------|------|
| 数据模型优先于页面 | 先建表，再做 UI |
| 每层可配置 | 权重和阈值走 YAML，公式逻辑写代码 |
| 所有能力走 API | Agent、前端、第三方都通过 API 访问数据 |
| 每个 Sprint 可独立验证 | Sprint 结束时对应模块必须可以跑 |

## 五、MVP 定义：GEO Industry Intelligence Loop

**MVP 不是"页面上线"，而是跑通一个核心闭环：**

```
输入一个企业 -> 系统建立企业实体 -> 关联行业/能力/关系/证据/事件 -> AI 理解 -> 输出企业画像和产业位置
```

### 闭环验证条件

| 步骤 | 条件 | 依赖 Sprint |
|------|------|------------|
| 搜索 | 输入企业名或域名，返回匹配 | Sprint 2 |
| 实体创建 | 自动/手动建立 Entity，返回 GEO ID | Sprint 1 |
| 行业归类 | 自动归入行业分类树 | Sprint 1 |
| 能力关联 | 系统填充或用户补充能力并附证据 | Sprint 1 |
| 关系识别 | 识别上下游/合作/竞争关系 | Sprint 1 |
| Event 记录 | 记录关键事件（融资/产品发布等） | Sprint 1 |
| AI 画像生成 | Context Engine 输出结构化企业上下文 | Sprint 3 |
| 可视化展示 | Dashboard 展示企业画像+产业位置 | Sprint 5 |

**这个闭环跑通，项目就"活"了。** 在此之后：
- 增加更多 Agent（Company Intelligence / GEO Optimization）
- 开放更多地图视图（5 张 MECE 地图）
- 启动交易市场和认证体系（L2+）
- 引入 Neo4j 图数据库（数据量增长后）
