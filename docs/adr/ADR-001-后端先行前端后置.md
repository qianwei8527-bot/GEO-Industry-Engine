# ADR-001: 后端先行、前端后置

> 状态: 已提议
> 日期: 2026-08-03
> 决策人: CTO Agent
> 替代: -

---

## 背景

GEO-Industry-Engine 处于架构完善 + 工程推进期。当前后端完成度约 95%，前端已有 60+ 页面骨架但设计系统与代码脱节。需要明确开发顺序：是否允许"先做代码、最后完成前端"。

## 决策

采用**后端先行、前端最后完成**的开发顺序，并设置三条护栏：

1. 契约先行：后端模块同步产出前端消费契约。
2. Node Demand First：后端每个 API/表/引擎必须有节点需求证据。
3. 前端降频维护：保持可编译、可启动，每 Sprint 冒烟 3 条核心链路；前端深度集成放最后。

## 选项分析

| 选项 | 描述 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A | 后端先行，前端最后 | 符合数据模型优先原则；后端可先收敛 | 失去用户价值检查点；集成风险后置 | **选择** |
| B | 前后端同步推进 | 反馈及时；设计系统可同步 | 上下文分裂；两个系统同时漂移 | 否 |
| C | 前端先行 | 视觉先行，快速验证 | 违反数据模型优先；骨架无真实数据 | 否 |

## 选择的理由

- 项目宪章明确"产业实体是基础、页面是视图"。
- 后端已高度成熟，继续推进是顺势；前端已有大量骨架，最后收口成本可控。
- 三条护栏可对冲 A 的主要缺点。

## 影响范围

- 代码: backend（阶段 A/B）、frontend（阶段 C 收口）
- 文档: 08_API接口规范.md（契约）、06 系列（最后对齐）、docs/44 阶段规划
- 测试: 后端测试 + 每 Sprint 前后端冒烟
- 部署: 无独立变更

## 后果

### 正面
- 后端先形成稳定内核，前端接入成本下降。
- 符合既有架构原则。

### 负面
- 用户价值检查点后置：以 Node Demand First + 契约先行对冲。
- 前端长期低维护：以冒烟链路 + 降频更新对冲。
- 可接受风险：集成集中在阶段 C，需预留返工缓冲。
